# From GenAI to Agentic AI Constitution

本憲章は、`specs/001-agentic-ai-platform/spec.md` の横断制約（Technical Constraints、Runtime
Environment、LLM Provider & Test Strategy、Non-Functional Requirements）と、要件レビュー
（`review-2026-09-26.md`）の決定のうち、**マイルストーンをまたいで譲れない判断基準**を統治規範として
昇格したものである。各原則には**検証方法**を併記する。検証方法を持たない原則は適合を判定できない
ため、本憲章には置かない。

本リポジトリは教材のリファレンス実装である。したがって「動くこと」に加えて、「学習者が同じ手順で
同じ結果を再現できること」と「原則を破るとテストが落ちること」を品質の定義に含める。

## Core Principles

### 1. ワークフローとエージェントを峻別する

制御フローを LLM が決める処理（エージェント）は、AI SDK v7 の `ToolLoopAgent` で実装することが
MUST である。制御フローをコードが決める処理（ワークフローパターン）は、`generateText` /
`streamText` を素の TypeScript で合成し、`ToolLoopAgent` を使ってはならない（MUST NOT）。

- 構造化出力は `output: Output.object(...)` を使う。非推奨の `generateObject` / `streamObject` を
  使ってはならない。
- ツール入力は Zod の `inputSchema` で定義する。
- LangChain / LangGraph の抽象を持ち込まない。移植で失われた機能は解説の対照表に記録する。
- マルチエージェント構成は、単一エージェント + ツールで不足することを実測で示し、トークンコストの
  増加に見合う根拠を設計に記録した場合に限り採用する。

**根拠**: 本カリキュラムの中心的な学習目標は「ワークフローとエージェントの峻別」である。実装が
両者を混ぜると、教材そのものが誤った設計を教える。

**検証**: `/sdd-plan` と `/sdd-analyze` で、各コンポーネントがどちらに属するかを確認する。
`generateObject` / `streamObject` の使用は Biome またはリポジトリ走査テストで失敗させる。

### 2. エージェントループは必ず止まり、止まった理由を語る

すべての `ToolLoopAgent` は、最大ステップ数、累積トークン使用量の上限、実行時間の上限の **3 種の
停止条件**を持つことが MUST である。停止条件を持たないエージェントの生成経路を用意してはならない。

- 停止理由は閉じた語彙（`completed`、`step-limit`、`token-budget`、`timeout`、`aborted`、`error`）
  の 1 つとして実行結果に含める。語彙の追加は本憲章の改正を要する。
- 学習者による停止は、実行中の LLM 呼び出し、ツール実行、サンドボックスへ伝播させる。
- 1 回のツール実行には時間上限を設け、超過はツール結果としてエージェントへ返す。
- 1 エージェントに登録するツールは **20 以下**とする。超過する構成は起動時に拒否する。

**根拠**: 暴走するエージェントを物理的に遮断できなければ、後続の安全策（承認ゲート、サンドボックス）
はすべて前提を失う（001 Req 6、003 Req 1.15）。

**検証**: 停止理由ごとのユニットテスト（`mock` モード）。エージェント生成を単一のファクトリ
（`createGuardedAgent`）に集約し、それ以外の `new ToolLoopAgent` をリポジトリ走査テストで検出する。

### 3. 品質ゲートは決定論的で、空振りしない

`mise run gate` は lint、format チェック、typecheck、テストを 1 コマンドで実行する唯一の検証入口で
あることが MUST である。

- `gate` は `mock` モードで実行し、API キー、Docker、ネットワークを必要としない。未モックの
  ネットワークアクセスはテストを失敗させる。
- 同一コミットで 10 回連続実行して 10 回とも同じ合否を返す。依存インストール済みの開発機で
  5 分以内に完了する。
- 各段で、実行したテスト数または走査したファイル数が 0 の場合は失敗させる。
- 実行できなかった比較・品質評価のテスト（`local` 限定）は理由付きの「スキップ」として報告し、
  合格として数えない。
- テストは**非空虚**でなければならない。エージェントの制御ロジック（ツール選択、停止条件、検証処理）
  を壊した変更で落ちることを確認していないテストは、テストとして数えない。

**根拠**: 「API キーなしで全テストが決定論的に通る」ことは本プラットフォームの価値の 1 つである。
空振りの緑は、壊れた教材を合格させる。

**検証**: `gate-reporter` の件数アサート、`gate:repeat`、ミューテーションテスト（`test:mutation`）。

### 4. テストを先に書く

実装コードは、それを要求する失敗するテストより先に書いてはならない（MUST NOT）。
RED（失敗を確認）→ GREEN（最小実装）→ REFACTOR の順序を守る。既に動くコードに合わせて後から
テストを書くことを禁ずる。

テストが予期せず落ちたときは、スキップ・リトライ・しきい値の引き下げではなく、**停止して根本原因を
特定する**ことが MUST である。

**検証**: `tdd-enforcement` skill の適用、コミット履歴でテストが実装に先行しているかのレビュー。

### 5. 型で境界を固定する

- TypeScript は strict モードで型検査を通す。`packages/ai-core` の公開 API に `any` を含めては
  ならない（Biome `noExplicitAny`）。
- システム境界（HTTP ハンドラ、ツール入力、LLM の構造化出力、環境変数、外部 API の応答）を越える
  データは Zod スキーマで検証する。内部コードは検証済みの型を信頼し、防御的な再検証を重ねない。
- `packages/ai-core` は React / Next.js に依存せず、テストや CLI から import できる。UI は検査・配信・
  描画だけを担い、LLM を呼ぶロジックを持たない。

**検証**: `mise run gate` の typecheck と Biome。`ai-core` の依存に UI フレームワークがないことを
リポジトリ走査テストで確認する。

### 6. 被害範囲を最小にする

- LLM が生成したコード（データ分析のコード、ハーネスの実装コードと検証テストスクリプトを含む）を
  ホスト環境で実行してはならない（MUST NOT）。サンドボックス（E2B）またはコンテナ内でのみ実行する。
  隔離環境がない場合、その機能は起動しない。
- ツールには読み取り / 書き込み / 破壊的のリスク区分を付与する。承認ゲート（004 Req 4）が実装される
  までは、書き込み・破壊的なツールをエージェントに登録してはならない。
- 承認要否はコミット済みのサーバー側コードで決める。クライアントが送る値や実行時のヒューリスティック
  で承認要否を決めてはならない。承認・再開のリクエストは未知のフィールドを拒否する厳格なスキーマで
  検証し、会話履歴・モデル・トークン使用量を受け付けない。
- 承認要求はサーバー側で発行し、ツール呼び出し ID と引数に束縛して署名し、1 回だけ消費できる。
- 計算などのツールは `eval` / `new Function` を使ってはならない。

**根拠**: 承認ダイアログは広く置くほど読まれずに承認される。安全性は承認だけでなく、隔離、
リスク区分、ループ予算の組み合わせで担保する。

**検証**: リポジトリ走査テスト（`eval` / `child_process` の禁止箇所、ツール登録のリスク区分）、
004 の承認経路テスト（承認・拒否・改ざん・二重消費・未知フィールド）。

### 7. 秘密情報とサプライチェーンを守る

- API キーは環境変数からのみ読み込み、サーバー側でのみ参照する（`server-only`）。ブラウザ向け
  バンドルに含めてはならない。`.env` をコミットせず、キー名だけの `.env.example` を提供する。
- 生のプロンプト、ツール引数の値、秘密情報をログに出力しない。シークレットスキャンの結果にも検出値を
  出力しない。
- 依存解決は公開から 24 時間未満の版を採用しない（`minimumReleaseAge: 1440`）。インストール
  スクリプトは `allowBuilds` で明示許可したパッケージに限り、各エントリに許可理由を記す。CI は
  `--frozen-lockfile` で実行する。
- GitHub Actions の `uses:` はコミット SHA で固定し、各ジョブの `permissions:` を最小にする。

**検証**: `secret-scan`（CI で全履歴、pre-commit でステージ済み変更）、クライアントバンドル検査、
`audit`、ワークフロー定義の SHA 固定を検査するテスト。

### 8. 事実は実測で確定する

ライブラリの API、バージョン、モデル ID、ツールの振る舞いに関する主張は、公式ドキュメント（Context7
等）の確認と、実インストール・実行による実測を根拠に記録することが MUST である。元教材や
カリキュラムの記述、記憶を根拠にしてはならない。

- モデル ID はモデルカタログに一元管理する。カタログ外のモデル ID をコードや文書に書いてはならず、
  品質ゲートで検出する。解説でも例外を設けず、採用したモデルはカタログへの参照で書く。
- 先行版（TypeScript 7.1、Node v26 等）は範囲指定ではなく完全一致の版で固定し、「なぜこの版か」を
  記録する。非互換で TypeScript 6.x へ後退する場合は、範囲・理由・解除条件を記録する。
- 移植時の変更点（カリキュラム確定版の差分記録と、実測で確定した API・版）は、モジュール解説に
  明記する（001 Req 7.4）。
- 誤りが判明した記述は、実測結果で置き換える。

**検証**: `research.md` の Evidence 欄、`check:model-ids`（gate の一段）、`/sdd-analyze`。

### 9. 段階ゲートを飛ばさない

実装はマイルストーン順（M1 → M2 → M3 → M4）に進める。後続 spec（002〜004）の要件は、先行
マイルストーンの実装が完了してから承認する。マイルストーンの並行実行、順序の入れ替え、受け入れ基準の
事後緩和を禁ずる。

- 各 spec の要件・設計・タスクの各フェーズは**人間が承認**する。一括の自動承認を禁ずる。
- 各実装フェーズの完了後に、新規コンテキストで敵対的レビューを 1 回行う。
- レビュー記録は 1 ラウンド 1 ファイルとし、過去のラウンドを上書きしない。承認判断の根拠となる記録は
  git 追跡対象に置く。

**根拠**: 誤読された要件は下流のすべてが継承する。spec を 4 つに分割した目的（Review C-1）は、先行
マイルストーンの実装結果で後続の要件を正すことにある。

**検証**: 各 `spec.json` の `approvals`、`specs/*/review-*.md` と `.sdd/reviews/` の記録。

### 10. 依存は plan に宣言してから追加する

`plan.md` に宣言されていない第三者依存の追加を禁ずる。追加が必要なときは、先に plan を改正する。
インフラ（Docker Compose のサービス等）の追加も同じ規律に従う。API キーを要する外部サービスは、
キーがない場合のスキップまたは代替実装を必ず持つ。

**検証**: `/sdd-analyze` で `package.json` の依存と plan の宣言を突き合わせる。

### 11. 教材はテストに裏付けられる

各モジュールは、リファレンス実装、テスト、日本語の解説ドキュメントの 3 点を揃えて完成とする。

- 解説は学習目標、ハンズオン手順（必要な実行モードと外部サービスを明示）、習熟度判定チェックリスト、
  実装とテストの所在、元教材との対照表を含む。
- チェックリストのうち自動テストで検証できる項目は対応するテストを参照し、参照先の実在を品質ゲートで
  機械的に検証する（走査した参照が 0 件なら失敗）。
- ハンズオンは `local` / `live` を原則とし、自動テストは `mock` で完走できる。

**根拠**: 習熟度をチェックリストと自動テストで客観判定できることは、本プラットフォームの価値の 1 つ
である。テストに結びつかない解説は、実装と乖離しても誰も気づかない。

**検証**: `docs:check`（gate の一段）。

## Additional Constraints

**ツールチェーン**: ランタイムとパッケージマネージャは `mise.toml` で固定する。pnpm workspaces +
Turborepo のモノレポとし、コマンドは `mise run <task>` → `pnpm exec <cmd>` の順で実行する。素の
ツールを直接実行しない。TypeScript は全ワークスペースで 7.1 先行版を完全一致で固定する（原則 8 の
例外手続きを除く）。

**lint / format**: 全ワークスペースに Biome を単一の規約として適用する。`noUnusedVariables` /
`noUnusedImports` は `error` とする。具体的なスタイルは設計（ADR）で定める。

**LLM 実行モード**: `mock`（テスト専用、決定論的）、`local`（Ollama、Web アプリとハンズオンの既定）、
`live`（Anthropic / OpenAI / Azure OpenAI / Google。IBM watsonx.ai は AI SDK v7 対応実装がある場合に
限る）の 3 層を、コードを変えずに設定で切り替える。

**実行環境**: 学習者 1 人のローカル実行を前提とし、認証・マルチテナントは扱わない。Postgres +
pgvector と Langfuse は Docker Compose で起動し、品質ゲートとは別のタスクでだけ使う。検索は pgvector +
Reciprocal Rank Fusion、可観測性は OpenTelemetry（OTLP）とする。

**品質目標（NFR の正本は 001 spec）**: `packages/ai-core` の行カバレッジ 80% 以上。WCAG 2.2 AA と
キーボード操作。最新安定版の Chrome / Firefox / Safari。`mock` でのストリーミング反映 100 ms 以内。

**言語**: spec・解説・UI 文言は日本語。コード、識別子、コメント、コミットメッセージ、PR は英語。
ルートの `AGENTS.md` は英語で維持する。

**Evals のしきい値**: しきい値の引き下げは PR で明示的に行う。テストを通すための暗黙の引き下げを
禁ずる。具体的な値は TODO(EVALS_THRESHOLD)。

## Governance

- **Authority**: 本憲章はアドホックな判断に優先する。ただし本憲章は spec を置き換えない。個別の要件と
  数値は spec が正本を持ち、本憲章は「どの判断基準が譲れないか」を定める。spec と本憲章が矛盾する
  場合は、spec を改訂するか本憲章を改正するかを明示的に決め、両者を同時に更新する。
- **Amendment procedure**: 変更提案 → レビュー → バージョン昇格 → Sync Impact Report への記録。
  原則の追加・削除・再定義は、影響する `plan.md` / `tasks.md` / `AGENTS.md` の同期確認を伴う。
- **Versioning policy**（セマンティック）:
  - MAJOR: 後方非互換な変更（原則の削除・再定義）。
  - MINOR: 原則・節の追加、または実質的な拡張。
  - PATCH: 明確化・表現修正。
- **Compliance review**: 設計とタスクを MUST 原則に対して検査する（`/sdd-plan`、`/sdd-tasks`、
  `/sdd-analyze`）。加えて原則 9 に従い、各実装フェーズの完了後に新規コンテキストで敵対的レビューを
  行う。
- **本憲章の正本**: `.sdd/memory/constitution.md`（git 追跡対象）。
