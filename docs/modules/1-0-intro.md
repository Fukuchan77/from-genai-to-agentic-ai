## 学習目標

このモジュールを終えると、次のことができます。

- 生成 AI（反応型）と Agentic AI（能動型）の構造的な違いを、「出力が文章か、環境の状態の変化か」という軸で説明できる。
- IBM の3段階成熟度モデルを使って、与えられたシステムの記述を、根拠を挙げて3水準のいずれかに分類できる。
- Agentic AI の7段階の閉ループ（知覚からオーケストレーションまで）を順に言え、各段を本カリキュラムのどのモジュールが実装するかを対応表から示せる。
- プロンプトの工夫からシステム全体（ツール、メモリ、停止条件、評価）の設計へ重心が移る理由を説明できる。

### 「テキストの生成」から「状態の変更」へ

生成 AI は、入力に対して静的なコンテンツ（文章、画像、コード）を出力して止まる**反応型（Reactive）**のシステムです。出力の価値は読み手が判断し、次に何をするかも人間が決めます。環境（DB、ファイル、チケット、外部サービス）は、システムの外側で人間が動かします。

Agentic AI は、最小限の人間の監督のもとで長期的な目標を達成するために、自ら推論し、外部ツールを実行して、環境の状態を**能動的（Proactive）**に変え続けるシステムです。出力は「文章」ではなく「環境がどう変わったか」で評価されます。

この違いは、評価のしかたに直結します。

| 観点 | 生成 AI | Agentic AI |
|---|---|---|
| 成果物 | 返ってきた文章 | 変更後の環境（例: チケットの状態、コミット、ファイル） |
| 良し悪しの確かめ方 | 文面を読んで判断する | 環境の最終状態（Outcome）を調べる |
| 失敗の姿 | 不正確・不適切な文章 | 誤った操作が実行されてしまう |

3つ目の行が、後続のモジュールで停止条件、承認ゲート、サンドボックスを扱う理由です。文章の誤りは読んで捨てられますが、実行された操作は取り消せない場合があります。

**本リポジトリでの現在地を正直に書きます。** Phase 1 の `ToolLoopAgent` が使えるツールは `read-only` に限られます。承認ゲート（4-4）が実装されるまで、書き込み・破壊的なツールはエージェントに登録できない設計です（`packages/ai-core/src/aci/tool-set.ts`）。つまり M1 のエージェントは「ループを回して環境を読む」ところまでで、「環境を変える」実装は Phase 3 以降です。

### LLM は認知・計画エンジン

LLM は「知性そのもの」ではありません。システムの中核にある**認知・計画エンジン**（次に何をするかを決める部品）であり、決定論的なコード（API、データベース、シェル）と組み合わさって初めて、実世界のタスクを完遂できます。

LangChain で言えば、`ChatOpenAI` を呼び出す1行がシステムなのではなく、`AgentExecutor` を含む周辺の仕組み全体がシステムです。本リポジトリでは、役割が次のように分かれています。

| 役割 | 担うもの | 本リポジトリでの所在 |
|---|---|---|
| 認知・計画（次の一手を決める） | LLM | モデルカタログとゲートウェイ経由で解決する（`packages/ai-core/src/models/`） |
| 行動（環境に作用する） | 決定論的なツール | `defineAciTool` で定義し、リスク区分を必ず宣言する（`packages/ai-core/src/aci/`） |
| 制御（いつ止めるか） | コード | ステップ数・累積トークン・実行時間の3種の停止条件（`packages/ai-core/src/agents/`） |

「プロンプトエンジニアリングからコンテキストの設計へ」という言い方もこの分担から出てきます。1回のプロンプトの巧拙より、ツール・メモリ・停止条件を含むシステム全体の設計が品質を決めます。

### IBM の3段階成熟度モデル

IBM の定義に基づき、システムの自律性を3つの水準に分けます。

| 水準 | 内容 | 判定の手がかり |
|---|---|---|
| Level 1: Generative AI（受動的生成） | 入力プロンプトに対して、文章・画像・コードなどの静的コンテンツを出力して完了する。状態を変えず、環境と能動的にやり取りしない | 出力が文章のみで、1回の応答で完了する |
| Level 2: AI Agents（タスク自動化） | 事前に定義されたワークフローに沿って、特定のタスクやルール化された外部ツールを実行する。局所的で決定論的な処理が中心 | 手順やツールの使い方が事前に決まっている |
| Level 3: Agentic AI（自律型エージェントシステム） | 最小限の人間の介入で、複雑でオープンエンドな長期目標を達成する。7段階の閉ループを自律的に反復し、環境の状態を変え続ける | 目標だけが与えられ、手順は実行中に決まる |

分類の例を3つ挙げます。

- 「記事の URL を渡すと、要約カードを返す」: 入力に対して構造化された出力を返して完了します。環境を変えません。**Level 1** です（1-3 の要約パイプラインがこれにあたります）。
- 「問い合わせを分類し、決まった手順で FAQ を検索して回答案を作る」: 手順がコードで決まっており、ルール化されたツールを使います。**Level 2** です。
- 「『来週の顧客ミーティングを設定して』と頼むと、参加者の空き時間を調べ、会議室を押さえ、招待を送り、衝突したら調整し直す」: 手順は実行中に決まり、環境の状態（予定表）を変え続けます。**Level 3** です。

境界は「LLM を使っているか」では決まりません。Level 1 でも LLM は使われます。分かれ目は、**誰が制御フローを決めるか**と**環境の状態を変えるか**です（ワークフローとエージェントの区別は 2-3 で詳しく扱います）。

水準はシステム全体の性質で、モデルの性能とは別の軸です。高性能なモデルを使った1回きりの要約は、Level 1 のままです。

### 7段階閉ループ

Level 3 のシステムは、次の7段階を一周ずつ回します（IBM）。直線ではなく**閉ループ**なのは、実行の結果が次の知覚に戻るためです。

| 段 | 名称 | 内容 |
|---|---|---|
| 1 | 知覚（Perception） | API、センサー、DB、ユーザーのログなどから環境の情報を取得する |
| 2 | 推論（Reasoning） | 取得した情報を解析し、制約を把握する |
| 3 | 目標設定（Goal Setting） | 高次の目標を、達成可能なサブゴールに分解する |
| 4 | 意思決定（Decision-Making） | コスト、安全性、確信度を評価し、行動の経路を選ぶ |
| 5 | 実行（Execution） | ツールの呼び出しやコマンドの実行を行う |
| 6 | 学習・適応（Learning & Adaptation） | 実行結果やエラーをフィードバックし、計画を修正する |
| 7 | オーケストレーション（Orchestration） | 複数のエージェント、リソースの配分、状態遷移を統括する |

```text
        ┌────────────────────────────────────────────────────┐
        ▼                                                    │
 1 知覚 → 2 推論 → 3 目標設定 → 4 意思決定 → 5 実行 → 6 学習・適応
                                                             
 7 オーケストレーション: 上の1周全体と、複数エージェント・資源・状態遷移を統括する
```

LangChain の `AgentExecutor`（ReAct 型）に慣れた読者には、「Thought → Action → Observation」の繰り返しが 2・4・5・1（と6）に、おおむね対応して見えるはずです。7段階モデルが足しているのは、その外側にある3（目標をサブゴールへ分解する）と 7（複数の主体・資源・状態の統括）です。1周のループだけなら、Phase 1 の `ToolLoopAgent` でも体験できます。

**7段階は実装の設計図ではなく、概念の整理です。** 1つのエージェントがこの7つを別々のコンポーネントとして持つ必要はなく、LLM の1回の推論が 2〜4 をまとめて担うこともあります。次の対応表は、「各段が、カリキュラムのどのモジュールで学習・実装の主題になるか」を示すものです。

### 生成AIとの比較マトリクス

| 比較の観点 | 生成 AI | Agentic AI |
|---|---|---|
| 主目的 | プロンプトに対するコンテンツの生成・要約・翻訳 | 定義された長期目標の自律的な達成 |
| 動作形態 | 反応型。1ステップで応答が完了する | 能動型。目標の達成までループを実行する |
| 自律性 | 限定的。ステップごとに人間の指示が要る | 高い。多段階の推論と行動の決定を自律的に行う |
| 環境とのやり取り | モデルの内部知識と静的なコンテキストに依存する | API、DB、シェル、Web などを能動的に操作する |
| エラーからの回復 | ユーザーの再指示やプロンプトの修正に依存する | 環境から得た客観的な事実（Ground Truth）で自己修正する |
| 開発の主眼 | プロンプト設計、RAG パイプライン、出力スキーマ | ワークフロー制御、ACI 設計、ハーネス、状態管理 |

「開発の主眼」の行が、カリキュラムの進み方に対応します。Phase 1〜2 はプロンプト、出力スキーマ、RAG（左の列）から始め、Phase 3 で ACI 設計、Phase 4 でハーネスと状態管理（右の列）へ進みます。

| 段 | 主に学ぶモジュール | 補助するモジュール | 何を実装するか | Phase 1 での扱い |
|---|---|---|---|---|
| 1 知覚 | 2-1 TypeScript ネイティブ RAG | 1-2、2-2、3-1、4-1 | 文書の検索、引用つき回答。Agentic RAG は検索を「ツール」にして必要なときだけ呼ぶ | 部分的。1-2 の `read-only` ツール（時刻、天気、為替、Web 検索）で外部の情報を取り込む |

| 5 実行 | 3-1 ACI と MCP | 1-2、3-3 | ツール定義の設計、MCP 接続（3-1）、サンドボックスでのコード実行（3-3） | 部分的。1-2 の `ToolLoopAgent` がツールを実行するが、`read-only` に限る |
| 6 学習・適応 | 3-3 データ分析エージェント | 2-3、3-1、3-2、4-3 | 実行エラーを返す自己修正ループ（最大 3 回、3-3）、Evaluator-Optimizer（2-3）、Ground Truth に基づく進行（3-1）、Outcome の評価（4-3） | 最小限。ツールのエラーが結果としてループに戻る点だけ |

この表の読み方を3点補足します。

- **Phase 1 はどの段も完成させません。** 7段階を自律的に反復して環境を変える Level 3 のシステムは、Phase 3〜4 で組み上がります。Phase 1 は、閉ループの最小の部品（モデル呼び出し、ツール実行、停止条件）を用意する段階です。
- **1つのモジュールが複数の段にまたがります。** たとえば 3-2 の Replanner は、タスク完了ごとに結果を見て計画を組み替える（6 学習・適応）と同時に、`continue` / `replan` / `finish` を選ぶ（4 意思決定）ものです。「主に学ぶモジュール」は、その段が学習の主題になる最初の場所を指します。
- **4-5 は設計時の判断です。** 4-5 の選定フローは、実行時にエージェントが下す意思決定ではなく、開発者が「そもそも自律型エージェントを使うか」を決める判断です。表では補助として挙げていますが、段 4 の実装そのものではありません。

## ハンズオン手順

このモジュールはコードを書きません。手順は「分類する」「対応づける」「実コードで対比する」の3つで、いずれも手元で数分で終わります。

### 手順 1: システムの記述を3水準に分類する

- 実行モード: 不要（コードを実行しない）
- 外部サービス: なし

次の4つの記述を、Level 1〜3 のどれに分類するかを、根拠つきで書いてください。「LLM を使っているか」ではなく、制御フローを誰が決めるかと、環境の状態を変えるかを根拠にします。

1. 社内文書の PDF を貼ると、箇条書きの要約を返すチャット画面。
2. 受信メールを「請求」「障害」「その他」に分類し、分類ごとに決まったテンプレートで返信を下書き保存するパイプライン。
3. 「この障害の原因を特定して修正して」と頼まれると、ログを検索し、仮説を立て、コードを変更し、テストが通るまで繰り返すシステム。
4. 画像生成モデルに、プロンプトから商品写真を作らせる社内ツール。

自分の答えを、同じ記述を別の言葉で言い換えた場合でも保てるか確かめます。たとえば 2 は、LLM が分類を行っていても、手順がコードで固定されていれば Level 2 です。

### 手順 2: 7段階を対応表で確かめる

- 実行モード: 不要（コードを実行しない）
- 外部サービス: なし

「7段階とモジュールの対応表」を見ながら、手順 1 の記述 3 が、7段階のそれぞれでどんな操作にあたるかを書き出します（例: 知覚 = ログの検索、実行 = コードの変更、学習・適応 = テストの失敗を見て仮説を直す）。そのうえで、各段を、表のどのモジュールで作るかを言い当てます。

### 手順 3: ツール呼び出しのループを、1回の生成と並べて観察する

- 実行モード: `mock`（既定のテスト実行。ネットワークは使いません）
- 外部サービス: なし

1-2 で扱う停止条件つきのエージェントのテストを実行し、「1回で終わる応答」と「ツールを呼びながら繰り返すループ」の違いを、テストの期待値で見ます。リポジトリのルートで次を実行します。

```bash
cd packages/ai-core
AI_TEST_RUN_MODE=mock AI_TEST_SUITE=gate pnpm exec vitest run src/agents/guarded-agent.test.ts \
  -t "run summary" --coverage.enabled=false
```

`src/agents/guarded-agent.test.ts` の次の2つのテストを読み比べます。

- `answers from knowledge without tools and leaves toolsCalled empty`: ツールを使わず `steps: 1` で完了します。Level 1 に近い1回の応答です。
- `repeats tool calls until the model answers and sums the run`: 計算ツールを2回呼び、`steps: 3` で完了します。モデルの出力（ツール呼び出し）が実行され、その結果が次の推論に戻ります。閉ループの最小形です。

あわせて `stops at the step limit and reports step-limit` を読みます。ループは、止まる理由を持たなければなりません。ステップ数、累積トークン、実行時間の3種の停止条件（constitution の原則）は、この「状態を変え続ける」システムの安全のために M1 から入っています。

## Python / Streamlit 経験者向けコラム

1-0 では、Streamlit で作った「プロンプトを入れると答えが返るチャットアプリ」と、「ループを回して状態を変えるシステム」を対比します。Streamlit の仕組みそのものの対比は、1-1 で詳しく扱います。

**Streamlit のチャットアプリは、Level 1 の典型です。** `st.chat_input` に入力すると、スクリプトが先頭から全行再実行され、`llm.invoke(prompt)` の結果を `st.write` で描画して終わります。会話の履歴は `st.session_state` に積みますが、それは**画面に表示するための記録**であり、システムが環境を変えた記録ではありません。次の動作は、ユーザーが再びボタンを押すか、文字を入力したときに始まります。

```python
# Streamlit: 1回の入力に対して1回の生成。制御は「再実行」で人間が駆動する
prompt = st.chat_input("質問を入力")
if prompt:
    answer = llm.invoke(prompt)          # 1ステップで完了
    st.session_state.messages.append((prompt, answer))
    st.write(answer)
```

| 観点 | Streamlit のチャットアプリ | 状態を変えるエージェント |
|---|---|---|
| 次の動作を駆動するもの | ユーザーの操作（ボタン、入力）。操作のたびにスクリプトが全行再実行される | システム自身のループ。モデルの出力（ツール呼び出し）が実行され、その結果が次の推論に入る |
| 1回の入力が引き起こす処理 | モデル呼び出し1回（Level 1） | モデル呼び出し + ツール実行の繰り返し。回数は実行時に決まる |
| 状態の持ち方 | `st.session_state`（表示用の履歴） | 会話履歴に加えて、ツールが変更する外部の状態（DB、チケット、ファイル） |
| 止まり方 | 応答を描画したら、再実行が終わって止まる | 停止条件（ステップ数・トークン・時間）か、モデルの完了で止まる。止まった理由を返す |
| 失敗の影響 | 画面に不適切な文章が出る | 環境に不適切な操作が実行される |

TypeScript 側では、「全行再実行」の代わりに、イベントハンドラとストリームが入ります。`useChat` の `sendMessage` が Route Handler を呼び、サーバー側でモデルの出力がストリームで返ります。エージェントの場合、そのストリームの中でツール呼び出しと結果が繰り返し流れてきます（1-2）。全体を再実行するモデルから、差分を流すモデルへの変化は 1-1 で扱います。

Streamlit のスクリプトの再実行は、実質的には「人間が1周ずつループを回している」とも読めます。Agentic AI は、その1周をシステムが自分で繰り返し、止まる条件も自分で（あらかじめ与えられた上限の範囲内で）判定するものです。
