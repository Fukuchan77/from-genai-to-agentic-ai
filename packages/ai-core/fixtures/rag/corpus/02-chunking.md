# チャンク分割

チャンク分割は、文書を検索の単位に切り分ける作業である。検索で取り出されるのはチャンク単位なので、分割の方法が検索の精度と回答の根拠の読みやすさを左右する。

## 見出し境界での分割

Markdown の文書は、見出し（`#` から `######`）で意味のまとまりに分かれている。このリポジトリのチャンク分割は、まず見出しの境界でセクションに分け、一つのチャンクが複数の見出しにまたがらないようにする。見出しをまたぐと、別の話題が一つのチャンクに混ざり、埋め込みが曖昧になるためである。

各チャンクは見出しの階層（たとえば「チャンク分割 > 見出し境界での分割」）を持つ。引用を表示するとき、この階層を出典の場所として示せる。PDF の場合は見出しがないので、ページ番号を出典の場所にする。

## チャンクサイズの考え方

チャンクが大きすぎると、一つのチャンクに複数の話題が混ざって埋め込みの意味が薄まり、検索で上位に来にくくなる。モデルへ渡す文脈の量も増えるため、回答の費用と時間が増える。一方で小さすぎると、文の前後関係が失われて、単独では意味が通らないチャンクになる。

このリポジトリでは、一つのチャンクの上限を 800 文字（コードポイント数）にしている。日本語は一文字がおよそ一トークン前後になることがあり、埋め込みモデルの入力上限に対して余裕を持たせた値である。上限を超えるセクションは、まず段落の境界で分け、それでも収まらない段落は文の境界で分ける。文の境界でも収まらない場合に限り、上限の文字数で機械的に切る。

分割するときは、元の文章の空白や改行をそのまま保つ。チャンクの本文が元の文書の連続した部分文字列であれば、引用の抜粋を表示するときに利用者が元の文書の該当箇所を探しやすい。

段落や文の単位でまとめるときは、隣り合う単位を上限に達するまで順に詰めていく。こうすると、短い段落が一つずつ独立したチャンクになって細切れになることを避けられる。逆に、一つの段落が上限を超えるときは、その段落だけを文の境界で分け、前後の段落とは混ぜない。

チャンク同士を一部重ねるオーバーラップという工夫もある。隣り合うチャンクの境目で文が途切れても、重なった部分に前後の文脈が残るので、境目にまたがる情報を取りこぼしにくい。ただし、重なった分だけチャンクの数と保存量が増え、同じ内容が検索結果に二回現れやすくなる。このリポジトリでは、見出しの境界を意味の切れ目として尊重するため、オーバーラップは使わない。

最適なチャンクサイズは、文書の種類と質問の傾向で変わる。仕様書のように見出しごとに話題が閉じた文書は、見出しの単位で十分に検索できる。講演の書き起こしのように話題が連続した文書は、小さめに切って重ねたほうが良いことがある。決め打ちせず、正解のわかっている質問の集まりで recall を測り、サイズを変えながら比べるのが確実である。

## チャンク ID

チャンクの ID は、文書 ID、見出しの階層、本文の内容から計算したハッシュ値である。同じ文書を同じ内容で取り込み直すと同じ ID になり、本文が一文字でも変わると別の ID になる。連番ではなく内容のハッシュを使う理由は、分割の規則を変えたときや文書の途中に文章を足したときに、無関係なチャンクの ID まで変わってしまうのを避けるためである。

同じ文書の中に同じ見出しと同じ本文のチャンクが二つあると、ハッシュが衝突する。この場合は、出現順に `-2`、`-3` の接尾辞を付けて区別する。
