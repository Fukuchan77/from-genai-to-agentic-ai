## 0. 総評

要件の粒度・EARS の書き方・「API キーなしで gate が通る」という軸の置き方は良く、ドラフトの内容を要件へ落とす作業としては完成度が高い。一方で、**承認前に直すべき問題が 3 系統**ある。

1. **要件同士の矛盾**: 「LLM 生成コードをホストで実行しない」NFR と長時間実行ハーネス（Req 13）、「全ハンズオンを mock で完走」（17.5）と E2B 必須のデータ分析（Req 10）、「オフラインで gate が通る」と pgvector 前提の RAG（Req 5/6）。
2. **LLM の出力に頼っているのに、決定論的な強制手段が書かれていない AC**: 15.8（外部コンテンツ起因の判定）、11.5（存在しない論文を引用しない）、9.8（認証情報を含めない）、13.3/13.6（`passes` の改ざん防止）など。書き方を変えないと、テストで検証できない。
3. **兄弟リポジトリで既に判明している落とし穴が入っていない**: AI SDK v7 の承認 HMAC、MCP ツールの破壊性注釈、ループのトークン予算と停止理由、compaction で tool-call ペアを分断しない不変条件、ネットワーク遮断テスト、空振り検知（anti-false-green）。

加えて、**14 モジュール・148 AC を単一の承認ゲートで扱う**構成が重すぎる（§1 C-1）。

重大度は次の 3 段階。

| 記号 | 意味 |
|---|---|
| **C** | Critical — 承認前に修正が必要（矛盾、検証不能、セキュリティ上の穴） |
| **H** | High — 設計フェーズに入る前に解決しておきたい |
| **M** | Medium/Low — 表現、補足、将来の手戻り防止 |

## 1. Critical

### C-1 単一 spec・単一承認に 4 マイルストーンを載せている

- 現状: M1〜M4 の全要件（Req 1〜17、148 AC）が 1 つの `spec.json` の `approvals.requirements` にぶら下がっている。M2〜M4 の要件は M1 の結果（Node 26 / TS 7.1 の互換性、mock 戦略が通用するか）に強く依存するので、今の時点で承認すると、M1 実装後に要件の事後改訂が避けられない。
- 参考: `vaz-agentic-ai-next` の constitution §10 は「フェーズの順序入れ替え・受け入れ基準の事後緩和」を禁止し、フェーズごとに人間承認と敵対的レビューを求めている。同 repo の spec も 001〜007 と小さく分かれている。
- **提案**: 本 spec を「プラットフォーム基盤 + M1」（Req 1〜4、横断 NFR、Req 17 の枠組み）に絞り、Req 5〜16 は `002-rag-and-workflows` / `003-domain-agents` / `004-harness-evals-safety` のような後続 spec へ移す。本 spec 側には Module → Requirement Mapping の表だけを残し、後続 spec へのリンクにする。
  分割しない場合でも、`spec.json` の承認をマイルストーン単位に分ける（例: `approvals.requirements.m1`）。

### C-2 「LLM 生成コードをホストで実行しない」と Req 13 が矛盾する

- NFR「隔離実行」（L379）は「LLM が生成したコードをホスト環境で実行しない」とし、Req 10.2 を横断適用している。
- 一方 Req 13 では、Initializer が**検証用テストスクリプト**を生成し（13.1）、Worker が**コードを実装**し、それをテストで検証する（13.3/13.4）。どちらも LLM 生成物の実行であり、13.9 は書き込み先を制限しているだけで、実行の隔離はしていない。ドラフトの `init.sh` も同様。
- **提案**: 次のどちらかを要件として明記する。
  - (a) ハーネスの作業ディレクトリをコンテナ（または Req 10 と同じサンドボックス）内に置き、テスト実行もその中で行う。
  - (b) NFR「隔離実行」に Req 13 の例外を明記し、その代わりに「学習者の明示的な確認後に実行」「ネットワーク遮断」「作業ディレクトリ外への書き込み禁止」を AC にする。
  - 教材として一貫させるなら (a) を推奨する。Anthropic のハーネス記事も、実行環境の隔離を前提にしている。

### C-3 「全ハンズオンを mock で完走」（17.5）が一部のモジュールで成立しない

| モジュール | 衝突している要件 |
|---|---|
| 3-3 データ分析 | 10.8: E2B キーがなければ「無効として表示」。mock 用の代替サンドボックスは Out of Scope（L394）で「設計フェーズで決定」とされている |
| 2-2 Advanced RAG | 6.9: 手法ごとの精度比較。mock の埋め込みでは比較結果に意味がない |
| 4-3 Evals | 14.9: Capability 評価は `local`/`live` 限定 |
| 3-4 リサーチ | 11.3: arXiv API（ネットワーク必須）。NFR「オフライン動作」（L374）と衝突する |

- **提案**:
  1. 17.5 を「各モジュールの**中核ハンズオン**は `mock` で完走できる。比較・品質評価の手順は `local`/`live` 限定と明示する」に弱める。
  2. E2B 未設定時の扱いは要件レベルで決める（設計に送らない）。最低限「mock モードではスクリプト化された疑似サンドボックス（コード受領 → 定義済みの stdout/stderr/画像を返す）で Req 10.3〜10.6 のループを検証できる」とする。
  3. arXiv と Web 取得（4.1）は mock モードでは fixture を返すことを明記する。

### C-4 gate が Docker（Postgres + pgvector）を要るのかが決まっていない

- 1.5 は「API キーなしで gate が成功」、NFR は「オフライン・5 分以内・10 回連続で同じ結果」を求めている。一方、Req 5/6/9/14.4 のテスト対象（チャンク保存、tsvector + pgvector の RRF、チケット状態）は DB を前提にしている。
- 「gate に Docker 起動が要るのか」は学習者の体験と CI の構成を左右するので、要件レベルで決めておく必要がある。
- **提案**: 「`mise run gate` は Docker なしで完走する」を AC に追加し、DB 依存のテストはインプロセス DB（例: PGlite + pgvector 拡張）か、別タスク（`gate:db`）に分ける。どちらにするかは設計で決めればよいが、「Docker 必須かどうか」は要件として固定する。

### C-5 HITL（Req 15）が AI SDK v7 の実際の攻撃面を押さえていない

`vaz-agentic-ai-next` が実装で見つけた穴を、要件レベルで塞いでおくべき。

1. **承認の偽造**: AI SDK v7 のステートレスなチャット経路では、`experimental_toolApprovalSecret` を設定しないと、`tool-approval-request` の HMAC 束縛が行われない。その結果、クライアントが送った `approval.id` から承認が再合成され、承認ゲートが形だけのものになる（`vaz-agentic-ai-next/packages/agents/src/chat-agent.ts` のコメントと `CLAUDE.md` の「TOOL_APPROVAL_SECRET」節）。
   → 15.3 に「承認は**サーバー側で発行した**ツール呼び出し ID と引数に束縛され、1 回だけ消費できる（再送・再利用不可）」を追加する。
2. **履歴注入**: 承認・再開リクエストにクライアントが会話履歴や `model` を混ぜられると、ゲートを迂回できる（vaz constitution §7 D1、X-9）。
   → 「承認・再開リクエストは未知フィールドを拒否する strict スキーマで検証する」を追加する。
3. **15.8 は検証できない**: 「外部から取得したコンテンツ**に起因して**」を、プラットフォームは判定できない。vaz は、RAG 結果などの外部コンテンツがコンテキストに入った時点でフラグ（`externallyDriven`）を立て、run の終わりまで下ろさない方式（sticky taint）をとっている。
   → 「WHILE 実行中に外部コンテンツがコンテキストへ取り込まれた状態、THE プラットフォーム SHALL 書き込み区分以上のツールを承認ゲート経由にする（取り込み以降、run の終了まで解除しない）」のような、状態ベースの書き方に直す。
4. **MCP ツールの区分がない**: 15.1 は「すべてのツールにリスク区分」とするが、Req 8.8/8.9 で動的に登録される MCP ツール（GitHub MCP には issue/PR 作成などの外部送信がある）の区分方法がない。
   → 「MCP ツールの区分は `readOnlyHint`/`destructiveHint` 注釈から決定論的に写像し、注釈がないツールは破壊的アクションとして扱う」を追加する（vaz ADR-0001「Design Principles Fixed In Advance」§2）。
5. **ハンズオンの対象がない**: リファレンス実装のどのツールが「破壊的アクション」なのかが、要件のどこにも書かれていない。15.2〜15.5 を実際に動かす対象として、少なくとも 1 つ具体的に指定する（例: ファイル削除、GitHub issue 作成、ヘルプデスクの回答メール送信）。
6. 15.5（中断時は実行しない）と Out of Scope「セッションをまたいだ永続化」（L389）を合わせると、**承認待ちはプロセス再起動で失効する**ことになる。これを明記し、Req 17.3 の対照表で「LangGraph の checkpointer / `interrupt` に相当する耐久中断は扱わない」と書く（vaz ADR-0005 は、この目的のために Inngest を採用している）。

### C-6 「〜しない」系の AC に強制手段がない

LLM の出力に依存する禁止要件は、**決定論的な後段検証**を AC に書かないと、テストが「モックがそう言ったから通る」だけの空振りになる（X-3）。

| AC | 今の書き方 | 提案 |
|---|---|---|
| 9.8 | 最終回答に認証情報を含めない | 保存前にパターン検査（パスワード・トークン形状）を行い、検出したら保存せずにエラーまたはマスクする |
| 11.5 | 検索結果に存在しない論文を引用しない | レポート出力前に、本文の arXiv ID を取得済み ID 集合と照合し、未取得の ID を含む場合は除去して警告を付ける |
| 5.5 | 引用を回答本文と対応付ける | 引用 ID は取得済みチャンク ID の部分集合であることを検証する |
| 13.3/13.4/13.6 | `passes` の更新はテスト成功時のみ、Worker は `passes` 以外を変更不可 | Worker にはファイル書き込みツールでの `feature_list.json` 変更を許可しない。更新は専用ツール（例: `mark_feature_passing(id)`）経由に限り、そのツールが**ハーネス側でテストを実行**して、成功時だけ書き込む（vaz review HE-4/HE-6） |
| 15.7 | 外部コンテンツをデータとして区別する | 区切り（delimiter）付きのコンテキストブロックで包み、システム指示と同じロールに入れない |

### C-7 mock モードの「決定性」が空振りする

- 2.4 は「事前定義された応答を同一入力に同一内容で返す」、14.8 は「Regression 評価を mock で決定論的に実行し gate に含める」としている。しかし、応答を事前にスクリプト化したモックに対する回帰評価は、**エージェントのロジックが壊れても通る**ことがある。
- **提案**:
  - 2.4 に応答の供給方式を要件として書く。候補は、(a) シナリオ単位のスクリプト（`next-agentic-stack/tests/helpers/mockModel.ts` の方式）、(b) `local`/`live` の実応答を録画したカセットの再生。BeeAI の `FileCache` / `NullCache` も同じ発想。
  - 「gate に含める回帰評価は、エージェントの制御ロジック（ツール選択、停止、検証）を壊したときに落ちることを確認済みであること」を AC にする（vaz constitution §3「非空虚」）。
  - 2.5 の「テストランナーから実行されている状態」を判定するより、**構造的なネットワーク遮断**（モックしていないネットワークアクセスはテストを即失敗させる）を AC にするほうが確実。参考: `vaz-agentic-ai-next/tests/setup/hermetic-network.ts`、X-2。
  - mock モードの埋め込み（Req 5）は、決定論的なダミーベクトル（例: ハッシュ由来）であることと、「検索精度の検証には使えない」ことを明記する。

### C-8 ループの上限が「ステップ数」しかなく、停止理由の語彙もない

- ループの上限が書かれているのは、個別要件の回数上限だけ（7.8、9.4、10.3、11.7/11.8）。**トークン予算・実行時間の上限・停止理由**が横断要件として存在しない。ドラフト「Agentic AI Development Guide」のブラスト半径の節は「最大ループ回数・タイムアウト・最大トークン消費量をハードコード」と明言している。
- vaz review LE-1（停止条件は多重に）/ LE-2（停止理由を閉じた語彙で監査可能に）、vaz ADR-0004（`natural | step-cap | budget-exceeded | error`）。
- **提案**: 横断要件を 1 つ追加する（例: Req 18「ループ制御」）。
  - すべてのエージェントループは、ステップ上限・累積トークン予算・実行時間上限を持つ（既定値は設定で指定）。
  - 実行結果には、閉じた語彙の停止理由を含める。
  - 学習者の停止操作（3.5）は `AbortSignal` として LLM 呼び出し、ツール実行、サンドボックスまで伝播させる。
  - ツールの実行タイムアウト超過は、回復可能なツールエラーとしてモデルに返す（BeeAI `ToolRunOptions.timeout` の方式）。

## 2. High

### H-1 AI SDK の API 名が要件の前提に焼き込まれている

- Project Description の Phase 1（L13）が「generateText / streamText / **generateObject / streamObject**」を 4 大プリミティブとしている。AI SDK 6 以降、構造化出力は `generateText` / `streamText` の `output: Output.object({ schema })` に統合され、`generateObject`/`streamObject` は非推奨になった（`vaz-agentic-ai-next/packages/evals/src/judge.ts` は `Output.object` を使っている）。v7 ではほかにも次の変更がある（`next-agentic-stack/AGENTS.md`）。
  - `system` → `instructions`
  - `stepCountIs` → `isStepCount`
  - `ToolLoopAgent` の追加
  - ツール単位の `needsApproval` から、呼び出し単位の `toolApproval` への移行
- L43 は「ドラフトとの差分はモジュール解説に明記」としているが、spec 本文がドラフトの API 名を前提にしている。
- **提案**: 学習目標を「テキスト生成／ストリーミング × 非構造／構造化の 2 軸」のように API 名に依存しない表現にする。あわせて、エージェントループを「素の TypeScript ループ」で教えるのか、`ToolLoopAgent` で教えるのか（または両方を順に教えるのか）を Clarification で決める。AGENTS.md は「Control loops are plain TypeScript」としているが、v7 の `ToolLoopAgent` にどう触れるかが書かれていない。

### H-2 バージョン方針に内部矛盾がある

- L42「最新安定版を採用」と「TS 7.1（安定リリース前）を先行採用」が同じ文にある。ドラフトの Vitest 5.0 も含め、何を先行版として許容するのかの一覧がない。
- 実例:
  - `next-agentic-stack` は TS `7.1.0-dev.20260923.1` / Next `16.4.0-canary.40` / Playwright alpha を**完全一致で固定**し、`minimumReleaseAge` と `scripts/check-updates.mjs` で運用している。
  - `vaz-agentic-ai-next` は **Vitest 4・TS 6 に意図的に留めている**（Vitest 5 はテスト間でモックの状態をリセットし、`auth.spec.ts` が壊れる。TS 7 はネイティブ移植で JS コンパイラ API がない）。
- **提案**: Technical Constraints に次を明記する。
  - 先行版を許容するパッケージのリスト。
  - 先行版は**完全一致で固定**すること。
  - 非互換が出た場合の後退先（例: TS 6.x stable）。
  - TS 7 には JS コンパイラ API がないので、それに依存するツールは採用しない。
  - L44 が「設計フェーズで定める」としている後退方針は、M1 の受け入れ条件に直結するので要件側で決める。

### H-3 プロバイダ 5 種の実現性リスク

- IBM watsonx.ai の AI SDK プロバイダは、IBM がメンテナンスしている**コミュニティプロバイダ** [`watsonx-ai-provider`](https://github.com/IBM/watsonx-ai-provider) で、README 上は 2.x が **AI SDK v6** 対象。v7 対応は未確認。
- Google は Gemini API（`@ai-sdk/google`）と Vertex（`@ai-sdk/google-vertex`）のどちらなのかが書かれていない。
- **提案**: 2.2 に「プロバイダごとに、AI SDK 7 対応の実装が存在することを M1 の設計時に実測で確認し、存在しない場合はそのプロバイダを後続マイルストーンへ送る」を追加する（vaz constitution §8「事実は実測で確定する」）。
- 参考: BeeAI は watsonx / Azure OpenAI / Gemini / Vertex / Anthropic / Ollama を TS/Python 両方でネイティブ提供している（`modules/backend.mdx`）。watsonx が AI SDK 7 で使えない場合の比較対象になる。

### H-4 モデルのメタデータ（カタログ）要件が抜けている

次の要件は、いずれもモデルごとのメタデータを前提にしているが、その「持ち方」を定める要件がない。

| 要件 | 必要なメタデータ |
|---|---|
| 2.9 | 機能対応（ツール、構造化出力、推論、埋め込み） |
| 4.6 / 12.1 | コンテキスト上限 |
| 4.8 | プロンプトキャッシュ対応 |
| NFR コスト可視化 | 単価 |

- **提案**: 「モデル ID・機能・コンテキスト上限・単価を 1 か所のカタログで管理し、それ以外の場所にモデル ID を書かない。この制約は機械的なゲートで検証する」を 2.8 に追加する。
  - 参考: vaz の `MODEL_ALLOWLIST` は `satisfies Record<AiProvider, …>` で、プロバイダの追加漏れを型エラーにしている。さらに `lint:model-ids` の grep ゲートで、カタログ以外へのモデル ID の直書きを検出している。

### H-5 会話途中のモデル切り替え（3.3）でプロバイダ固有のパーツが壊れる

- 推論パーツ（Anthropic の thinking には署名が付く）やプロバイダ固有のメタデータは、別プロバイダへそのまま送れない。
- **提案**: 3.3 に「切り替え先のプロバイダが受け付けない履歴パーツ（推論内容など）は、送信時に除外または変換し、UI 上の表示は保持する」を追加する。

### H-6 Req 8（ACI / MCP）の不足

1. **パス検査**: ドラフトのパターン B は `normalized.startsWith(BASE_PROJECT_DIR)` で判定しているが、これは `/workspace/projects-evil/…` を通してしまう。シンボリックリンクも解決していない。8.5 に「シンボリックリンク解決後の実パスが、許可ルートの**配下**にあること（パス区切りを考慮した包含判定）」を明記する。
2. **ツール数の上限**: GitHub MCP サーバーは多数のツールを公開する。8.8 の「一覧を取得し、そのまま登録」は、ツール選択の精度を落とす（MCP-2）。「エージェントごとの許可リストで登録ツールを絞る」と「1 エージェントあたりのツール数の上限」（vaz constitution §6 は 20）を追加する。
3. **ACI 原則のうち、AC になっていないもの**（ドラフト Guide モジュール 3、X-6）:
   - description に「いつ使うか」を書く
   - 低レベル CRUD をそのままラップしない
   - セマンティックな識別子
   - ページング（`next_offset`）
   - 思考の余地（BeeAI の `ThinkTool` に相当）
4. MCP のトランスポート（stdio / Streamable HTTP）と、クライアント実装（AI SDK 7 の `@ai-sdk/mcp` `createMCPClient()`）が書かれていない。8.7 を自作するのか、公式の filesystem サーバーを使うのかも決めておく（教材としては自作に意味がある）。
5. 8.2/8.3 のエラー分類: 「回復可能（モデルに返す）／致命的（run を止める）」の区別を要件にする。BeeAI の `FrameworkError` は `is_retryable` / `is_fatal` と `ToolInputValidationError` を持っており、そのまま参考になる。

### H-7 Req 12（コンテキストエンジニアリング）に必須の不変条件がない

- compaction や履歴の切り詰めで**tool-call とその tool-result のペアを分断すると、次のターンでプロバイダがエラーを返す**（X-7、`fastapi-pydantic-ai-agent/_trim.py` の不変条件）。
- 12.2 に次の 2 点を追加する。
  - 「tool-call／tool-result のペアを分断しない」
  - 「システムプロンプトは要約対象にしない」
- 12.1 の「コンテキスト上限の 70%」は H-4 のカタログを参照すると明記する。
- ドラフトの主要トピック「システムプロンプトの適正高度（Goldilocks Zone）」は AC がない。解説（Req 17）だけで扱うなら、そう明記する。
- 参考: BeeAI の `SlidingMemory` / `TokenMemory` / `SummarizeMemory` は、12.1 の段階的な選択肢（窓化 → トークン上限 → 要約）にそのまま対応するので、解説の比較表に使える。

### H-8 Req 14（Evals）の不足

| 追加・修正 | 根拠 |
|---|---|
| LLM-as-a-Judge は評価軸ごとにプロンプトを分け、「判定不能（unknown）」を返せるようにする（14.5） | ドラフト Guide モジュール 5、X-8（`eval_graders.py` の `Rating = "1".."5" \| "unknown"`） |

### H-9 ヘルプデスク（Req 9）の計画に関するエッジケースがない

- 9.1: 生成された計画が不正な場合（循環依存、存在しないタスクへの依存）の扱いがない。「検証に失敗した計画は実行せず再生成する」を追加する。
- 9.3「計画の前提と矛盾した時」はトリガーとして検証できない。「各タスクの完了後、Replanner が `continue | replan | finish` を構造化出力で返し、`replan` のときに…」のように、観測できる判定へ書き換える。
- 参考: BeeAI の `RequirementAgent`（`ConditionalRequirement` の `force_at_step` / `only_after` / `min_invocations` / `max_invocations` / `prevent_stop`）は、ツールの呼び出し順序を宣言的な規則で強制する別のアプローチ。Plan-and-Execute との対比教材として 3-2 か 3-4 の解説に入れると、「計画を LLM に任せる／規則でコードが強制する」の境界線が教えやすい（ドラフト Guide の結論「決定論と確率の境界をどこに引くか」に直結する）。

### H-10 マルチエージェント（Req 11）のコスト可視化

- vaz constitution §1 とその根拠の Anthropic 記事 [A9] は、マルチエージェントの採用を「単一エージェント比で約 15 倍のトークンコストに見合うか」で判断させる。教材として最も教えるべき点だが、Req 11 には AC がない。
- **提案**: 「Supervisor と各サブエージェントのトークン使用量の内訳を、実行結果とレポートに表示する」を追加する（X-16 が挙げる `beeai-agentic-ai-sandbox/effective_agents/research_system.py` の `_print_usage()` と同じ目的）。
- 7.11 の統合スコアの算出方法（平均か最小値か）が書かれていない。セキュリティ評価器を含むなら、最小値が妥当。

### H-11 E2E テスト・サプライチェーン・シークレットスキャンが要件にない

UI の AC（3.x、4.5、9.5、10.5、15.2）を検証する E2E テスト、アクセシビリティの検証手段、サプライチェーン対策が要件にない。兄弟 2 repo はすべて実装済みで、X-14 は「E2E が CI にない」ことを、同じ欠陥として 2 repo で指摘している。

- **1.7 に追加**:
  - Playwright E2E を CI で実行する。LLM 呼び出しはネットワーク層でモックする（`next-agentic-stack` の `page.route` 方式）。
  - シークレットスキャン（`gitleaks git --redact`）。
  - `pnpm audit`。
- **NFR に追加**:
  - `minimumReleaseAge`
  - `allowBuilds`
  - GitHub Actions の SHA 固定と `permissions:` の最小化（X-1）
  - Dependabot（X-15）
- **アクセシビリティ（L380）の検証手段**: axe-core の Playwright 連携（vaz の `@axe-core/playwright`）。
- **対応ブラウザ（L381）**: Safari を含めるなら、CI で WebKit を回すかどうかも決める（`next-agentic-stack` は Chromium と Firefox のみ）。

### H-12 トレース基盤（1.8 / 16.3）の重さ

- Langfuse の現行セルフホスト構成は、Postgres・ClickHouse・Redis・オブジェクトストレージを要する。「学習者 1 人がローカルで」という前提に対しては重い。
- **提案**: 16.x を「OTLP でエクスポートし、ローカルのトレース UI で 1 run を 1 トレースとして閲覧できる」とバックエンド非依存に書く。Langfuse は選択肢の 1 つ（ほかに Arize Phoenix、Jaeger など。BeeAI は Phoenix/Langfuse/LangSmith に対応）にし、必要リソースを解説に書く。
- 16.4 は認証情報だけを除外対象にしている。**プロンプトやツール引数の本文をスパンに記録するかどうか**（AI SDK の `recordInputs`/`recordOutputs`）を明示する。ローカル学習用途なら記録してよいが、既定値と切り替え手段を要件として持たせる（vaz の privacy contract R4.7 との違いを解説に書く価値がある）。

## 6. 推奨アクション（順序）

1. **spec の分割方針を決める**（C-1）。分割するなら、本 spec は Req 1〜4 + 横断 NFR + Req 17 の枠組みに絞る。

5. **ドラフトからの除外表を Out of Scope に追加する**（§4、M-1）。
6. 以上を反映したうえで要件を承認し、M1 の design へ進む。
