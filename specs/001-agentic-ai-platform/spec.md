# agentic-ai-platform — Requirements

## Overview

LLM アプリ開発を Python / LangChain で学んだ（あるいは学ぼうとしている）エンジニアが、TypeScript / Web 標準スタックで本番品質の Agentic AI システムを一人で設計・構築・評価できるようになることを目的とする。本 spec は、マスターカリキュラム全4フェーズ・14モジュールに、他ドラフトから復元した5モジュールを加えた計19モジュールのハンズオンを「ローカルで動き、テストで検証できるリファレンス実装」と「モジュール別の日本語解説」として提供するプラットフォーム（以下「プラットフォーム」）の要件を定義する。価値は、(1) 受動的生成 → タスク自動化 → 自律型エージェントへの成熟段階をコードで体験できること、(2) API キーなしでも全テストが決定論的に通ること、(3) 各モジュールの習熟度をチェックリストと自動テストで客観判定できること、の3点にある。

## Project Description

出典: [specs/drafts/Next-Gen AgenticAI App Dev Learning.md](../drafts/Next-Gen%20AgenticAI%20App%20Dev%20Learning.md)（マスターカリキュラム。他ドラフトと矛盾する場合はこちらを正とする）。マスターカリキュラムが統合時に落とした内容は、[`1_llm-agent.md`](../drafts/1_llm-agent.md)、[`2_ai-agent.md`](../drafts/2_ai-agent.md)、[`3_genai-agent.md`](../drafts/3_genai-agent.md)、[`Agentic AI Development Guide.md`](../drafts/Agentic%20AI%20Development%20Guide.md) から復元した（[ドラフトからの復元対応表](#ドラフトからの復元対応表)）。

Python / LangChain / LangGraph ベースの3冊の教材（AIアプリ開発入門、RAG・AIエージェント実践入門、AIエージェント実践入門）と Anthropic / IBM の Agentic AI 知見を、TypeScript / Next.js / Vercel AI SDK / Zod / MCP / E2B / Vitest のスタックへ移植・統合した、4フェーズ構成の学習カリキュラムおよびそのリファレンス実装。

- **Phase 1 基礎編**: 概念体系（生成 AI → AI Agents → Agentic AI）、モノレポ・Biome 基盤、AI SDK v7 Core（`generateText` / `streamText`、`Output.object` による構造化出力、`ToolLoopAgent` によるツール呼び出しループ）、マルチプロバイダ切替ストリーミングチャット（画像入力・ペルソナ切替）、Generative UI、Web 記事・YouTube 字幕の構造化要約、プロンプトキャッシュ
- **Phase 2 発展編**: TypeScript ネイティブ RAG（pgvector + Drizzle、引用付き回答、Agentic RAG）、Advanced RAG（HyDE / Multi-Query / RRF / Rerank、RAG 評価）、Anthropic 5大ワークフローパターン、エージェントデザインパターン（18 パターン体系と主要 6 実装）
- **Phase 3 現場実践編**: ACI 設計と MCP、ヘルプデスク（Plan-and-Execute）、データ分析（E2B サンドボックス + 自己修正）、階層型論文リサーチ（Agent-as-a-Tool）、要件定義書生成（インタビュー型）、マーケティング支援（ロールプレイ合議・会話型レコメンド）
- **Phase 4 運用・品質編**: コンテキストエンジニアリング（Compaction / Note-Taking / 段階的開示 / メモリ分類）、長時間実行2層ハーネス（Initializer → Worker）、Agent Evals（Vitest、LLM-as-a-Judge、合成データ、CI 統合）、安全設計（ブラスト半径、強制停止条件、Human-in-the-Loop、プロンプトインジェクション対策、OpenTelemetry）、総合演習（アーキテクチャ選定）

計画上のリポジトリ構成は pnpm + Turborepo モノレポ（`apps/web`、`packages/ai-core`、`packages/eval-suite`）。各フェーズにはハンズオン課題と習熟度判定チェックリストが定義されている。

## Technical Constraints

- バージョン方針: 各ライブラリは実装時点の最新安定版を採用し、`mise.toml` / `package.json` で固定する。ただし次世代志向として、Node.js v26（LTS 予定）と TypeScript v7.1（安定リリース前）を先行採用する
- TypeScript 7.1 先行版の方針:
  - 全ワークスペース（`apps/*`、`packages/*`、テスト用 tsconfig）で TypeScript 7.1 先行版を使うことを原則とする。
  - 先行版は範囲指定ではなく完全一致のバージョン（例: `7.1.0-dev.YYYYMMDD.N`）で固定し、公開から 24 時間以上経過したビルドだけを採用する（`pnpm-workspace.yaml` の `minimumReleaseAge` と整合させる）。
  - TypeScript 7 はネイティブ実装で JS コンパイラ API を持たないため、コンパイラ API に依存するツールは採用しない。同等機能を持つ代替ツールを優先する。
  - 先行版に起因する非互換で代替もない場合に限り、影響するツールまたはワークスペースだけを TypeScript 6.x 安定版へ後退させる。後退した範囲、理由、解除条件は `package.json` のコメントと解説ドキュメントに記録する。
  - 先行版の最新ビルドと正式版の公開状況を確認する手段（例: `mise run outdated`）を提供する。
- AI SDK 方針:
  - Vercel AI SDK v7 を使う。エージェントループは `ToolLoopAgent`（`instructions`、`tools`、`stopWhen: isStepCount(n)` 等）で実装する。構造化出力は `Output.object`、ツール入力は `inputSchema` で定義する。Human-in-the-Loop は呼び出し単位の `toolApproval` 機構を使う。
  - ワークフローパターン（Req 7）は、`ToolLoopAgent` を使わず素の TypeScript で制御フローを書く（ワークフローとエージェントの峻別を教えるため）。
- API とモデル ID は実装時点の公式ドキュメント（Context7 等）で検証したものを正とする。ドラフトのコード例（例: tool の `parameters`、`maxSteps`、`generateObject` / `streamObject`、`toDataStreamResponse()`、`experimental.reactCompiler`、`claude-3-7-sonnet` / `GPT-4o`）との差分は、モジュール解説に明記する
- Node v26、Next.js 等の先行版に起因するツールチェーン（Biome、Vitest、Next.js 等）の互換性問題の扱いは、設計フェーズで定める（TypeScript については上記の方針に従う）

## Runtime Environment

- 利用者: 学習者1人がローカル環境で実行する
- Postgres + pgvector、Langfuse（トレース）は Docker Compose でローカル起動する
- E2B（サンドボックス）、Cohere Rerank など API キー必須の外部サービスは、キーが設定されている場合のみ有効化し、未設定時はスキップまたは代替実装で動作を継続する

## LLM Provider & Test Strategy

- LLM 実行モードは3層を切替可能にする:
  1. **モック**: AI SDK のテスト用モックモデルによる決定論的実行（API キー不要）
  2. **ローカル LLM**: Ollama
  3. **実 API**: Anthropic / OpenAI / IBM watsonx.ai / Microsoft Azure（Azure OpenAI）/ Google を設定で切替。IBM watsonx.ai は、AI SDK v7 に対応したプロバイダ実装が存在する場合に限り提供し、存在しない場合はスキップする（2026-09 時点の `watsonx-ai-provider` 2.x は AI SDK v6 対象。v7 対応は設計フェーズで実測確認する）
- 前提（要確認）: `mise run gate` と PR CI はモック層で実行し、ローカル/実 API 層を使う capability Evals・LLM-as-a-Judge は別タスクとして実行する
- 未決: 既定の実 API プロバイダ、Evals の実行頻度と予算上限（設計フェーズで決定）

## Glossary

| Term | Definition |
|------|------------|
| プラットフォーム | 本 spec が定義するリファレンス実装一式（Web アプリ、エージェント基盤ライブラリ、評価スイート、解説ドキュメント）。EARS の主語として用いる |
| 学習者 | プラットフォームをローカルで動かしてカリキュラムを進める唯一の利用者 |
| モジュール | カリキュラムの学習単位（1-0〜4-5 の19個）。各モジュールはハンズオン（1-0 は観察・確認課題）と解説を1つずつ持つ |
| 実行モード | LLM 呼び出し先の切替層。`mock`（決定論的モック）/ `local`（Ollama）/ `live`（商用 API）の3種 |
| プロバイダ | `live` モードで選択できる商用 LLM API: Anthropic / OpenAI / IBM watsonx.ai / Azure OpenAI / Google |
| 品質ゲート | `mise run gate`。lint・format・typecheck・test を1コマンドで実行する検証手段 |
| ACI | Agent-Computer Interface。エージェントが呼び出すツールの定義とその入出力設計 |
| MCP | Model Context Protocol。ツール・リソースを外部プロセスとやり取りする標準プロトコル |
| 引用（Citation） | RAG 回答が根拠としたナレッジベース上のチャンクの識別子と出典情報 |
| RRF | Reciprocal Rank Fusion。複数の検索結果ランキングを順位ベースで統合する手法 |
| トランスクリプト | エージェント1回の実行で発生したメッセージ・ツール呼び出し・結果の完全な記録 |
| Outcome | エージェント実行後の外部環境の最終状態（DB レコード、生成ファイル等）。Evals の主な判定対象 |
| Compaction | 会話履歴を要約・再構築して、コンテキストのトークン量を削減する処理 |
| 破壊的アクション | 削除・外部送信・決済など、実行後に元へ戻せない副作用を伴うツール呼び出し |
| 機能リスト | 長時間実行ハーネスで Initializer が生成する、機能ごとの `passes` 真偽値を持つ進捗ファイル |
| ToolLoopAgent | AI SDK v7 のエージェント実装。モデル呼び出しとツール実行を、停止条件（`stopWhen`）を満たすまで反復する。本 spec の「エージェント」は原則これで実装する |
| ワークフロー | コードが制御フローを決める LLM 処理の合成（Req 7）。LLM が制御フローを決める「エージェント」と区別する |
| 停止理由 | エージェントループが停止した理由を表す、閉じた語彙の値（Req 19） |
| Generative UI | ツール呼び出しや構造化出力の結果を、テキストではなく型付きの UI コンポーネント（カード、チャート、フォーム等）として描画する方式 |
| ペルソナ | エージェントや LLM 呼び出しに与える役割・視点の定義。システムプロンプトのテンプレートとして管理する |

## Requirements

### Requirement 1: モノレポ基盤と品質ゲート

学習者として、1コマンドでセットアップと品質検証ができるモノレポが欲しい。これにより全モジュールを同じ規約・同じ検証手段で進められる。（モジュール 1-1）

**Acceptance Criteria**

1.1 THE プラットフォーム SHALL Web アプリ、エージェント基盤ライブラリ、評価スイートを単一リポジトリ内の独立したワークスペースパッケージとして提供する。
1.2 THE プラットフォーム SHALL エージェント基盤ライブラリを UI フレームワークに依存せず、Web アプリ以外（テスト、CLI スクリプト）からも import 可能な形で提供する。
1.3 WHEN 学習者がクリーンな clone に対して依存インストールを実行した時、THE プラットフォーム SHALL `mise.toml` に固定されたランタイム・パッケージマネージャのバージョンで全ワークスペースの依存を解決する。
1.4 WHEN 学習者が `mise run gate` を実行した時、THE プラットフォーム SHALL lint、format チェック、typecheck、テストを全ワークスペースに対して実行し、いずれかが失敗した場合は非ゼロの終了コードを返す。
1.5 WHILE 環境変数に LLM・外部サービスの API キーが一切設定されていない状態、THE プラットフォーム SHALL `mise run gate` を成功させる。
1.6 THE プラットフォーム SHALL lint / format 規約として、2スペースインデント、行幅100、シングルクォート、セミコロン必須、未使用変数・未使用 import をエラーとするルールを適用する。
1.7 WHEN プルリクエストが作成または更新された時、THE プラットフォーム SHALL CI 上で品質ゲートと同等の検証を実行し、結果をプルリクエストのステータスとして報告する。
1.8 WHEN 学習者がローカル依存サービスの起動コマンドを実行した時、THE プラットフォーム SHALL Postgres（pgvector 有効）とトレース収集基盤をコンテナとして起動する。
1.9 IF 必須の環境変数が不足した状態で Web アプリまたはエージェントを起動した場合、THEN THE プラットフォーム SHALL 不足している変数名と、それを必要とする機能名を示すエラーメッセージを出力する。
1.10 THE プラットフォーム SHALL API キー等の秘密情報をサーバー側でのみ参照し、ブラウザへ配信されるバンドルに含めない。

### Requirement 2: LLM プロバイダと実行モード

学習者として、同じコードのまま LLM の呼び出し先をモック・ローカル・商用 API の間で切り替えたい。これによりコストをかけずに開発・テストし、必要な時だけ実モデルで確認できる。

**Acceptance Criteria**

2.1 THE プラットフォーム SHALL 実行モードとして `mock`、`local`、`live` の3種を提供し、アプリケーションコードを変更せずに設定だけで切り替えられるようにする。
2.2 WHERE 実行モードが `live` の場合、THE プラットフォーム SHALL プロバイダとして Anthropic、OpenAI、Azure OpenAI、Google を選択可能にし、IBM watsonx.ai は AI SDK v7 に対応したプロバイダ実装が存在する場合に限り選択可能にする。
2.10 IF IBM watsonx.ai 用の AI SDK v7 対応プロバイダ実装が存在しない場合、THEN THE プラットフォーム SHALL watsonx.ai をプロバイダ選択肢と設定項目から除外し、スキップした旨と理由を解説ドキュメントに記載する。
2.3 WHERE 実行モードが `local` の場合、THE プラットフォーム SHALL ローカルで稼働する Ollama サーバー上のモデルへ LLM 呼び出しを送る。
2.4 WHERE 実行モードが `mock` の場合、THE プラットフォーム SHALL ネットワーク通信を行わず、事前定義された応答（テキスト、構造化オブジェクト、ツール呼び出し、ストリームチャンク）を同一入力に対して毎回同一の内容で返す。
2.5 WHILE テストランナーから実行されている状態、THE プラットフォーム SHALL 明示的な上書き設定がない限り実行モードを `mock` とする。
2.6 IF 選択されたプロバイダの認証情報が未設定の場合、THEN THE プラットフォーム SHALL LLM 呼び出しを行わずに、プロバイダ名と必要な環境変数名を含むエラーを返す。
2.7 IF 実行モードが `local` で Ollama サーバーに接続できない場合、THEN THE プラットフォーム SHALL 接続先 URL と起動方法の案内を含むエラーを返す。
2.8 THE プラットフォーム SHALL 用途（チャット、構造化出力、埋め込み、評価器）ごとに使用するモデルを設定で指定できるようにし、モデル ID をアプリケーションコードにハードコードしない。
2.9 IF 選択されたモデルが要求された機能（ツール呼び出し、構造化出力、推論トークン、埋め込み）に対応していない場合、THEN THE プラットフォーム SHALL 呼び出し前に、非対応の機能名とモデル名を含むエラーを返す。

### Requirement 3: ストリーミングチャット

学習者として、ブラウザ上でモデルを切り替えながらリアルタイムにストリーミングされるチャットを試したい。（モジュール 1-2）

**Acceptance Criteria**

3.1 WHEN 学習者がチャット画面でメッセージを送信した時、THE プラットフォーム SHALL 応答テキストを生成完了を待たずにトークン単位で逐次表示する。
3.2 THE プラットフォーム SHALL チャット画面で、実行モードとプロバイダの組み合わせから利用可能なモデルの一覧を表示し、学習者が選択できるようにする。
3.3 WHEN 学習者が会話途中でモデルを切り替えた時、THE プラットフォーム SHALL 既存の会話履歴を保持したまま、次のメッセージから新しいモデルで応答を生成する。
3.4 WHERE 選択されたモデルが推論トークン（思考過程）を出力する場合、THE プラットフォーム SHALL 推論内容を最終回答とは視覚的に区別された折りたたみ可能な領域に表示する。
3.5 WHEN 学習者が生成中に停止操作を行った時、THE プラットフォーム SHALL ストリーミングを中断し、それまでに受信したテキストを会話履歴に保持する。
3.6 IF LLM 呼び出しがエラーで失敗した場合、THEN THE プラットフォーム SHALL チャット画面にエラー内容と再送操作を表示し、送信済みの学習者メッセージを失わない。
3.7 THE プラットフォーム SHALL 各応答について、使用したモデル名と入力・出力トークン数を表示する。
3.8 THE プラットフォーム SHALL LLM 呼び出しをサーバー側で実行し、ブラウザから直接 LLM プロバイダへ通信しない。
3.9 WHERE 選択されたモデルが画像入力に対応している場合、THE プラットフォーム SHALL 学習者がチャットに画像を添付して送信し、画像の内容に基づく応答を得られるようにする。
3.10 THE プラットフォーム SHALL システムプロンプト（ペルソナ）を、バージョン管理されたテンプレートとして複数提供し、学習者がチャット画面で切り替えられるようにする。
3.11 WHILE 実行モードが `live` の状態、THE プラットフォーム SHALL LLM を呼び出す前に、リクエストの件数・長さ・サイズの上限と単位時間あたりの呼び出し回数の上限を検査し、超過したリクエストを LLM 呼び出しなしで拒否する。

### Requirement 4: 構造化出力と要約パイプライン

学習者として、Web 記事や動画字幕から型安全な要約を抽出し、UI にカードとして描画したい。正規表現パースに頼らないスキーマ駆動開発とプロンプトキャッシュを体験する。（モジュール 1-3）

**Acceptance Criteria**

4.1 WHEN 学習者が Web 記事の URL を入力した時、THE プラットフォーム SHALL 本文テキストを取得し、タイトル、3行の要点、重要タグ、アクション項目を持つ要約オブジェクトを生成する。
4.2 WHEN 学習者が動画の字幕テキスト（トランスクリプト）を入力した時、THE プラットフォーム SHALL 4.1 と同じ構造の要約オブジェクトを生成する。
4.3 THE プラットフォーム SHALL 要約オブジェクトをスキーマで検証し、スキーマに適合したオブジェクトのみを UI とライブラリ利用者へ返す。
4.4 IF LLM の出力がスキーマ検証に失敗した場合、THEN THE プラットフォーム SHALL 最大2回まで再生成し、それでも失敗した場合は検証エラーの内容を含むエラーを返す。
4.5 WHILE 要約オブジェクトを生成中の状態、THE プラットフォーム SHALL 確定したフィールドから順にカード UI へ逐次描画する。
4.6 WHEN 入力テキストが選択モデルのコンテキスト上限を超える長さである時、THE プラットフォーム SHALL 入力を分割して段階的に要約し、最終的に 4.1 と同じ構造の要約オブジェクトを1つ返す。入力がコンテキスト上限内に収まる場合は、分割せずに全文を1回の呼び出しで要約する。
4.7 IF 指定 URL の取得に失敗した場合、または本文が空の場合、THEN THE プラットフォーム SHALL LLM を呼び出さずに、失敗理由（HTTP ステータスまたは空本文）を含むエラーを表示する。
4.8 WHERE 選択プロバイダがプロンプトキャッシュに対応している場合、THE プラットフォーム SHALL 同一の長いコンテキストを再送する呼び出しでキャッシュを有効化し、キャッシュ読み出しトークン数を記録・表示する。
4.9 WHEN 学習者が YouTube 動画の URL を入力した時、THE プラットフォーム SHALL 動画の字幕（トランスクリプト）をタイムスタンプ付きで取得し、4.2 の入力として要約する。
4.10 WHEN タイムスタンプ付きの字幕から要約を生成した時、THE プラットフォーム SHALL 要約オブジェクトに、各見出しと開始時刻を持つ目次（チャプター）を含める。
4.11 IF 指定動画の字幕が取得できない場合（字幕なし、非公開、取得エラー）、THEN THE プラットフォーム SHALL LLM を呼び出さずに、取得できなかった理由を含むエラーを表示する。
4.12 THE プラットフォーム SHALL 各要約について、分割せずに全文を投入したか、分割して段階的に要約したかと、その判断に用いた入力トークン数を結果に含める。

### Requirement 5: RAG ナレッジベースと引用付き回答

学習者として、PDF 等の文書からナレッジベースを作り、根拠となる引用付きで回答する RAG を、フレームワークのブラックボックスなしで構築したい。（モジュール 2-1）

**Acceptance Criteria**

5.1 WHEN 学習者が PDF または Markdown 文書を取り込み対象として指定した時、THE プラットフォーム SHALL 文書をチャンクに分割し、各チャンクの埋め込みベクトル、本文、出典メタデータ（文書名、ページまたは見出し）をナレッジベースに保存する。
5.2 THE プラットフォーム SHALL Markdown 文書を見出し境界でチャンク分割し、1つのチャンクが複数の見出しセクションをまたがないようにする。
5.3 WHEN 同一文書が再度取り込まれた時、THE プラットフォーム SHALL 既存のチャンクを置き換え、同一文書のチャンクを重複して保存しない。
5.4 WHEN 学習者が質問を送信した時、THE プラットフォーム SHALL 質問とベクトル類似度の高い上位 k 件（k は設定可能、既定 5）のチャンクを取得し、それらを根拠とした回答をストリーミングで返す。
5.5 THE プラットフォーム SHALL 回答とともに、回答が根拠としたチャンクの引用（文書名、ページまたは見出し、本文抜粋）を返し、UI で回答本文と対応付けて表示する。
5.6 WHERE 検索時にメタデータフィルタ（文書名、タグ等）が指定された場合、THE プラットフォーム SHALL フィルタ条件に一致するチャンクのみを検索対象とする。
5.7 IF 類似度が設定された閾値以上のチャンクが1件も見つからない場合、THEN THE プラットフォーム SHALL 推測で回答を生成せず、ナレッジベースに該当情報がない旨を返す。
5.8 IF 取り込み対象ファイルが非対応形式である、またはテキストを抽出できない場合、THEN THE プラットフォーム SHALL そのファイルをスキップし、ファイル名と理由を取り込み結果に含める。
5.9 WHERE Agentic RAG モードが有効な場合、THE プラットフォーム SHALL ナレッジベース検索をエージェントのツールとして提供し、検索の要否・検索クエリ・検索回数をエージェントに判断させる。
5.10 WHILE Agentic RAG モードで、質問がナレッジベースの内容と無関係な状態、THE プラットフォーム SHALL 検索ツールを呼び出さずに回答できるようにし、各回答で検索ツールを呼び出したかどうかを結果に含める。

### Requirement 6: Advanced RAG

学習者として、曖昧な質問やキーワード不一致に強い高度な検索パイプラインを構築し、ナイーブなベクトル検索との差を比較したい。（モジュール 2-2）

**Acceptance Criteria**

6.1 WHERE HyDE が有効な場合、THE プラットフォーム SHALL 質問から仮想回答を生成し、その仮想回答の埋め込みを用いてベクトル検索を行う。
6.2 WHERE Multi-Query 展開が有効な場合、THE プラットフォーム SHALL 1つの質問から構造化出力として3件のサブクエリを生成し、それらの検索を並列に実行する。
6.3 WHERE ハイブリッド検索が有効な場合、THE プラットフォーム SHALL 全文検索とベクトル検索の結果を RRF で統合した単一のランキングを返す。
6.4 THE プラットフォーム SHALL RRF 統合において、同一チャンクが複数の検索結果に含まれる場合でも統合後ランキングに1回だけ含める。
6.5 WHERE Rerank API のキーが設定されている場合、THE プラットフォーム SHALL 統合後の候補を Rerank で再順位付けし、上位 k 件を回答生成に用いる。
6.6 IF Rerank API のキーが未設定の場合、THEN THE プラットフォーム SHALL Rerank 段をスキップして統合後ランキングの上位 k 件を用い、Rerank がスキップされたことを実行結果に記録する。
6.7 THE プラットフォーム SHALL 各検索手法（ナイーブ、HyDE、Multi-Query、ハイブリッド、Rerank）を個別に有効・無効化できる設定を提供する。
6.8 WHEN 学習者が検索パイプラインを実行した時、THE プラットフォーム SHALL 各段階（サブクエリ、各検索の候補、統合後、Rerank 後）の中間結果を確認できる形で返す。
6.9 THE プラットフォーム SHALL 同一の評価用質問セットに対して、手法の組み合わせごとの検索精度（上位 k 件中の正解チャンク含有率）を比較できる評価を提供する。
6.10 THE プラットフォーム SHALL RAG 回答の品質評価として、忠実性（回答が取得チャンクに裏付けられているか）と回答関連性（回答が質問に答えているか）を、LLM-as-a-Judge で採点する評価を提供する。
6.11 WHILE 検索パイプラインが実行中の状態、THE プラットフォーム SHALL 各段階の進行状況（サブクエリ生成中、検索中、統合中、Rerank 中）と中間結果を、回答テキストとは別のデータとして UI へストリーミングし、表示する。

### Requirement 7: ワークフローパターン

学習者として、Anthropic の5大ワークフローパターンをグラフ抽象なしに実装し、要件に応じて使い分けられるようになりたい。（モジュール 2-3）

**Acceptance Criteria**

7.1 THE プラットフォーム SHALL Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer の5パターンを、それぞれ独立して呼び出せる再利用可能な関数として提供する。
7.2 WHEN Prompt Chaining の途中ステップの出力がステップ間検証に失敗した時、THE プラットフォーム SHALL 後続ステップを実行せず、失敗したステップ名と検証エラーを返す。
7.3 WHEN Routing に入力が与えられた時、THE プラットフォーム SHALL 入力を事前定義された分類のいずれか1つに振り分け、分類結果と選択理由を返したうえで対応する処理を実行する。
7.4 IF Routing の分類結果が事前定義された分類のいずれにも該当しない場合、THEN THE プラットフォーム SHALL 既定のフォールバック処理を実行する。
7.5 WHERE Parallelization が Sectioning モードの場合、THE プラットフォーム SHALL 分割された各サブタスクを並列に実行し、全結果を統合した出力を返す。
7.6 WHERE Parallelization が Voting モードの場合、THE プラットフォーム SHALL 同一タスクを N 回（N は設定可能）並列実行し、多数決による結論と各票の内訳を返す。
7.7 WHEN Orchestrator-Workers にタスクが与えられた時、THE プラットフォーム SHALL オーケストレーターが実行時にサブタスクを動的に決定し、各サブタスクをワーカーへ並列委譲し、統合結果とサブタスク一覧を返す。
7.8 WHEN Evaluator-Optimizer が実行された時、THE プラットフォーム SHALL 生成物を 0〜100 点のスコアと改善フィードバックで評価し、スコアが合格基準（既定 85 点）に達するか最大反復回数（既定 3 回）に達するまで改善を繰り返す。
7.9 THE プラットフォーム SHALL Evaluator-Optimizer の結果として、最終生成物、実行した反復回数、各反復のスコアとフィードバックの履歴を返す。
7.10 IF Evaluator-Optimizer が最大反復回数に達しても合格基準を満たさない場合、THEN THE プラットフォーム SHALL 最高スコアの生成物を返し、結果に未合格であることを明示する。
7.11 WHEN Evaluator-Optimizer が複数の専門評価器（例: セキュリティ、パフォーマンス）で構成された時、THE プラットフォーム SHALL 各評価器を並列に実行し、評価器ごとのスコアと統合スコアを返す。
7.12 WHERE Routing がモデル選択に用いられる場合、THE プラットフォーム SHALL 入力の難度分類に応じて軽量モデルと高性能モデルのいずれかへ振り分け、振り分け先のモデル名とトークン使用量を結果に含める。
7.13 THE プラットフォーム SHALL ワークフローパターンの制御フローをコード（TypeScript の関数合成）で記述し、`ToolLoopAgent` を使わずに実装する。

### Requirement 8: ACI ツール設計と MCP 連携

学習者として、エージェントが誤用しにくいツール（ACI）を設計し、MCP を通じて標準的に外部ツールへ接続したい。（モジュール 3-1）

**Acceptance Criteria**

8.1 THE プラットフォーム SHALL すべてのツールに、用途・入力の意味・使用例を含む説明文と、スキーマで検証される入力定義を持たせる。
8.2 IF ツール入力がスキーマ検証に失敗した場合、THEN THE プラットフォーム SHALL ツール本体を実行せず、違反したパラメータ名と正しい入力形式を示す修正ガイドをエージェントへ返す。
8.3 IF ツール実行中にエラーが発生した場合、THEN THE プラットフォーム SHALL 生のスタックトレースではなく、エラーの要約と次に取るべき修正アクションを含む結果をエージェントへ返す。
8.4 WHEN ファイル操作ツールが呼び出された時、THE プラットフォーム SHALL 相対パスを拒否し、許可されたワークスペースのルート配下に正規化される絶対パスのみを受け付ける。
8.5 IF ファイル操作ツールに渡されたパスが正規化後に許可ワークスペース外を指す場合、THEN THE プラットフォーム SHALL アクセスを拒否し、許可されたルートパスを含むエラーを返す。
8.6 WHERE ツールが応答形式パラメータ（`concise` / `detailed`）を持つ場合、THE プラットフォーム SHALL `concise` 指定時に出力を設定された上限（既定 1,000 文字）以内の要約に切り詰め、全文取得方法の案内を付与する。
8.7 THE プラットフォーム SHALL ローカルファイルシステムを操作するツール群を MCP サーバーとして公開する。
8.8 WHEN エージェントが MCP サーバーへ接続した時、THE プラットフォーム SHALL サーバーが公開するツール一覧を取得し、エージェントが呼び出せるツールとして登録する。
8.9 WHERE GitHub のアクセストークンが設定されている場合、THE プラットフォーム SHALL GitHub を操作する MCP サーバーへ接続し、そのツールをエージェントから利用可能にする。
8.10 IF MCP サーバーへの接続が失敗した、または実行中に切断された場合、THEN THE プラットフォーム SHALL 該当サーバーのツールを利用不可として扱い、サーバー名と原因をエージェントと学習者に通知する。
8.11 THE プラットフォーム SHALL すべてのツールの説明文に、そのツールを「いつ使うか」「いつ使わないか」を含める。
8.12 THE プラットフォーム SHALL 複数の低レベル API 呼び出しを要する業務操作を、1つの高水準ツールとして提供する例を少なくとも1つ含め、同じ操作を低レベルツールの組み合わせで行った場合とのステップ数・トークン数の比較を提供する。
8.13 THE プラットフォーム SHALL ツールの出力でエージェントに参照させる識別子に、機械的な UUID ではなく、名称または 0 始まりの短いインデックスなどの意味のある識別子を用いる。
8.14 THE プラットフォーム SHALL エージェントがツール呼び出しの前に計画や仮説を書き出せる思考用ツール（Think ツール）を提供し、有効・無効を設定で切り替えられるようにする。

### Requirement 9: ヘルプデスク・エージェント

学習者として、複雑な問い合わせに対して計画を立ててから実行し、状況に応じて計画を組み替えるヘルプデスク・エージェントを構築し、その進捗をダッシュボードで確認したい。（モジュール 3-2）

**Acceptance Criteria**

9.1 WHEN 問い合わせチケットがエージェントに渡された時、THE プラットフォーム SHALL 実行前に、依存関係を持つタスクの一覧からなる実行計画を構造化出力として生成する。
9.2 THE プラットフォーム SHALL 実行計画の各タスクを依存関係の順序に従って実行し、依存先タスクが完了していないタスクを実行しない。
9.3 WHEN タスクの実行結果が計画の前提と矛盾した時、THE プラットフォーム SHALL 残りのタスクについて計画を再生成し、変更前後の差分を記録する。
9.4 THE プラットフォーム SHALL 1回の実行で使用するステップ数に上限（設定可能）を設け、上限に達した場合は実行を停止して未完了タスクの一覧を返す。
9.5 WHILE エージェントが実行中の状態、THE プラットフォーム SHALL ダッシュボードに「現在のタスク」「完了タスク」「修正された計画」を、各状態変化から 1 秒以内に反映する。
9.6 WHEN エージェントが問い合わせを解決した時、THE プラットフォーム SHALL チケットの状態を `resolved` に更新し、利用者向けの最終回答を保存する。
9.7 IF エージェントが問い合わせを解決できないと判断した場合、THEN THE プラットフォーム SHALL チケットの状態を `escalated` に更新し、未解決の理由を記録する。
9.8 THE プラットフォーム SHALL 最終回答に平文のパスワード、一時パスワード、または API キーなどの認証情報を含めない。
9.9 THE プラットフォーム SHALL 評価用に、ヘルプデスクのナレッジ（FAQ・手順書）とチケットのサンプルデータを初期投入する手段を提供する。

### Requirement 10: データ分析エージェント

学習者として、アップロードしたデータをエージェントが隔離環境で自律的に分析・可視化し、エラー時には自分でコードを直して再実行する仕組みを構築したい。（モジュール 3-3）

**Acceptance Criteria**

10.1 WHEN 学習者が CSV または Excel ファイルと分析指示を送信した時、THE プラットフォーム SHALL 分析コードを生成し、ホスト環境から隔離されたサンドボックス内で実行する。
10.2 THE プラットフォーム SHALL 生成されたコードをホスト環境（Web アプリのサーバープロセスや学習者のファイルシステム）で直接実行しない。
10.3 IF サンドボックスでのコード実行がエラーで終了した場合、THEN THE プラットフォーム SHALL エラー出力をエージェントへフィードバックして修正版のコードを生成・再実行し、この修正を最大 3 回まで繰り返す。
10.4 IF 最大修正回数に達してもコード実行が成功しない場合、THEN THE プラットフォーム SHALL 実行を停止し、最後のコード、エラー内容、試行履歴を学習者に表示する。
10.5 WHEN サンドボックス内のコードがグラフ画像または表データを出力した時、THE プラットフォーム SHALL それらを UI へストリーミングし、チャート・表として描画する。
10.6 THE プラットフォーム SHALL 各実行について、生成されたコード、標準出力、エラー出力、修正回数を学習者が確認できるようにする。
10.7 THE プラットフォーム SHALL サンドボックスを分析セッションごとに作成し、セッション終了時またはアイドル状態が設定時間（既定 10 分）続いた時点で破棄する。
10.8 IF サンドボックスサービスの API キーが未設定の場合、THEN THE プラットフォーム SHALL 分析エージェントを無効として表示し、有効化に必要な設定を案内する。
10.9 IF アップロードされたファイルが非対応形式である、またはサイズ上限（既定 20 MB）を超える場合、THEN THE プラットフォーム SHALL サンドボックスを起動せずに理由を表示する。

### Requirement 11: 階層型リサーチエージェント

学習者として、専門サブエージェントを Supervisor のツールとして束ねる階層型マルチエージェントで、論文リサーチレポートを自動生成したい。（モジュール 3-4）

**Acceptance Criteria**

11.1 THE プラットフォーム SHALL 検索、手法精読、市場影響評価の3つのサブエージェントを、Supervisor エージェントから入力スキーマ付きのツールとして呼び出せる形で提供する。
11.2 WHEN 学習者がリサーチテーマを入力した時、THE プラットフォーム SHALL Supervisor がサブエージェントを呼び出して調査を進め、Markdown 形式の総合リサーチレポートを出力する。
11.3 WHEN 検索サブエージェントが呼び出された時、THE プラットフォーム SHALL arXiv から論文を検索し、各論文のタイトル、著者、公開日、arXiv ID、要旨を返す。
11.4 THE プラットフォーム SHALL サブエージェントの内部トランスクリプト全体ではなく、要約された結果のみを Supervisor のコンテキストへ返す。
11.5 THE プラットフォーム SHALL リサーチレポート中で言及されるすべての論文に、検索結果で取得した arXiv ID またはリンクを付与し、検索結果に存在しない論文を引用しない。
11.6 IF サブエージェントの実行が失敗した場合、THEN THE プラットフォーム SHALL 失敗したサブエージェント名と理由を Supervisor に返し、Supervisor は残りの結果でレポートを作成したうえで欠落した観点をレポートに明記する。
11.7 IF arXiv API がレート制限またはエラーを返した場合、THEN THE プラットフォーム SHALL 待機を挟んで最大 3 回まで再試行し、それでも失敗した場合は 11.6 に従う。
11.8 THE プラットフォーム SHALL Supervisor によるサブエージェント呼び出しの回数に上限（設定可能）を設ける。
11.9 WHILE リサーチが実行中の状態、THE プラットフォーム SHALL 各サブエージェントの呼び出し、ツール実行、中間成果物（論文サマリーカード等）を、どのサブエージェントのものかを区別して UI へストリーミング表示する（Agent Inspector UI）。
11.10 WHEN リサーチが完了した時、THE プラットフォーム SHALL Supervisor と各サブエージェントのトークン使用量の内訳と合計を、実行結果に含めて表示する。

### Requirement 12: コンテキストエンジニアリング

学習者として、長い会話や大量データでもコンテキストの肥大化（Context Rot）を防ぎ、注意バジェットを健全に保つ仕組みを実装したい。（モジュール 4-1）

**Acceptance Criteria**

12.1 WHEN 会話履歴のトークン数が設定された閾値（既定: モデルのコンテキスト上限の 70%）を超えた時、THE プラットフォーム SHALL Compaction を実行し、履歴を要約済みコンテキストと直近のメッセージで置き換える。
12.2 THE プラットフォーム SHALL Compaction 後のコンテキストに、未解決事項、決定事項、以降の処理で参照される重要な値（ID、ファイルパス等）を保持する。
12.3 THE プラットフォーム SHALL Compaction の実行ごとに、実行前後のトークン数と削減率を記録する。
12.4 WHERE Structured Note-Taking が有効な場合、THE プラットフォーム SHALL エージェントがノートを外部ストレージへ書き込み・読み出しできるツールを提供し、ノートの内容を会話履歴の Compaction 後も保持する。
12.5 WHEN ツールの生の出力が設定された上限（既定 2,000 トークン）を超える時、THE プラットフォーム SHALL 出力全体をコンテキストへ入れず、集約・フィルタ済みの結果と全体の取得方法の案内を返す（段階的開示）。
12.6 IF Compaction の要約生成が失敗した場合、THEN THE プラットフォーム SHALL 元の会話履歴を変更せずに保持し、失敗を記録する。
12.7 THE プラットフォーム SHALL エージェントのメモリとして、短期メモリ（会話のメッセージ配列）、長期セマンティックメモリ（ベクトル検索で想起する過去の知識）、外部状態ストア（DB 等に保存する構造化状態）の3種を提供し、各エージェントがどれを使うかを設定で指定できるようにする。
12.8 THE プラットフォーム SHALL リファレンス実装のエージェントのシステムプロンプトを、「達成すべきゴール」「許容されない行動の境界」「優先順位の判断基準」の区分を持つテンプレートとして管理する。

### Requirement 13: 長時間実行ハーネス

学習者として、セッションをまたぐ長時間タスクで「中途半端な状態での完了宣言」を防ぐ、Initializer → Worker の2層ハーネスを構築したい。（モジュール 4-2）

**Acceptance Criteria**

13.1 WHEN ハーネスに要件記述が与えられた時、THE プラットフォーム SHALL Initializer エージェントに、全項目の `passes` を `false` とした機能リスト、検証用テストスクリプト、進捗ログを作業ディレクトリに生成させる。
13.2 WHEN Worker エージェントのセッションが開始された時、THE プラットフォーム SHALL 機能リスト、進捗ログ、バージョン管理の履歴を読み込ませ、`passes` が `false` の機能を1つだけ選んで作業させる。
13.3 THE プラットフォーム SHALL 機能の `passes` を `true` に更新することを、その機能の検証テストが成功した場合にのみ許可する。
13.4 IF Worker が検証テストの失敗した機能の `passes` を `true` に更新しようとした場合、THEN THE プラットフォーム SHALL 更新を拒否し、失敗したテストの内容を Worker に返す。
13.5 WHEN Worker が1つの機能を完了した時、THE プラットフォーム SHALL 変更をバージョン管理にコミットし、進捗ログに完了内容と次の作業候補を追記する。
13.6 THE プラットフォーム SHALL 機能リストの項目の追加・削除・説明文変更を Worker に許可せず、`passes` フィールドの更新のみを許可する。
13.7 WHILE 機能リストに `passes` が `false` の項目が残っている状態、THE プラットフォーム SHALL 設定された最大セッション数に達するまで Worker セッションを繰り返し起動する。
13.8 WHEN 機能リストの全項目の `passes` が `true` になった時、または最大セッション数に達した時、THE プラットフォーム SHALL ハーネスを終了し、完了・未完了の機能数を報告する。
13.9 THE プラットフォーム SHALL ハーネスの作業ディレクトリを学習者指定のディレクトリ配下に限定し、それ以外のパスへの書き込みを拒否する。

### Requirement 14: Agent Evals

学習者として、エージェントの推論過程ではなく最終結果（Outcome）を客観評価する評価スイートを作り、CI で回帰を検出したい。（モジュール 4-3）

**Acceptance Criteria**

14.1 THE プラットフォーム SHALL 評価を Task（評価課題）、Trial（1回の試行）、Transcript（実行記録）、Outcome（最終状態）の4要素で記録する。
14.2 THE プラットフォーム SHALL 評価スイートを Capability（能力評価）と Regression（回帰評価）の2区分に分け、区分ごとに実行できるようにする。
14.3 THE プラットフォーム SHALL グレーダーとして、Code-based（決定論的アサーション）と LLM-as-a-Judge（ルーブリック採点）の2種を提供する。
14.4 WHEN Code-based グレーダーが実行された時、THE プラットフォーム SHALL エージェント実行後の外部状態（DB レコード、生成ファイル等）を検証し、合否を判定する。
14.5 WHEN LLM-as-a-Judge グレーダーが実行された時、THE プラットフォーム SHALL ルーブリックの各項目について、スコアと判定根拠を構造化出力として返す。
14.6 THE プラットフォーム SHALL 各評価タスクについて、Human SME が判定を記入するためのレビュー用出力（トランスクリプトと Outcome の要約）を生成できるようにする。
14.7 WHERE 評価タスクの試行回数 N が2以上に設定された場合、THE プラットフォーム SHALL N 回の Trial を実行し、成功率を報告する。
14.8 WHILE 実行モードが `mock` の状態、THE プラットフォーム SHALL Regression 評価を API キーなしで決定論的に実行し、品質ゲートに含める。
14.9 THE プラットフォーム SHALL `local` または `live` モードの Capability 評価と LLM-as-a-Judge を品質ゲートとは別のコマンドで実行できるようにする。
14.10 WHEN 評価が完了した時、THE プラットフォーム SHALL タスクごとの合否、スコア、所要時間、トークン使用量を含むレポートを出力する。
14.11 THE プラットフォーム SHALL 各評価タスクに「エージェントが行動すべきでない」ケース（過剰トリガー検出）を含められるようにする。
14.12 IF Capability 評価の全タスクが連続して合格し続けた場合（飽和）、THEN THE プラットフォーム SHALL 評価レポートでその区分が飽和していることを警告する。
14.13 THE プラットフォーム SHALL LLM-as-a-Judge を評価軸ごとに別のプロンプトで実行し、各軸の判定に、根拠不足を表す「判定不能（unknown）」を選択肢として含める。
14.14 THE プラットフォーム SHALL Capability 評価で安定して合格したタスクを、Regression 評価へ昇格（卒業）させる手段を提供する。
14.15 THE プラットフォーム SHALL 評価タスクのシナリオとテストデータを、構造化出力を用いて合成生成する手段を提供し、生成したデータを人間がレビューしてから評価セットに追加できるようにする。

### Requirement 15: 安全設計と Human-in-the-Loop

学習者として、プロンプトインジェクションや不可逆な操作による被害範囲（ブラスト半径）を最小化し、破壊的アクションの前に人間の承認を挟む仕組みを実装したい。（モジュール 4-4）

**Acceptance Criteria**

15.1 THE プラットフォーム SHALL すべてのツールに「読み取り専用」「書き込み」「破壊的アクション」のいずれかのリスク区分を付与する。
15.2 WHEN エージェントが破壊的アクションに区分されたツールを呼び出そうとした時、THE プラットフォーム SHALL ツールを実行せずに実行を一時停止し、ツール名と実行予定の引数を含む承認ダイアログを学習者に表示する。
15.3 WHEN 学習者が承認ダイアログで承認した時、THE プラットフォーム SHALL 承認された引数のままツールを実行し、エージェントの実行を再開する。
15.4 WHEN 学習者が承認ダイアログで拒否した時、THE プラットフォーム SHALL ツールを実行せず、拒否された旨をツール結果としてエージェントへ返して実行を再開する。
15.5 IF 承認待ちの間にエージェントの実行セッションが中断された場合、THEN THE プラットフォーム SHALL 承認待ちのツールを実行しない。
15.6 WHERE エージェントに読み取り専用モードが指定された場合、THE プラットフォーム SHALL 書き込みおよび破壊的アクションに区分されたツールをエージェントに公開しない。
15.7 THE プラットフォーム SHALL 外部から取得したコンテンツ（Web ページ、ファイル、ツール結果）を、システム指示とは区別されたデータとしてエージェントに渡す。
15.8 WHEN 外部から取得したコンテンツに起因してエージェントが破壊的アクションを呼び出そうとした時、THE プラットフォーム SHALL 15.2 の承認ゲートを必ず経由させる。
15.9 THE プラットフォーム SHALL 承認・拒否の判断を、日時、ツール名、引数、判断結果とともに監査ログとして記録する。
15.10 WHEN 外部から取得したコンテンツがエージェントのコンテキストへ取り込まれる時、THE プラットフォーム SHALL 既知のプロンプトインジェクションのパターン（指示の上書き、ロールの偽装、ツール呼び出しの誘導等）を検査し、検出した場合は検出内容を記録して学習者に警告を表示する。
15.11 THE プラットフォーム SHALL エージェントの最終出力と構造化出力をスキーマで検証し、スキーマ外のフィールドや許可されない形式の値（スクリプト、実行可能なリンク等）を除去してから UI とツールへ渡す。

### Requirement 16: オブザーバビリティ

学習者として、エージェントの LLM 呼び出しとツール実行をトレースとして可視化し、問題の原因を追跡したい。（モジュール 4-4）

**Acceptance Criteria**

16.1 WHERE トレース収集が有効な場合、THE プラットフォーム SHALL LLM 呼び出し、ツール実行、ワークフローの各ステップを、親子関係を持つ OpenTelemetry 形式のスパンとして出力する。
16.2 THE プラットフォーム SHALL 各 LLM 呼び出しのスパンに、プロバイダ、モデル名、入力・出力トークン数、所要時間を記録する。
16.3 WHEN トレース収集先としてローカルのトレース基盤が指定された時、THE プラットフォーム SHALL そのトレース基盤の UI で1回のエージェント実行全体を1つのトレースとして閲覧できるようにする。
16.4 THE プラットフォーム SHALL スパンに API キー等の認証情報を記録しない。
16.5 IF トレース収集先に接続できない場合、THEN THE プラットフォーム SHALL エージェントの実行を継続し、トレース送信の失敗を警告として記録する。
16.6 WHILE トレース収集が無効な状態、THE プラットフォーム SHALL トレース収集先への通信を一切行わない。

### Requirement 17: モジュール解説ドキュメント

学習者として、各モジュールで何を学び、何を作り、どう習熟度を判定するかを日本語で読める解説が欲しい。

**Acceptance Criteria**

17.1 THE プラットフォーム SHALL 19 モジュールそれぞれについて、日本語の解説ドキュメントを1つずつ提供する。
17.2 THE プラットフォーム SHALL 各解説ドキュメントに、学習目標、主要トピック、ハンズオン手順、習熟度判定チェックリスト、対応するリファレンス実装とテストの所在を含める。
17.3 THE プラットフォーム SHALL 各解説ドキュメントに、元教材（Python / LangChain / LangGraph）の対応箇所と、TypeScript / AI SDK 版での置き換え内容を示す対照表を含める。
17.4 THE プラットフォーム SHALL 各解説ドキュメントに、ドラフトのコード例・バージョン・モデル ID と実装で採用したものとの差分を明記する。
17.5 THE プラットフォーム SHALL 各解説ドキュメントのハンズオン手順を、`mock` モードのみで最後まで実施できるようにし、`local` / `live` モードでのみ確認できる手順にはその旨を明示する。
17.6 THE プラットフォーム SHALL 習熟度判定チェックリストの各項目について、自動テストで検証できるものには対応するテストへの参照を付与する。
17.7 THE プラットフォーム SHALL 各フェーズの冒頭に、IBM の3段階成熟度モデル（Generative AI / AI Agents / Agentic AI）のどの水準を扱うかを明記する。
17.8 THE プラットフォーム SHALL モジュール 1-0 の解説として、IBM の3段階成熟度モデル、Agentic AI の7段階閉ループ（知覚→推論→目標設定→意思決定→実行→学習/適応→オーケストレーション）、生成 AI と Agentic AI の比較マトリクスを提供し、7段階の各段がどのモジュールで実装されるかの対応表を含める。
17.9 THE プラットフォーム SHALL 各解説ドキュメントに、下表「モジュール別の必須解説トピック」に挙げたトピックを含める。
17.10 THE プラットフォーム SHALL Phase 1 の各解説ドキュメントに、Python / Streamlit 経験者向けの対比コラム（例: `st.session_state` と `useChat` / `useState`、再実行モデルとイベントハンドラ）を含める。
17.11 THE プラットフォーム SHALL 各モジュールの完成時点のリファレンス実装を、バージョン管理のタグとして提供し、学習者が自分の作業との差分を比較して復帰できるようにする。

### Requirement 18: ツール呼び出しと ToolLoopAgent

学習者として、受動的な生成からツールを使う AI エージェントへの転換を、AI SDK v7 の `ToolLoopAgent` で最小構成から体験したい。ツールの実行状況と結果が UI 上で型付きのコンポーネントとして見えるようにしたい。（モジュール 1-2）

**Acceptance Criteria**

18.1 WHEN 学習者がツールを必要とする質問を送信した時、THE プラットフォーム SHALL `ToolLoopAgent` により「ツール呼び出し → 結果の取得 → 次の判断」を停止条件（Req 19）に達するか回答が完成するまで反復し、最終回答をストリーミングで返す。
18.2 THE プラットフォーム SHALL 外部 API キーなしで動くサンプルツール（現在時刻、計算、為替換算、天気）を提供する。
18.3 WHERE Web 検索サービスの API キーが設定されている場合、THE プラットフォーム SHALL Web 検索ツールをエージェントに登録する。
18.4 IF Web 検索サービスの API キーが未設定の場合、THEN THE プラットフォーム SHALL Web 検索ツールを登録せず、UI に無効である旨と有効化に必要な設定を表示する。
18.5 WHEN ツールの実行が開始・完了・失敗した時、THE プラットフォーム SHALL チャット画面に、ツール名、入力、実行状態、結果を表示する。表示用コンポーネントが登録されたツールの結果は、生の JSON ではなく、型付きの UI コンポーネント（カード、チャート、フォーム等）として描画する（Generative UI）。
18.6 WHILE 質問がモデル自身の知識だけで回答できる状態、THE プラットフォーム SHALL ツールを呼び出さずに回答できるようにし、各回答で呼び出したツールの一覧を結果に含める。
18.7 THE プラットフォーム SHALL 現在時刻に依存するツールに、時刻を取得する関数（Clock）を注入し、ツール内で直接システム時刻を読まない。
18.8 IF ツールの実行中に例外が発生した場合、THEN THE プラットフォーム SHALL ループを中断せず、エラー内容をツール結果としてエージェントに返す（Req 8.3 の形式に従う）。

### Requirement 19: ループ制御と強制停止条件

学習者として、エージェントの無限ループや暴走を物理的に遮断し、なぜ止まったのかを後から確認できるようにしたい。（全体。M1 から適用し、モジュール 4-4 で解説）

**Acceptance Criteria**

19.1 THE プラットフォーム SHALL すべての `ToolLoopAgent` に、最大ステップ数、累積トークン使用量の上限、実行時間の上限の3種の停止条件を設定し、いずれかに達した時点でループを停止する。既定値は設定で変更できる。
19.2 WHEN エージェントループが停止した時、THE プラットフォーム SHALL 停止理由を閉じた語彙（`completed`、`step-limit`、`token-budget`、`timeout`、`aborted`、`error`）の1つとして実行結果に含める。
19.3 WHEN 学習者が実行中のエージェントを停止した時、THE プラットフォーム SHALL 停止を実行中の LLM 呼び出し、ツール実行、サンドボックスへ伝播させて中断し、停止理由を `aborted` とする。
19.4 IF 1回のツール実行が設定された時間上限を超えた場合、THEN THE プラットフォーム SHALL そのツール実行を打ち切り、タイムアウトしたことをツール結果としてエージェントに返してループを継続する。
19.5 THE プラットフォーム SHALL 停止理由と、停止時点のステップ数・累積トークン数・経過時間を、トレース（Req 16）と評価レポート（Req 14.10）に記録する。

### Requirement 20: エージェントデザインパターン

学習者として、18 のエージェントデザインパターンの体系を理解し、そのうち主要なパターンをグラフ抽象なしの TypeScript で実装して使い分けられるようになりたい。（モジュール 2-4）

**Acceptance Criteria**

20.1 THE プラットフォーム SHALL Passive Goal Creator、Prompt/Response Optimizer、Single-Path Plan Generator、Multi-Path Plan Generator、Self-Reflection / Cross-Reflection、Role-Based Cooperation の6パターンを、それぞれ独立して呼び出せる再利用可能な関数として提供する。
20.2 WHEN Passive Goal Creator に曖昧な指示が与えられた時、THE プラットフォーム SHALL 目的、制約、成功基準を持つ目標仕様を構造化出力として返し、情報が不足する場合は不足項目と確認用の質問を併せて返す。
20.3 WHEN Prompt/Response Optimizer が実行された時、THE プラットフォーム SHALL 改善前後のプロンプト（または回答）と、改善の理由を返す。
20.4 WHEN Single-Path Plan Generator にゴールが与えられた時、THE プラットフォーム SHALL 順序付きのステップ一覧を生成して順に実行し、ステップごとの結果を返す。
20.5 WHEN Multi-Path Plan Generator にゴールが与えられた時、THE プラットフォーム SHALL 複数の候補計画（数は設定可能、既定 3）を並列に生成し、評価器が選んだ計画と選択理由、全候補の評価結果を返す。
20.6 WHEN Self-Reflection または Cross-Reflection が実行された時、THE プラットフォーム SHALL 批評（Cross-Reflection では生成時と異なるモデルによる批評）と修正を最大反復回数（既定 3 回）まで繰り返し、各反復の批評と修正の履歴を返す。
20.7 WHEN Role-Based Cooperation にタスクが与えられた時、THE プラットフォーム SHALL 役割（例: リサーチャー、コーダー、レビュアー）ごとの `ToolLoopAgent` に作業を順に受け渡し、役割ごとの出力と最終成果物を返す。
20.8 THE プラットフォーム SHALL 18 パターンすべてについて、リファレンス実装のどのモジュール・関数に対応するか、または解説のみで扱うかを示す対応表を、モジュール 2-4 の解説ドキュメントに含める。

### Requirement 21: 要件定義書生成エージェント

学習者として、ユーザーへのヒアリングを通じて要件を構造化し、要件定義書を生成するエージェントを構築したい。（モジュール 3-5）

**Acceptance Criteria**

21.1 WHEN 学習者がプロダクトの概要を入力した時、THE プラットフォーム SHALL 想定利用者のペルソナを複数（数は設定可能、既定 3）、構造化出力として生成する。
21.2 WHEN ペルソナが生成された時、THE プラットフォーム SHALL 各ペルソナの視点からのヒアリング質問を生成し、学習者との対話形式でインタビューを進める。
21.3 WHILE インタビューが進行中の状態、THE プラットフォーム SHALL 回答から要件（機能、非機能、制約、未確認事項）を抽出し、画面上の要件プレビューを回答ごとに更新する。
21.4 WHEN インタビューの1ラウンドが終わった時、THE プラットフォーム SHALL 収集した情報が要件定義書の作成に十分かを判定し、判定結果と不足している項目を構造化出力として返す。
21.5 IF 情報が不足していて、インタビューのラウンド数が上限（設定可能、既定 5）未満の場合、THEN THE プラットフォーム SHALL 不足項目に焦点を当てた追加の質問でインタビューを継続する。
21.6 WHEN 情報が十分と判定された時、またはラウンド数が上限に達した時、THE プラットフォーム SHALL 固定の章立てを持つ Markdown 形式の要件定義書を生成し、上限到達で終了した場合は「未確認事項」の章に不足項目を列挙する。
21.7 THE プラットフォーム SHALL 生成した要件定義書を Markdown ファイルとしてダウンロードできるようにする。

### Requirement 22: マーケティング支援エージェント

学習者として、複数ペルソナの合議による改善ループと、会話から抽出した利用者プロファイルに基づくレコメンドを構築したい。（モジュール 3-6）

**Acceptance Criteria**

22.1 WHEN 学習者が改善対象の文案（例: 広告コピー、商品説明）を入力した時、THE プラットフォーム SHALL 複数のペルソナ（数と役割は設定可能、既定は辛口なマーケター、一般消費者、SEO スペシャリストの3名）が、他のペルソナの発言を踏まえて順番に意見と改善案を述べるラウンドロビン形式の合議を実行する。
22.2 THE プラットフォーム SHALL 各ラウンドの終了時に合意に達したかを判定し、合意に達するか最大ラウンド数（既定 3）に達した時点で合議を終了して、改善後の文案、ラウンドごと・ペルソナごとの発言、終了理由を返す。
22.3 WHILE 合議が進行中の状態、THE プラットフォーム SHALL 各ペルソナの発言を、ペルソナ名を付けて UI へストリーミング表示する。
22.4 WHILE 学習者がレコメンド用のチャットで会話している状態、THE プラットフォーム SHALL 会話から利用者プロファイル（関心事、予算、懸念点）を構造化出力として逐次抽出し、画面上のプロファイル表示とレコメンド表示を更新する（Generative UI）。
22.5 THE プラットフォーム SHALL レコメンドの候補を事前に投入された商品カタログからのみ選び、各レコメンドに商品 ID と推薦理由を付け、カタログに存在しない商品を提示しない。
22.6 THE プラットフォーム SHALL 評価用に、商品カタログとペルソナ定義のサンプルデータを初期投入する手段を提供する。

### Requirement 23: 総合演習（アーキテクチャ選定）

学習者として、新しいアプリケーションの要件に対して、単一プロンプト・ワークフロー・自律型エージェントのどれを採用すべきかを根拠をもって判断できるようになりたい。（モジュール 4-5）

**Acceptance Criteria**

23.1 THE プラットフォーム SHALL アーキテクチャ選定の判断フロー（単一プロンプト + Augmented LLM で足りるか → 固定のワークフローに分解できるか → サブタスクが入力依存で動的か → 反復回数が予測不能で環境フィードバックによる試行錯誤が必須か）を解説ドキュメントとして提供する。
23.2 THE プラットフォーム SHALL 判断フローを適用する演習シナリオを10件以上提供し、各シナリオに、要件の記述、模範解答（採用するアーキテクチャ）、判断の根拠を含める。
23.3 THE プラットフォーム SHALL 演習シナリオに、単一プロンプトで足りるもの、5つのワークフローパターンの各々が適するもの、Orchestrator-Workers が適するもの、自律型エージェントが適するものを、それぞれ1件以上含める。
23.4 THE プラットフォーム SHALL 各模範解答に、そのアーキテクチャを実装しているリファレンス実装のモジュールへの参照と、自律型エージェントを採用する場合に併設すべき安全策（ACI のポカヨケ、隔離サンドボックス、ハーネス、Evals、強制停止条件）を含める。
23.5 THE プラットフォーム SHALL マルチエージェント構成を模範解答とするシナリオについて、単一エージェント構成と比べたトークン使用量の実測値（Req 11 の実行結果に基づく）を判断材料として示す。

## Non-Functional Requirements

- **検証速度**: WHILE 実行モードが `mock` の状態、THE プラットフォーム SHALL 依存インストール済みの開発機で `mise run gate` を 5 分以内に完了する。
- **決定性**: WHILE 実行モードが `mock` の状態、THE プラットフォーム SHALL 同一コミットに対して品質ゲートを 10 回連続実行した場合に 10 回とも同一の合否結果を返す。
- **オフライン動作**: WHILE ネットワークに接続されていない状態、THE プラットフォーム SHALL `mock` モードでの品質ゲートとハンズオン手順を実行可能にする（依存インストールを除く）。
- **ストリーミング応答性**: THE プラットフォーム SHALL `mock` モードにおいて、チャット送信から最初のトークンが画面に表示されるまでを 500 ms 以内とする。
- **型安全性**: THE プラットフォーム SHALL TypeScript の strict モードで型検査を通し、エージェント基盤ライブラリの公開 API に `any` 型を含めない。
- **テストカバレッジ**: THE プラットフォーム SHALL エージェント基盤ライブラリの行カバレッジを 80% 以上に保つ。
- **秘密情報**: THE プラットフォーム SHALL API キーを環境変数からのみ読み込み、秘密情報を含む設定ファイルをバージョン管理の対象から除外し、キー名の一覧のみを含むサンプル設定ファイルを提供する。
- **隔離実行**: THE プラットフォーム SHALL LLM が生成したコードをホスト環境で実行しない（Req 10.2 の横断適用）。
- **アクセシビリティ**: THE プラットフォーム SHALL チャット画面、ダッシュボード、承認ダイアログをキーボードのみで操作可能にし、WCAG 2.2 AA のコントラスト基準を満たす。
- **対応ブラウザ**: THE プラットフォーム SHALL 最新安定版の Chrome、Firefox、Safari で Web アプリの全機能を動作させる。
- **UI 言語**: THE プラットフォーム SHALL Web アプリの UI 文言と解説ドキュメントを日本語で提供する。
- **コスト可視化**: WHERE 実行モードが `live` の場合、THE プラットフォーム SHALL 評価レポートとトレースに、トークン使用量に基づく推定コストを表示する。
