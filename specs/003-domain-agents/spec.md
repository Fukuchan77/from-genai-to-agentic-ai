# domain-agents — Requirements

## Overview

マスターカリキュラム Phase 3（現場実践編。確定版は [curriculum/phase-3.md](../curriculum/phase-3.md)）のリファレンス実装の要件を定義する。ACI 設計と MCP によるツール統合を土台に、ヘルプデスク（Plan-and-Execute）、データ分析（E2B サンドボックスと自己修正）、階層型論文リサーチ（Agent-as-a-Tool）、要件定義書生成（インタビュー型）、マーケティング支援（ロールプレイ合議と会話型レコメンド）の6つの実務ドメインのエージェントを `ToolLoopAgent` で実装する。IBM の成熟度モデルでは、主に Level 2（AI Agents）から Level 3（Agentic AI）を扱う。

本 spec は、2026-09-27 に [`001-agentic-ai-platform`](../001-agentic-ai-platform/spec.md) から分割した（要件レビュー C-1。[review-2026-09-26.md](../001-agentic-ai-platform/review-2026-09-26.md) §8）。

## 前提（001 から継承）

- 次の事項は `001-agentic-ai-platform` を正本とし、本 spec では再定義しない: Clarifications、Technical Constraints、Runtime Environment、LLM Provider & Test Strategy、Glossary、Non-Functional Requirements、Out of Scope / Future Work、001 Req 6（ループ制御と強制停止条件）、001 Req 7（モジュール解説ドキュメント）。
- 特にテスト方針は 001 に従う: 各モジュールの自動テストは `mock` モードで完走でき（001 Req 1.13）、比較・品質評価のテストは `local` モードで実行可能な場合に限り実行する（001 Req 1.13、1.14）。モジュールの実行（ハンズオン）は `local` / `live` を原則とする（001 Req 2.12）。外部サービスは `mock` では fixture または疑似実装に置き換える（001 Req 2.15）。品質ゲートは Docker なしで完走する（001 Req 1.11、1.12）。
- 本文中の `00N Req X.Y` は spec `00N` の要件 X.Y を指す。spec 番号のない `Req X.Y` は本 spec の要件を指す。

## Requirements

### Requirement 1: ACI ツール設計と MCP 連携

学習者として、エージェントが誤用しにくいツール（ACI）を設計し、MCP を通じて標準的に外部ツールへ接続したい。（モジュール 3-1）

**Acceptance Criteria**

1.1 THE プラットフォーム SHALL すべてのツールに、用途・入力の意味・使用例を含む説明文と、スキーマで検証される入力定義を持たせる。
1.2 IF ツール入力がスキーマ検証に失敗した場合、THEN THE プラットフォーム SHALL ツール本体を実行せず、違反したパラメータ名と正しい入力形式を示す修正ガイドをエージェントへ返す。
1.3 IF ツール実行中にエラーが発生した場合、THEN THE プラットフォーム SHALL エラーを「回復可能（入力の誤り、一時的な失敗、タイムアウト）」と「致命的（認証失敗、設定不備、許可されない操作）」に分類する。回復可能なエラーは、生のスタックトレースではなく、エラーの要約と次に取るべき修正アクションを含む結果としてエージェントへ返し、致命的なエラーは run を停止して停止理由 `error` とともに学習者に表示する。
1.4 WHEN ファイル操作ツールが呼び出された時、THE プラットフォーム SHALL 相対パスを拒否し、許可されたワークスペースのルート配下に正規化される絶対パスのみを受け付ける。
1.5 IF ファイル操作ツールに渡されたパスを、シンボリックリンクを解決した実パスに変換した結果が、許可ワークスペースのルートと同一またはその配下（パス区切り単位で判定し、ルートと同じ接頭辞を持つ別ディレクトリを含めない）でない場合、THEN THE プラットフォーム SHALL アクセスを拒否し、許可されたルートパスを含むエラーを返す。
1.6 WHERE ツールが応答形式パラメータ（`concise` / `detailed`）を持つ場合、THE プラットフォーム SHALL `concise` 指定時に出力を設定された上限（既定 1,000 文字）以内の要約に切り詰め、全文取得方法の案内を付与する。
1.7 THE プラットフォーム SHALL ローカルファイルシステムを操作するツール群を、公式の MCP SDK を用いて自作した MCP サーバーとして公開し、stdio トランスポートで接続できるようにする。
1.8 WHEN エージェントが MCP サーバーへ接続した時、THE プラットフォーム SHALL AI SDK v7 の MCP クライアントでサーバーが公開するツール一覧を取得し、エージェントごとの許可リストに含まれるツールだけを、エージェントが呼び出せるツールとして登録する。
1.9 WHERE GitHub のアクセストークンが設定されている場合、THE プラットフォーム SHALL GitHub を操作する MCP サーバーへ接続し、そのツールをエージェントから利用可能にする。
1.10 IF MCP サーバーへの接続が失敗した、または実行中に切断された場合、THEN THE プラットフォーム SHALL 該当サーバーのツールを利用不可として扱い、サーバー名と原因をエージェントと学習者に通知する。
1.11 THE プラットフォーム SHALL すべてのツールの説明文に、そのツールを「いつ使うか」「いつ使わないか」を含める。
1.12 THE プラットフォーム SHALL 複数の低レベル API 呼び出しを要する業務操作を、1つの高水準ツールとして提供する例を少なくとも1つ含め、同じ操作を低レベルツールの組み合わせで行った場合とのステップ数・トークン数の比較を提供する。
1.13 THE プラットフォーム SHALL ツールの出力でエージェントに参照させる識別子に、機械的な UUID ではなく、名称または 0 始まりの短いインデックスなどの意味のある識別子を用いる。
1.14 THE プラットフォーム SHALL エージェントがツール呼び出しの前に計画や仮説を書き出せる思考用ツール（Think ツール）を提供し、有効・無効を設定で切り替えられるようにする。
1.15 THE プラットフォーム SHALL 1つのエージェントに登録するツールの数を 20 以下に制限し、MCP サーバーのツールを含めて上限を超える構成を起動時に拒否する。
1.16 THE プラットフォーム SHALL すべてのツール定義に、004 Req 4.1 のリスク区分（読み取り専用、書き込み、破壊的アクション）を M3 の時点から付与する。
1.17 WHILE 004 Req 4 の承認ゲートが実装されていない状態、THE プラットフォーム SHALL 書き込みおよび破壊的アクションに区分されたツール（ファイル削除、GitHub への issue 作成、回答送信等）をエージェントに登録せず、読み取り専用のツールだけで M3 のハンズオンとテストを完結させる。

### Requirement 2: ヘルプデスク・エージェント

学習者として、複雑な問い合わせに対して計画を立ててから実行し、状況に応じて計画を組み替えるヘルプデスク・エージェントを構築し、その進捗をダッシュボードで確認したい。（モジュール 3-2）

**Acceptance Criteria**

2.1 WHEN 問い合わせチケットがエージェントに渡された時、THE プラットフォーム SHALL 実行前に、依存関係を持つタスクの一覧からなる実行計画を構造化出力として生成する。
2.2 THE プラットフォーム SHALL 実行計画の各タスクを依存関係の順序に従って実行し、依存先タスクが完了していないタスクを実行しない。
2.3 WHEN 計画の各タスクの実行が完了した時、THE プラットフォーム SHALL Replanner に `continue`（計画どおり続行）、`replan`（残りのタスクを再計画）、`finish`（最終回答へ進む）のいずれかを判断理由とともに構造化出力で返させ、`replan` の場合は残りのタスクについて計画を再生成して、変更前後の差分を記録する。
2.4 THE プラットフォーム SHALL 1回の実行で使用するステップ数に上限（設定可能）を設け、上限に達した場合は実行を停止して未完了タスクの一覧を返す。
2.5 WHILE エージェントが実行中の状態、THE プラットフォーム SHALL ダッシュボードに「現在のタスク」「完了タスク」「修正された計画」を、各状態変化から 1 秒以内に反映する。
2.6 WHEN エージェントが問い合わせを解決した時、THE プラットフォーム SHALL チケットの状態を `resolved` に更新し、利用者向けの最終回答を保存する。
2.7 IF エージェントが問い合わせを解決できないと判断した場合、THEN THE プラットフォーム SHALL チケットの状態を `escalated` に更新し、未解決の理由を記録する。
2.8 WHEN エージェントが最終回答を作成した時、THE プラットフォーム SHALL 保存・表示の前に認証情報の形状（平文のパスワード、一時パスワード、API キー、アクセストークン）をパターン検査し、検出した場合は保存せず、検出した種別を記録してエージェントに回答を再作成させる。再作成後も検出された場合は、チケットを `escalated` にする。
2.9 THE プラットフォーム SHALL 評価用に、ヘルプデスクのナレッジ（FAQ・手順書）とチケットのサンプルデータを初期投入する手段を提供する。
2.10 IF 生成された実行計画が不正な場合（依存関係の循環、存在しないタスクへの依存、空の計画）、THEN THE プラットフォーム SHALL その計画を実行せず、不正の内容をフィードバックして計画を再生成し、再生成が上限（既定 2 回）に達しても不正な場合はチケットを `escalated` にする。

### Requirement 3: データ分析エージェント

学習者として、アップロードしたデータをエージェントが隔離環境で自律的に分析・可視化し、エラー時には自分でコードを直して再実行する仕組みを構築したい。（モジュール 3-3）

**Acceptance Criteria**

3.1 WHEN 学習者が CSV または Excel ファイルと分析指示を送信した時、THE プラットフォーム SHALL 分析コードを生成し、ホスト環境から隔離されたサンドボックス内で実行する。
3.2 THE プラットフォーム SHALL 生成されたコードをホスト環境（Web アプリのサーバープロセスや学習者のファイルシステム）で直接実行しない。
3.3 IF サンドボックスでのコード実行がエラーで終了した場合、THEN THE プラットフォーム SHALL エラー出力をエージェントへフィードバックして修正版のコードを生成・再実行し、この修正を最大 3 回まで繰り返す。
3.4 IF 最大修正回数に達してもコード実行が成功しない場合、THEN THE プラットフォーム SHALL 実行を停止し、最後のコード、エラー内容、試行履歴を学習者に表示する。
3.5 WHEN サンドボックス内のコードがグラフ画像または表データを出力した時、THE プラットフォーム SHALL それらを UI へストリーミングし、チャート・表として描画する。
3.6 THE プラットフォーム SHALL 各実行について、生成されたコード、標準出力、エラー出力、修正回数を学習者が確認できるようにする。
3.7 THE プラットフォーム SHALL サンドボックスを分析セッションごとに作成し、学習者の明示的な終了操作、またはクライアントとの接続が途絶えた状態を含むアイドル状態が設定時間（既定 10 分）続いた時点で破棄する。
3.8 IF サンドボックスサービス（E2B）の API キーが未設定の場合、THEN THE プラットフォーム SHALL コンテナ実行環境が利用できるときはローカルのコンテナをサンドボックスとして使い（3.2 と同じ隔離要件を満たす）、コンテナ実行環境も利用できないときは分析エージェントを無効として表示し、有効化に必要な設定を案内する。
3.9 IF アップロードされたファイルが非対応形式である、またはサイズ上限（既定 20 MB）を超える場合、THEN THE プラットフォーム SHALL サンドボックスを起動せずに理由を表示する。
3.10 THE プラットフォーム SHALL `mock` モードのテストでは、コードを受け取り定義済みの標準出力・エラー出力・画像を返す疑似サンドボックスを用いて、3.3〜3.6 の制御を検証できるようにする。

### Requirement 4: 階層型リサーチエージェント

学習者として、専門サブエージェントを Supervisor のツールとして束ねる階層型マルチエージェントで、論文リサーチレポートを自動生成したい。（モジュール 3-4）

**Acceptance Criteria**

4.1 THE プラットフォーム SHALL 検索、手法精読、市場影響評価の3つのサブエージェントを、Supervisor エージェントから入力スキーマ付きのツールとして呼び出せる形で提供する。
4.2 WHEN 学習者がリサーチテーマを入力した時、THE プラットフォーム SHALL Supervisor がサブエージェントを呼び出して調査を進め、Markdown 形式の総合リサーチレポートを出力する。
4.3 WHEN 検索サブエージェントが呼び出された時、THE プラットフォーム SHALL arXiv から論文を検索し、各論文のタイトル、著者、公開日、arXiv ID、要旨を返す。
4.4 THE プラットフォーム SHALL サブエージェントの内部トランスクリプト全体ではなく、要約された結果のみを Supervisor のコンテキストへ返す。
4.5 WHEN リサーチレポートを出力する時、THE プラットフォーム SHALL 出力前に本文中のすべての arXiv ID とリンクを、検索サブエージェントが取得した論文の集合と照合し、集合に含まれない論文への言及を除去して、除去した旨の警告をレポートに付ける。レポート中で言及するすべての論文には arXiv ID またはリンクを付与する。
4.6 IF サブエージェントの実行が失敗した場合、THEN THE プラットフォーム SHALL 失敗したサブエージェント名と理由を Supervisor に返し、Supervisor は残りの結果でレポートを作成したうえで欠落した観点をレポートに明記する。
4.7 IF arXiv API がレート制限またはエラーを返した場合、THEN THE プラットフォーム SHALL 待機を挟んで最大 3 回まで再試行し、それでも失敗した場合は 4.6 に従う。
4.8 THE プラットフォーム SHALL Supervisor によるサブエージェント呼び出しの回数に上限（設定可能）を設ける。
4.9 WHILE リサーチが実行中の状態、THE プラットフォーム SHALL 各サブエージェントの呼び出し、ツール実行、中間成果物（論文サマリーカード等）を、どのサブエージェントのものかを区別して UI へストリーミング表示する（Agent Inspector UI）。
4.10 WHEN リサーチが完了した時、THE プラットフォーム SHALL Supervisor と各サブエージェントのトークン使用量の内訳と合計を、実行結果に含めて表示する。

### Requirement 5: 要件定義書生成エージェント

学習者として、ユーザーへのヒアリングを通じて要件を構造化し、要件定義書を生成するエージェントを構築したい。（モジュール 3-5）

**Acceptance Criteria**

5.1 WHEN 学習者がプロダクトの概要を入力した時、THE プラットフォーム SHALL 想定利用者のペルソナを複数（数は設定可能、既定 3）、構造化出力として生成する。
5.2 WHEN ペルソナが生成された時、THE プラットフォーム SHALL 各ペルソナの視点からのヒアリング質問を生成し、学習者との対話形式でインタビューを進める。
5.3 WHILE インタビューが進行中の状態、THE プラットフォーム SHALL 回答から要件（機能、非機能、制約、未確認事項）を抽出し、画面上の要件プレビューを回答ごとに更新する。
5.4 WHEN インタビューの1ラウンドが終わった時、THE プラットフォーム SHALL 収集した情報が要件定義書の作成に十分かを判定し、判定結果と不足している項目を構造化出力として返す。
5.5 IF 情報が不足していて、インタビューのラウンド数が上限（設定可能、既定 5）未満の場合、THEN THE プラットフォーム SHALL 不足項目に焦点を当てた追加の質問でインタビューを継続する。
5.6 WHEN 情報が十分と判定された時、またはラウンド数が上限に達した時、THE プラットフォーム SHALL 固定の章立てを持つ Markdown 形式の要件定義書を生成し、上限到達で終了した場合は「未確認事項」の章に不足項目を列挙する。
5.7 THE プラットフォーム SHALL 生成した要件定義書を Markdown ファイルとしてダウンロードできるようにする。

### Requirement 6: マーケティング支援エージェント

学習者として、複数ペルソナの合議による改善ループと、会話から抽出した利用者プロファイルに基づくレコメンドを構築したい。（モジュール 3-6）

**Acceptance Criteria**

6.1 WHEN 学習者が改善対象の文案（例: 広告コピー、商品説明）を入力した時、THE プラットフォーム SHALL 複数のペルソナ（数と役割は設定可能、既定は辛口なマーケター、一般消費者、SEO スペシャリストの3名）が、他のペルソナの発言を踏まえて順番に意見と改善案を述べるラウンドロビン形式の合議を実行する。
6.2 THE プラットフォーム SHALL 各ラウンドの終了時に合意に達したかを判定し、合意に達するか最大ラウンド数（既定 3）に達した時点で合議を終了して、改善後の文案、ラウンドごと・ペルソナごとの発言、終了理由を返す。
6.3 WHILE 合議が進行中の状態、THE プラットフォーム SHALL 各ペルソナの発言を、ペルソナ名を付けて UI へストリーミング表示する。
6.4 WHILE 学習者がレコメンド用のチャットで会話している状態、THE プラットフォーム SHALL 会話から利用者プロファイル（関心事、予算、懸念点）を構造化出力として逐次抽出し、画面上のプロファイル表示とレコメンド表示を更新する（Generative UI）。
6.5 THE プラットフォーム SHALL レコメンドの候補を事前に投入された商品カタログからのみ選び、各レコメンドに商品 ID と推薦理由を付ける。表示の前に商品 ID をカタログと照合し、カタログに存在しない商品を除去して、除去したことを記録する。
6.6 THE プラットフォーム SHALL 評価用に、商品カタログとペルソナ定義のサンプルデータを初期投入する手段を提供する。
