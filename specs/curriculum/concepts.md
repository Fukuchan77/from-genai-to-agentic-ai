# 概念体系

全モジュールが前提とする概念をまとめる。出典は Guide（Anthropic / IBM の知見）で、本カリキュラムでの実装方針と対応する要件を併記する。個々の数値と受け入れ基準は spec を正とする。

## 1. 生成 AI から Agentic AI へ

モジュール 1-0 で扱う（001 Req 7.8）。

### 考え方

- **「テキストの生成」から「状態の変更」へ**: 生成 AI は、入力に対して静的なコンテンツを出力して止まる反応型（Reactive）のシステムである。Agentic AI は、最小限の人間の監督のもとで長期的な目標を達成するため、自ら推論し、外部ツールを実行して、環境の状態を能動的（Proactive）に変え続ける。
- **LLM は「知性そのもの」ではなく「認知・計画エンジン」**: LLM はシステムの中核の意思決定エンジンとして働き、決定論的なコード（API、データベース、シェル）と組み合わさって初めて実世界のタスクを完遂できる。
- **プロンプトエンジニアリングからコンテキストの設計へ**: 1回のプロンプトの巧拙より、ツール・メモリ・停止条件を含むシステム全体の設計が品質を決める。

### 3段階の成熟度モデル（IBM）

| 水準 | 内容 |
|---|---|
| Level 1: Generative AI（受動的生成） | 入力プロンプトに対して、文章・画像・コードなどの静的コンテンツを出力して完了する。状態を変えず、環境と能動的にやり取りしない |
| Level 2: AI Agents（タスク自動化） | 事前に定義されたワークフローに沿って、特定のタスクやルール化された外部ツールを実行する。局所的で決定論的な処理が中心 |
| Level 3: Agentic AI（自律型エージェントシステム） | 最小限の人間の介入で、複雑でオープンエンドな長期目標を達成する。下記の7段階の閉ループを自律的に反復し、環境の状態を変え続ける |

### 7段階の閉ループ（IBM）

1. **知覚（Perception）**: API、センサー、DB、ユーザーのログなどから環境の情報を取得する。
2. **推論（Reasoning）**: 取得した情報を解析し、制約を把握する。
3. **目標設定（Goal Setting）**: 高次の目標を、達成可能なサブゴールに分解する。
4. **意思決定（Decision-Making）**: コスト、安全性、確信度を評価し、行動の経路を選ぶ。
5. **実行（Execution）**: ツールの呼び出しやコマンドの実行を行う。
6. **学習・適応（Learning & Adaptation）**: 実行結果やエラーをフィードバックし、計画を修正する。
7. **オーケストレーション（Orchestration）**: 複数のエージェント、リソースの配分、状態遷移を統括する。

各段がどのモジュールで実装されるかの対応表は、1-0 の解説を書く時点で作る（001 Req 7.8）。

### 生成 AI と Agentic AI の比較

| 比較の観点 | 生成 AI | Agentic AI |
|---|---|---|
| 主目的 | プロンプトに対するコンテンツの生成・要約・翻訳 | 定義された長期目標の自律的な達成 |
| 動作形態 | 反応型。1ステップで応答が完了する | 能動型。目標の達成までループを実行する |
| 自律性 | 限定的。ステップごとに人間の指示が要る | 高い。多段階の推論と行動の決定を自律的に行う |
| 環境とのやり取り | モデルの内部知識と静的なコンテキストに依存する | API、DB、シェル、Web などを能動的に操作する |
| エラーからの回復 | ユーザーの再指示やプロンプトの修正に依存する | 環境から得た客観的な事実（Ground Truth）で自己修正する |
| 開発の主眼 | プロンプト設計、RAG パイプライン、出力スキーマ | ワークフロー制御、ACI 設計、ハーネス、状態管理 |

## 2. ワークフローとエージェント

モジュール 2-3 の解説と 4-5 の総合演習で扱う。constitution 原則 1 がこの区別を実装の規約として定める。

### 考え方

- **最もシンプルな設計から始める（Start Simple）**: 与える自律性が高いほど、不確実性とデバッグの難しさが増す。決定論的なコードパスで解ける問題に、自律型エージェントを使わない。
- **Augmented LLM がすべての基本**: エージェント的なシステムの最小単位は、検索（Retrieval）・ツール（Tools）・メモリ（Memory）で補強した単一の LLM である。

### 区別

| | ワークフロー | エージェント |
|---|---|---|
| 制御フローを決めるもの | コード（事前に書いたコードパス） | LLM（ステップ数とツール呼び出しの順序を動的に決める） |
| 向く場面 | 高い予測可能性、低レイテンシ、再現性が要る場合 | オープンエンドで、分岐を事前に予測できない場合 |
| 本カリキュラムでの実装 | `generateText` / `streamText` を素の TypeScript で合成する。`ToolLoopAgent` を使わない（002 Req 3.13） | `ToolLoopAgent` を、3種の停止条件を強制するファクトリ経由で生成する（001 Req 5、6、constitution 原則 2、research ADR-6） |

### 5大ワークフローパターン（Anthropic）

実装はモジュール 2-3（002 Req 3）。

| パターン | 仕組み | 主な用途 | トレードオフと実装の要点 |
|---|---|---|---|
| Prompt Chaining | タスクを直列のステップに分け、出力を後続へ渡す。ステップ間にコードの検証ゲートを置ける | アウトラインから本文を書く。生成後に翻訳・書式変換する | 各ステップの焦点を絞って精度を上げる。直列のため、レイテンシが積み上がる |
| Routing | 分類器が入力を判定し、専門の処理や最適なモデルへ振り分ける | 問い合わせの分類。難度に応じた軽量モデルと高性能モデルの使い分け | 関心の分離で精度が上がる。軽量モデルへ振り分けるとコストが下がる |
| Parallelization | 複数の LLM 呼び出しを並列に実行する。タスクを分ける Sectioning と、同じタスクを複数回試す Voting がある | Sectioning: ガードレール検査と回答の並列実行。Voting: 脆弱性監査、コンテンツ審査 | Sectioning は時間を短縮する。Voting は多数決で確信度を上げる。並列数に比例してトークンを消費する |
| Orchestrator-Workers | オーケストレーターが実行時にタスクを分解し、ワーカーへ並列に委譲して、最後に統合する | 複数ファイルにまたがる修正、多角的な調査レポート | サブタスクが入力に依存して事前に予測できない場合に効く。委譲指示の具体性が品質を左右する |
| Evaluator-Optimizer | 生成器の出力を評価器が明文化した基準で採点・フィードバックし、改善を繰り返す | 専門的な翻訳の推敲、情報の充足度を判定しながらの反復検索 | 明文化された評価基準があるときに機能する。最大反復回数の設定が必須 |

## 3. ACI（Agent-Computer Interface）工学

モジュール 3-1 で扱う（003 Req 1）。

### 考え方

- **エージェントの失敗の多くは、モデルではなくツール定義の不備に起因する**: 仕様が曖昧なツールや低レベルすぎるツールでは、高性能なモデルでも迷走する。
- **客観的な事実（Ground Truth）に基づいて進む**: エージェントは思い込みではなく、ツールの戻り値、コンパイル結果、テストの成否といった事実を取り込んで次の一歩を決める。
- **エージェント設計の3原則（Anthropic）**: シンプルな設計を保つ（Maintain Simplicity）、思考と計画を可視化する（Prioritize Transparency）、ツール仕様を磨き込む（Carefully Craft ACI）。

### 設計の指針

| 指針 | 内容 | 対応する要件 |
|---|---|---|
| 思考の余地を与える | ツールを呼ぶ前に、計画や仮説を書き出せる領域を用意する。推論してからツールを呼ぶと、誤ったパラメータが減る | 003 Req 1.14（Think ツール） |
| 低レベル API をそのまま包まない | REST の CRUD を1対1でツール化すると、往復が増えてトークンとステップを浪費する。業務ロジックをまとめた高水準ツールを提供する（例: 利用者一覧・予定一覧・予定作成を個別に渡さず、会議の設定を1つのツールにする） | 003 Req 1.12 |
| 相対パスを禁止する（ポカヨケ） | ファイル操作ツールは絶対パスだけを受け付ける。シンボリックリンクを解決した実パスが、許可したルートと同一またはその配下（パス区切り単位で判定）であることを確かめる。文字列の前方一致だけでは、同じ接頭辞を持つ別ディレクトリを通してしまう | 003 Req 1.4、1.5 |
| 意味のある識別子 | 機械的な UUID ではなく、名称や 0 始まりの短いインデックスを返す | 003 Req 1.13 |
| 詳細度を選べるようにする | `concise` / `detailed` の応答形式パラメータを設け、必要最小限のトークンだけを取得できるようにする | 003 Req 1.6 |
| 行動を促すエラー | 生のスタックトレースを返さない。どの引数が不正か、正しい入力形式の例、次に取るべき修正アクションを返す。回復可能なエラーと致命的なエラーを分ける | 001 Req 5.8、003 Req 1.2、1.3 |
| 使う場面と使わない場面 | ツールの説明文に「いつ使うか」「いつ使わないか」を書く | 003 Req 1.11 |
| ツール数を絞る | 1つのエージェントに登録するツールは 20 以下にする | 003 Req 1.15、constitution 原則 2 |

## 4. コンテキストエンジニアリング

モジュール 4-1 で扱う（004 Req 1）。

### 考え方

- **コンテキストは有限の計算・注意リソースである**: コンテキストウィンドウが広がっても、不要な情報が溜まるとモデルの注意が散り、指示への追従性が下がる（Context Rot）。コンテキストに入れる情報は、注意バジェット（Attention Budget）の配分として設計する。

### システムプロンプトの適正な高度（Goldilocks Zone）

| 高度 | 例 | 問題 |
|---|---|---|
| 低すぎる | if-else の条件分岐をプロンプトに網羅する | 仕様変更に弱く、想定外の状況で止まる |
| 高すぎる | 「優秀なリサーチャーとして最善を尽くせ」のような抽象的な指示だけ | 評価基準や安全の境界が伝わらず、迷走する |
| 適正 | 達成すべきゴール、許容されない行動の境界、優先順位の判断基準を明記し、具体的な手順はモデルの推論に委ねる | — |

本カリキュラムでは、リファレンス実装のシステムプロンプトを、この3区分を持つテンプレートとして管理する（004 Req 1.8）。

### コンテキスト最適化の3技法

1. **Compaction**: 上限に近づいた会話履歴から、未解決事項・決定事項・重要な値だけを要約して新しいコンテキストへ移し、古いツール呼び出しのログを捨てる。システムプロンプトは要約せず、ツール呼び出しと結果の組を分断しない（004 Req 1.1〜1.3、1.6、1.9）。
2. **Structured Note-Taking**: 進捗や発見を、コンテキストの外の永続ストレージ（ノートファイルや DB）に書き出させ、必要なときに読み出させる（004 Req 1.4）。
3. **段階的開示（Progressive Disclosure）**: 大量の API 出力や DB のダンプを直接 LLM に渡さない。集約・フィルタした最小限の結果と、全体を取得する方法だけをコンテキストに返す（004 Req 1.5）。絞り込みにコードを実行する場合は、サンドボックス内で行う。

### メモリの種類

短期メモリ（会話のメッセージ配列）、長期セマンティックメモリ（ベクトル検索で想起する過去の知識）、外部状態ストア（DB などに保存する構造化状態）の3種を区別し、エージェントごとにどれを使うかを決める（004 Req 1.7）。

## 5. 長時間実行ハーネス

モジュール 4-2 で扱う（004 Req 2）。

### 考え方

- **交代勤務のエンジニアのたとえ**: 数時間〜数日に及ぶタスクを自律的に実行する場合、前任者の記憶が完全にリセットされた交代要員でも作業を引き継げるファイル構造と状態の追跡を、システム側で用意する。
- **「中途半端な状態での完了宣言」を防ぐ**: コンテキストの枯渇と、未完成のまま完了を宣言する失敗を、エージェントの自己申告ではなく検証の仕組みで防ぐ。

### 2層構造（Initializer → Worker）

| 役割 | 責務 | 扱う成果物 |
|---|---|---|
| Initializer（初回） | 要件記述を機能に分解する。検証用のテストスクリプトと進捗ログを作る | 機能リスト（全項目 `passes: false`）、検証テストスクリプト、進捗ログ |
| Worker（2回目以降） | セッションの開始時に合格済み機能の退行を検証する。未完了の機能を1つだけ選んで実装する。完了したらコミットし、進捗ログに追記する | 機能リスト（専用ツールによる検証が成功したときだけ `passes: true`）、進捗ログ、コミット履歴 |

本カリキュラムの実装では、次の点を強制する（004 Req 2）。

- `passes` の更新は、機能 ID だけを入力とする専用ツールに限る。ツールはハーネス側で検証テストを実行し、成功した場合だけ更新する。Worker は機能リストのファイルを書き換えられない。
- 作業ディレクトリはコンテナ（またはデータ分析と同じサンドボックス）内に置き、コードとテストの実行もその中で行う。作業ディレクトリは本体とは別の git リポジトリとし、ホストへの書き込みは学習者が指定したエクスポート先に限る。

## 6. Agent Evals

モジュール 4-3 で扱う（004 Req 3）。

### 考え方

- **過程（Path）ではなく、環境の最終結果（Outcome）を評価する**: エージェントは非決定論的で、想定と違うツールの呼び出し順でも正しく解決することがある。呼び出し順を縛らず、DB の最終状態や生成されたファイルなどの客観的な結果を採点する。
- **早く作り、実際の失敗 20〜50 問から始める**: 大きなデータセットが揃うのを待たない。初期は実際の失敗ケースを 20〜50 問集めるだけで、改善の効果を測れる。

### 評価の4要素

| 要素 | 内容 |
|---|---|
| Task | 明確な入力と成功基準を持つ最小のテストケース |
| Trial | 確率的な揺らぎを捉えるための、同じタスクの1回の試行（複数回実行する） |
| Transcript | 推論、ツール呼び出し、戻り値を含む実行の全記録 |
| Outcome | 試行の終了時点での外部環境の状態（DB の更新、作成されたファイル等） |

### グレーダー

| 種類 | 手法の例 | 利点 | 注意点 | 本カリキュラムでの扱い |
|---|---|---|---|---|
| コードベース | 単体テスト、型検査、正規表現、DB クエリの整合性 | 高速、安価、決定論的で再現できる | 柔軟性に欠け、妥当な別解を弾くことがある | Code-based グレーダー（004 Req 3.4） |
| モデルベース（LLM-as-a-Judge） | ルーブリックによる採点、自然言語のアサーション | 表現の揺らぎや自由記述を柔軟に評価できる | 確率的に揺れる。Judge 自身のハルシネーション | 評価軸ごとに別プロンプトで採点し、「判定不能（unknown）」を選べるようにする（004 Req 3.5、3.13） |
| 人間（SME レビュー） | 専門家による抜き取り監査 | 評価の基準点になる | 高コストで遅い。常時の CI には向かない | レビュー用の出力（トランスクリプトと Outcome の要約）の生成まで（004 Req 3.6） |

### 評価スイートの運用

1. **能力評価（Capability）**: 今のエージェントが解けない挑戦的なタスク。合格率は低くてよく、改善の進捗を測る目標になる。
2. **回帰評価（Regression）**: 解決済みの重要なタスク。常に 100% 近い合格率を保ち、変更による退行を検出する。本カリキュラムでは `mock` モードで品質ゲートに含める（004 Req 3.8）。
3. **卒業と飽和への対策**: 安定して解けるようになった能力評価のタスクは回帰評価へ移し、能力評価には難しい課題を足し続ける（004 Req 3.12、3.14）。
4. **過剰トリガーの防止**: ツールを使うべき問題だけでなく、「ツールを使ってはならない問題」（内部知識で即答すべき平易な問い合わせ等）を評価セットに含める（004 Req 3.11）。

## 7. 安全設計（ブラスト半径の制御）

モジュール 4-4 で扱う（004 Req 4、5、001 Req 6）。

| 手段 | 内容 | 対応する要件 |
|---|---|---|
| 隔離サンドボックス | LLM が生成したコード（データ分析のコード、ハーネスの実装とテスト）は、ホストで実行せず、使い捨てのサンドボックスまたはコンテナの中で実行する。ファイル操作ツールの対象は、許可したワークスペースのルート配下に限る | 001 NFR 隔離実行、003 Req 1.4、1.5、3.2、004 Req 2.10 |
| 権限の分離 | すべてのツールにリスク区分（読み取り専用、書き込み、破壊的アクション）を付ける。読み取り専用のツールは自律実行を許す。破壊的アクション（削除、外部送信等）は実行前に人間の承認を必須にする。書き込みのツールも、外部から取得したコンテンツを取り込んだ run では承認を通す（下の「外部コンテンツの扱い」）。読み取り専用モードでは、書き込みと破壊的アクションのツールを公開しない | 004 Req 4.1〜4.6、4.8、003 Req 1.16、1.17 |
| 承認の改ざん防止 | 承認要求はサーバーが発行し、ツール呼び出し ID と引数に束縛して署名する。1回だけ消費できる。承認待ちの状態をセッションやプロセスをまたいで保持しない | 004 Req 4.3、4.5、4.12、4.13 |
| 強制停止条件 | 最大ステップ数、累積トークン、実行時間の3種の上限をすべてのエージェントに必ず設定し、閉じた語彙の停止理由を記録する。既定値は設定で変えられる | 001 Req 6 |
| 外部コンテンツの扱い | 外部から取得したコンテンツは、出所を付けた区切りで包み、指示として扱わない。外部コンテンツを取り込んだ run では、書き込み・破壊的なツールを必ず承認ゲートに通す。パターンによるインジェクション検知は補助であり、承認ゲートの代わりにならない | 004 Req 4.7、4.8、4.10 |

## 8. アーキテクチャ選定フロー

モジュール 4-5 の総合演習で扱う（004 Req 6）。新しいアプリケーションを設計するときに、次の順で判断する。

1. **単一プロンプト + Augmented LLM で解決できるか**: 質の高いプロンプト、Few-shot の例、検索拡張（RAG）だけで要件を満たせるかを確かめる。満たせるなら、それが最も信頼性が高く安価な解である。
2. **タスクを固定の決定論的なステップに分解できるか**: 直列なら Prompt Chaining、入力の種類や難度で分岐するなら Routing、独立したタスクの並行処理や安全検査なら Parallelization、明確な基準による推敲なら Evaluator-Optimizer を使う。
3. **サブタスクの構成が入力に依存して動的に変わるか**: タスクの全容を事前に予測できない場合は Orchestrator-Workers を採用し、委譲指示の境界条件を厳密に定める。
4. **反復回数が予測できず、環境からのフィードバック（エラーログ、テスト結果）による試行錯誤が必須か**: 複数ファイルにわたる自律的なコーディングや、オープンエンドな調査にだけ、自律型エージェントを採用する。その場合は、ACI のポカヨケ、隔離サンドボックス、状態を引き継ぐハーネス、Evals、強制停止条件を必ず併設する。

エージェントシステムの成否は、複雑なマルチエージェントフレームワークの導入ではなく、決定論的なソフトウェア工学と確率的な言語モデルの境界をどこに引くかという設計判断で決まる。
