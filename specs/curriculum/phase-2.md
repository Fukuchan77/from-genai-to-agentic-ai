# Phase 2 発展編: モダン RAG と決定論的ワークフローパターン

| 項目 | 内容 |
|---|---|
| マイルストーン | M2 |
| 要件 | [spec 002](../002-rag-and-workflows/spec.md)（Req 1〜4）。前提は 001 を継承する |
| 成熟度 | 主に Level 1（Generative AI）から Level 2（AI Agents）への移行 |
| 主な元教材 | 教材 B（2_ai-agent）第4〜12章、教材 A（1_llm-agent）第9・10章、Guide モジュール2 |

LangChain の LCEL やグラフ抽象を使わず、TypeScript の関数合成と AI SDK v7 で、引用付きの RAG、Advanced RAG、Anthropic の5大ワークフローパターン、エージェントデザインパターンを実装する。ワークフロー（コードが制御フローを決める）とエージェント（LLM が制御フローを決める）の区別を、実装で体得するフェーズである（[concepts.md §2](concepts.md#2-ワークフローとエージェント)）。

ハンズオンでは、Postgres + pgvector を Docker Compose で起動する。品質ゲートのテストは、インプロセス DB で実行できるものだけを含め、実行できないものは別のタスクに分ける（001 Req 1.12、002 Req 1.12）。

## モジュール 2-1: TypeScript ネイティブ RAG

| 要件 | 元教材の対応章 |
|---|---|
| 002 Req 1 | マスター、1_llm-agent 第9・10章、2_ai-agent 第4章 |

- **学習目標**
  - LCEL のブラックボックスを使わず、非同期関数の合成で保守しやすい RAG を実装できる。
  - 引用（Citation）付きの回答をストリーミングで返し、回答本文と根拠を UI で対応付けられる。
  - 常に検索する RAG と、検索をツールにして必要なときだけ呼ぶ Agentic RAG の違いを説明できる。
- **主要トピック**
  - チャンク分割の戦略: 文字数だけでなく、Markdown の見出し境界を意識した分割（002 Req 1.2）。
  - AI SDK の `embed` / `embedMany` と pgvector（Drizzle ORM 経由）の直接連携。コサイン類似度検索とメタデータフィルタ。
  - 根拠がないときに推測で回答しない設計（類似度の閾値）（002 Req 1.7）。
  - 引用の検証: 引用したチャンク ID を、そのリクエストで取得したチャンクと照合する（002 Req 1.11）。
  - `mock` モードの埋め込みは入力から決定論的に作るダミーであり、検索精度の評価に使えないこと（001 Req 2.16）。
- **ハンズオン**
  1. PDF と Markdown の文書からナレッジベースを作る。同じ文書を再度取り込んでも、チャンクが重複しないことを確かめる（`local` / `live`、Docker の Postgres）。
  2. 引用付きの回答をストリーミングで返す API と画面を作る。
  3. Agentic RAG モードに切り替え、ナレッジベースと無関係な質問では検索ツールが呼ばれないことを確かめる。
- **習熟度判定の観点**
  - 取得した上位 k 件のチャンクを根拠に回答し、文書名・ページまたは見出し・本文抜粋の引用を返せる（002 Req 1.4、1.5）。
  - 閾値以上のチャンクがないとき、該当情報がない旨を返せる（002 Req 1.7）。
  - Agentic RAG で、検索の要否・クエリ・回数をエージェントに判断させられる（002 Req 1.9、1.10）。

## モジュール 2-2: Advanced RAG

| 要件 | 元教材の対応章 |
|---|---|
| 002 Req 2 | マスター、2_ai-agent 第5〜7章 |

- **学習目標**
  - ナイーブなベクトル検索の限界（キーワードの不一致、文脈の欠落）を、検索手法の組み合わせで克服できる。
  - 手法ごとの効果を、同じ評価用の質問セットで比較できる。
- **主要トピック**
  - **HyDE**: 仮想回答を生成し、その埋め込みで検索する。
  - **Multi-Query**: 1つの質問から、構造化出力で3件のサブクエリを生成して並列に検索する。
  - **ハイブリッド検索と RRF**: Postgres の全文検索とベクトル検索の結果を、Reciprocal Rank Fusion で1つのランキングに統合する。同じチャンクは1回だけ含める。
  - **Rerank**: API キーがあるときだけ再順位付けを行い、ないときはスキップしたことを記録する。
  - パイプラインの各段（サブクエリ生成、検索、統合、Rerank）の進行状況と中間結果を、回答テキストとは別のデータとして UI へストリーミングする（002 Req 2.11）。
  - RAG の評価: 検索精度（上位 k 件中の正解チャンクの含有率）と、LLM-as-a-Judge による忠実性・回答関連性（002 Req 2.9、2.10）。
- **ハンズオン**
  1. 曖昧な問い合わせから3件のサブクエリを生成して並列に検索し、ハイブリッド検索と Rerank を経て回答するパイプラインを作る（`local` / `live`。Rerank は API キーがある場合）。
  2. 手法を個別に有効・無効にして、同じ質問セットで検索精度を比べる（`local`。比較・品質評価のテスト）。
- **習熟度判定の観点**
  - 単純なベクトル検索と、HyDE / Multi-Query / RRF / Rerank を組み合わせた検索の違いを、中間結果を示して説明できる（002 Req 2.8）。
  - Rerank のキーがなくても、統合後のランキングで回答を続けられる（002 Req 2.6）。
  - ラベル付きの質問セット（20 問以上）で、手法の組み合わせごとの精度を比較できる（002 Req 2.9、2.12）。

## モジュール 2-3: 5大ワークフローパターン

| 要件 | 元教材の対応章 |
|---|---|
| 002 Req 3 | マスター、Guide モジュール2、2_ai-agent 第8章、3_genai-agent 第2・10章 |

- **学習目標**
  - LangGraph などのグラフ抽象を使わず、Anthropic の5大ワークフローパターンを素の TypeScript と AI SDK で実装できる。
  - 要件に応じてパターンを選び、利点とトレードオフを説明できる（[concepts.md §2](concepts.md#5大ワークフローパターンanthropic)）。
- **主要トピック**
  1. **Prompt Chaining**: 直列のパイプラインと、ステップ間の検証。検証に失敗したら後続を実行しない。
  2. **Routing**: 入力の分類による処理の振り分けと、該当しない場合のフォールバック。難度に応じた軽量モデルと高性能モデルの振り分け（002 Req 3.12）。
  3. **Parallelization**: Sectioning（分割して並列）と Voting（多数決。最多票が同数なら「同数」を返す）。
  4. **Orchestrator-Workers**: 実行時のタスク分解と、ワーカーへの並列委譲。
  5. **Evaluator-Optimizer**: 0〜100 点のスコアとフィードバックによる改善ループ。合格の判定は、LLM の自己申告ではなくコードがスコアと合格基準を比べて行う。
  - 制御フローをコードで書き、`ToolLoopAgent` を使わない理由（002 Req 3.13）。
- **ハンズオン**: 仕様書のドラフトを生成し、専門の評価器（例: セキュリティ、パフォーマンス）で並列に採点して、合格基準（既定 85 点）に達するか最大反復回数（既定 3 回）に達するまで推敲する Evaluator-Optimizer を作る。統合スコアは評価器ごとのスコアの最小値とし、合格しなかった場合は最高スコアの生成物を未合格と明示して返す（`local` / `live`。002 Req 3.8〜3.11）。
- **習熟度判定の観点**
  - 5パターンを、それぞれ独立して呼び出せる関数として実装できる（002 Req 3.1）。
  - Orchestrator-Workers と Evaluator-Optimizer を、要件に応じて正しく選べる。
  - Evaluator-Optimizer の結果として、反復回数と各反復のスコア・フィードバックの履歴を返せる（002 Req 3.9）。

## モジュール 2-4: エージェントデザインパターン

| 要件 | 元教材の対応章 |
|---|---|
| 002 Req 4 | 2_ai-agent 第11・12章（復元） |

- **学習目標**
  - 元教材の 18 のエージェントデザインパターンの体系を理解する。
  - 主要な6パターンを、グラフ抽象なしの TypeScript で実装し、使い分けられる。
- **主要トピック**
  - 18 パターンの体系と、LangGraph のグラフ定義で書く場合と TypeScript の関数で書く場合の比較（001 Req 7.9）。
  - 実装する6パターン: Passive Goal Creator、Prompt/Response Optimizer、Single-Path Plan Generator、Multi-Path Plan Generator、Self-Reflection / Cross-Reflection（生成時と異なるモデルによる批評）、Role-Based Cooperation（役割ごとの `ToolLoopAgent` へ作業を順に受け渡す）。
  - 18 パターンのそれぞれが、リファレンス実装のどこに対応するか、解説だけで扱うか（002 Req 4.8）。
- **ハンズオン**: 曖昧な指示から目標仕様を作り（Passive Goal Creator）、複数の候補計画から評価器が1つを選び（Multi-Path Plan Generator）、リサーチャー・コーダー・レビュアーの役割で成果物を作る（Role-Based Cooperation）流れを実装する（`local` / `live`）。
- **習熟度判定の観点**
  - 6パターンを、それぞれ独立して呼び出せる関数として実装できる（002 Req 4.1）。
  - 情報が不足した指示に対して、不足項目と確認の質問を返せる（002 Req 4.2）。
  - Self-Reflection と Cross-Reflection の違いを、批評と修正の履歴で示せる（002 Req 4.6）。
