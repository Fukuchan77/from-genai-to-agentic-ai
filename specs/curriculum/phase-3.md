# Phase 3 現場実践編: 実務ドメイン特化型エージェント開発

| 項目 | 内容 |
|---|---|
| マイルストーン | M3 |
| 要件 | [spec 003](../003-domain-agents/spec.md)（Req 1〜6）。前提は 001 を継承する |
| 成熟度 | 主に Level 2（AI Agents）から Level 3（Agentic AI） |
| 主な元教材 | 教材 C（3_genai-agent）第2〜7章、教材 B（2_ai-agent）第10章、Guide モジュール3 |

ACI 設計と MCP によるツール統合を土台に、6つの実務ドメインのエージェントを `ToolLoopAgent` で実装する。エージェントは、3種の停止条件を強制するファクトリ経由でだけ生成する（001 Req 6、constitution 原則 2）。

このフェーズの安全上の前提は次の2点である。

- LLM が生成したコードは、ホストでは実行しない。サンドボックスまたはコンテナの中でだけ実行する（001 NFR 隔離実行）。
- すべてのツールにリスク区分（読み取り専用、書き込み、破壊的アクション）を付ける。承認ゲート（004 Req 4）が実装されるまでは、書き込みと破壊的アクションのツールをエージェントに登録しない（003 Req 1.16、1.17）。M3 のハンズオンとテストは、読み取り専用のツールだけで完結させる。

## モジュール 3-1: ACI と MCP

| 要件 | 元教材の対応章 |
|---|---|
| 003 Req 1 | マスター、Guide モジュール3、3_genai-agent 第2・3章 |

- **学習目標**
  - Anthropic の ACI 設計原則を理解し、エージェントが誤用しにくいツールを設計できる（[concepts.md §3](concepts.md#3-aciagent-computer-interface工学)）。
  - 独自のツール定義から、MCP による標準的な接続へ移行できる。
- **主要トピック**
  - ポカヨケ: 相対パスの禁止と、シンボリックリンクを解決した実パスによるワークスペースの包含判定（003 Req 1.4、1.5）。意味のある識別子、`concise` / `detailed` の応答形式。
  - 生のスタックトレースではなく、修正アクションを示すエラー。回復可能なエラーと致命的なエラーの分類（003 Req 1.2、1.3）。
  - ツールの説明文に「いつ使うか」「いつ使わないか」を書く。低レベル API を包んだツールと高水準ツールのステップ数・トークン数の比較。Think ツール（003 Req 1.11〜1.14）。
  - 公式 MCP SDK で自作するファイルシステム MCP サーバー（stdio 接続）と、AI SDK v7 の MCP クライアント。エージェントごとの許可リストと、ツール数 20 以下の制限（003 Req 1.7、1.8、1.15）。
  - MCP とエージェント間通信プロトコル（A2A / ACP）の役割の違い（本カリキュラムは MCP だけを扱う）。
- **ハンズオン**
  1. ローカルファイルシステムを読み取る MCP サーバーを自作し、エージェントから stdio で接続する（`local` / `live`）。
  2. GitHub のアクセストークンがあるときだけ、GitHub の MCP サーバーへ接続する（`live`、GitHub のトークン）。
  3. MCP サーバーを停止し、そのサーバーのツールが利用不可として扱われ、理由が通知されることを確かめる。
- **習熟度判定の観点**
  - ツール定義から、曖昧なパラメータや相対パスを排除できる（003 Req 1.1、1.4）。
  - 許可ワークスペースの外を指すパス（同じ接頭辞を持つ別ディレクトリ、シンボリックリンク経由を含む）を拒否できる（003 Req 1.5）。
  - MCP サーバーのツールを、許可リストで絞ってエージェントに登録できる（003 Req 1.8）。

## モジュール 3-2: ヘルプデスク・エージェント（Plan-and-Execute）

| 要件 | 元教材の対応章 |
|---|---|
| 003 Req 2 | マスター、3_genai-agent 第4章 |

- **学習目標**
  - 複雑な問い合わせに対して、まず実行計画を立て、進捗に応じて計画を組み替えながら実行するパターンを実装できる。
- **主要トピック**
  - Planner: 依存関係を持つタスクの一覧を、構造化出力で生成する。不正な計画（循環、存在しないタスクへの依存、空の計画）は実行せずに再生成する（003 Req 2.1、2.10）。
  - Executor: 依存関係の順にタスクを実行し、各タスクではツール（マニュアル検索、過去の QA 検索）を使うエージェントを動かす。
  - Replanner: タスクの完了ごとに `continue` / `replan` / `finish` を判断し、再計画の前後の差分を記録する（003 Req 2.3）。
  - 解決（`resolved`）とエスカレーション（`escalated`）。最終回答を保存する前の、認証情報の形状（平文のパスワード、一時パスワード、API キー等）の検査（003 Req 2.6〜2.8）。
- **ハンズオン**: 「現在のタスク」「完了タスク」「修正された計画」がリアルタイムに更新されるヘルプデスクのダッシュボードを作る。サンプルのナレッジとチケットを投入して動かす（`local` / `live`）。
- **習熟度判定の観点**
  - 依存先が完了していないタスクを実行しない（003 Req 2.2）。
  - 再計画の判断理由と、計画の変更前後の差分を示せる（003 Req 2.3）。
  - 認証情報を含む最終回答を保存せず、再作成させられる（003 Req 2.8）。

## モジュール 3-3: データ分析エージェント（サンドボックスと自己修正）

| 要件 | 元教材の対応章 |
|---|---|
| 003 Req 3 | マスター、3_genai-agent 第5章 |

- **学習目標**
  - ホストから隔離した環境で、エージェントに分析コードを生成・実行させ、エラー時には自分でコードを直して再実行させる仕組みを構築できる。
- **主要トピック**
  - TypeScript から E2B のサンドボックスを操作する構成。E2B のキーがないときは、コンテナが使えればローカルのコンテナをサンドボックスにする（003 Req 3.8）。
  - 実行時エラー（Traceback）をエージェントへ返すリフレクションのループ。修正は最大 3 回まで（003 Req 3.3、3.4）。
  - 生成されたグラフ画像と表データの、UI へのストリーミング（Generative UI）。
  - サンドボックスの寿命: 分析セッションごとに作り、終了操作か一定時間のアイドル（既定 10 分）で破棄する（003 Req 3.7）。
  - `mock` モードでは、コードを受け取って定義済みの出力を返す疑似サンドボックスで制御を検証する（003 Req 3.10）。
- **ハンズオン**: CSV または Excel のファイルと「売上の推移と異常値を分析して可視化せよ」という指示から、コードの生成 → サンドボックスでの実行 → エラーの自動修正 → チャートの描画までを自律的に完遂するエージェントを作る（`local` / `live`、E2B のキーまたはコンテナ実行環境）。
- **習熟度判定の観点**
  - 生成したコードがホストで実行されないことを説明し、テストで示せる（003 Req 3.2）。
  - コードの実行エラー時に、エージェントが修正して再実行するループを構築できる（003 Req 3.3）。
  - 生成したコード、標準出力、エラー出力、修正回数を学習者に示せる（003 Req 3.6）。

## モジュール 3-4: 階層型リサーチエージェント（Agent-as-a-Tool）

| 要件 | 元教材の対応章 |
|---|---|
| 003 Req 4 | マスター、3_genai-agent 第6章 |

- **学習目標**
  - 複雑なメッセージパッシングのフレームワークを使わずに、専門のサブエージェントを束ねる階層型のマルチエージェントを実装できる。
- **主要トピック**
  - Agent-as-a-Tool: サブエージェントを、入力スキーマ付きのツールとして Supervisor に渡す設計。
  - サブエージェントのトランスクリプト全体ではなく、要約した結果だけを Supervisor へ返す（003 Req 4.4）。
  - arXiv の検索と、レポート中の論文の言及を取得済みの論文と照合する検証（003 Req 4.3、4.5）。
  - 呼び出し回数の上限、サブエージェントの失敗と再試行、欠落した観点の明記（003 Req 4.6〜4.8）。
  - LangGraph Studio の代わりに、各サブエージェントの呼び出し・ツール実行・中間成果物を区別して表示する Agent Inspector UI（003 Req 4.9）。
  - Supervisor と各サブエージェントのトークン使用量の内訳（003 Req 4.10。4-5 の判断材料になる）。
- **ハンズオン**: 検索、手法の精読、市場への影響評価の3つのサブエージェントを Supervisor が統括し、AI 論文の総合リサーチレポートを Markdown で出力するシステムを作る（`local` / `live`、arXiv へのアクセス）。
- **習熟度判定の観点**
  - サブエージェントをツールとして Supervisor から呼び出せる（003 Req 4.1）。
  - 取得していない論文への言及をレポートから除去できる（003 Req 4.5）。
  - サブエージェントの失敗時に、残りの結果でレポートを作り、欠落した観点を明記できる（003 Req 4.6）。

## モジュール 3-5: 要件定義書生成エージェント

| 要件 | 元教材の対応章 |
|---|---|
| 003 Req 5 | 2_ai-agent 第10章（復元） |

- **学習目標**
  - 利用者へのヒアリングを通じて要件を構造化し、要件定義書を生成するエージェントを構築できる。
- **主要トピック**
  - 元教材の4つの役割（ペルソナ生成、インタビュー、情報の十分性の評価、文書生成）を、型付きの関数とエージェントに分ける。
  - インタビューのラウンドごとの十分性の判定と、不足項目に絞った追加の質問。ラウンド数の上限（既定 5）（003 Req 5.4、5.5）。
  - 回答ごとに要件（機能、非機能、制約、未確認事項）を抽出し、画面上のプレビューを更新する（003 Req 5.3）。
- **ハンズオン**: プロダクトの概要から想定利用者のペルソナを作り、対話形式でインタビューを進め、固定の章立てを持つ Markdown の要件定義書をダウンロードできるアプリを作る（`local` / `live`）。
- **習熟度判定の観点**
  - 情報が十分かを構造化出力で判定し、不足項目を返せる（003 Req 5.4）。
  - 上限到達で終了した場合、「未確認事項」の章に不足項目を列挙できる（003 Req 5.6）。

## モジュール 3-6: マーケティング支援エージェント

| 要件 | 元教材の対応章 |
|---|---|
| 003 Req 6 | 3_genai-agent 第7章（復元） |

- **学習目標**
  - 複数のペルソナによる合議で文案を改善するループと、会話から抽出した利用者プロファイルに基づくレコメンドを構築できる。
- **主要トピック**
  - ロールプレイによる合議: 複数のペルソナ（既定は辛口なマーケター、一般消費者、SEO スペシャリスト）が、他のペルソナの発言を踏まえて順に意見を述べるラウンドロビン。合意の判定と最大ラウンド数（既定 3）（003 Req 6.1、6.2）。
  - 会話からの利用者プロファイル（関心事、予算、懸念点）の逐次抽出と、レコメンド表示の更新（Generative UI）（003 Req 6.4）。
  - レコメンドを商品カタログの中からだけ選び、カタログにない商品を除去する検証（003 Req 6.5）。
- **ハンズオン**: 広告コピーを入力するとペルソナの合議で改善案が出る画面と、会話に応じてプロファイルとレコメンドが更新されるチャットを作る（`local` / `live`）。
- **習熟度判定の観点**
  - 合議の終了理由と、ラウンドごと・ペルソナごとの発言を返せる（003 Req 6.2）。
  - カタログに存在しない商品をレコメンドから除去できる（003 Req 6.5）。
