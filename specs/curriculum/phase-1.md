# Phase 1 基礎編: モダン Web ネイティブ AI アプリ開発

| 項目 | 内容 |
|---|---|
| マイルストーン | M1（MVP） |
| 要件 | [spec 001](../001-agentic-ai-platform/spec.md)（Req 1〜7、NFR）。設計は [plan](../001-agentic-ai-platform/plan.md) |
| 成熟度 | 主に Level 1（Generative AI）。1-2 のツール呼び出しで Level 2（AI Agents）の入口を扱う |
| 主な元教材 | 教材 A（1_llm-agent）全編、教材 B（2_ai-agent）第1〜3章、Guide モジュール1 |

Streamlit + LangChain によるプロトタイプを、Next.js App Router + AI SDK v7 の本番品質のアプリへ移す。受動的な生成（チャット、構造化要約）から始め、`ToolLoopAgent` によるツール呼び出しで AI エージェントへの転換を最小構成で体験する。後続のフェーズが依存する基盤（モノレポ、品質ゲート、実行モード、モデルカタログ、停止条件、ツールの規約、解説の枠組み）も、このフェーズで固める。

Phase 1 の解説には、Python / Streamlit 経験者向けの対比コラム（例: `st.session_state` と `useChat` / `useState`、ボタンを押すたびの再実行とイベントハンドラ）を入れる（001 Req 7.10）。

## モジュール 1-0: 導入 — 生成 AI から Agentic AI へ

| 要件 | 元教材の対応章 |
|---|---|
| 001 Req 7.7、7.8 | Guide モジュール1（復元） |

解説が中心のモジュールで、コードは書かない。

- **学習目標**
  - 生成 AI（反応型）と Agentic AI（能動型）の構造的な違いを説明できる。
  - IBM の3段階成熟度モデルと、Agentic AI の7段階の閉ループを説明できる。
  - プロンプトの工夫からシステム全体（ツール、メモリ、停止条件、評価）の設計へ重心が移る理由を説明できる。
- **主要トピック**: 「テキストの生成」から「状態の変更」へ、LLM は認知・計画エンジン、生成 AI と Agentic AI の比較マトリクス（[concepts.md §1](concepts.md#1-生成-ai-から-agentic-ai-へ)）。
- **観察・確認課題**: 例として示すシステムの記述を3つの水準に分類する。7段階の各段が、どのモジュールで実装されるかを対応表で確かめる。
- **習熟度判定の観点**
  - 与えられたシステムの記述を、根拠を挙げて3水準のいずれかに分類できる。
  - 7段階の各段を、カリキュラムのどのモジュールで実装するかを対応表から示せる。

## モジュール 1-1: 開発環境とモダンスタック基盤

| 要件 | 元教材の対応章 |
|---|---|
| 001 Req 1、2 | マスター、1_llm-agent 第1・2章 |

- **学習目標**
  - pnpm workspaces + Turborepo のモノレポを、mise のタスク経由で操作できる。
  - 1コマンドの品質ゲート（`mise run gate`: lint、format、typecheck、test）で全ワークスペースを検証できる。
  - LLM の呼び出し先を、コードを変えずに `mock` / `local` / `live` の間で切り替えられる。
- **主要トピック**
  - Streamlit の全行再実行モデルと、App Router の差分ストリーミングレンダリングの比較。
  - Server Components と Client Components の境界。API キーをサーバー側でだけ扱う原則（001 Req 1.10）。
  - React Compiler による自動メモ化（手書きの `useMemo` / `useCallback` を前提にしない）。
  - エージェント基盤ライブラリ（`packages/ai-core`）を UI から分離する理由（001 Req 1.2）。
  - 版の方針: 最新安定版の完全一致での固定、TypeScript 7.1 先行版と後退の条件、サプライチェーン対策（001 Technical Constraints、NFR）。
  - 実行モードとモデルカタログ（001 Req 2）。モデル ID をカタログの外に書かない理由（constitution 原則 8）。
  - 空振りしない品質ゲート: テスト中のネットワーク遮断、0 件を失敗にする検査（001 Req 1.15、2.11）。
- **ハンズオン**
  1. `mise install` → `mise run setup` → `mise run gate` を実行する。API キー・Docker・ネットワークなしで完走することを確かめる（`mock`）。
  2. Ollama を起動し、既定の `local` モードで Web アプリを動かす（`local`、Ollama）。
  3. 必須の環境変数を外して起動し、不足した変数名と機能名を示すエラーを確かめる。
  4. ローカル依存サービス（Postgres + pgvector、Langfuse）をコンテナで起動し、必要なリソースを確かめる（Docker。M2 以降の準備）。
- **習熟度判定の観点**
  - クリーンな clone から、キーなしで `mise run gate` を成功させられる（001 Req 1.3〜1.5、1.11）。
  - 設定だけで実行モードとプロバイダを切り替えられ、テストでは `mock` に固定されることを説明できる（001 Req 2.1、2.5）。
  - モックされていない通信がテストを失敗させることを、テストで示せる（001 Req 2.11）。

## モジュール 1-2: AI SDK v7 Core とツール呼び出し

| 要件 | 元教材の対応章 |
|---|---|
| 001 Req 3、5（Req 6 を適用） | マスター、1_llm-agent 第3・4・11章、2_ai-agent 第1〜3章 |

- **学習目標**
  - `generateText` / `streamText` と、`Output.object` による構造化出力、`ToolLoopAgent` によるツール呼び出しループを使い分けられる。
  - 複数のモデル・プロバイダを、同じ UI で会話の途中から切り替えられる。
  - ツールの実行状況と結果を、型付きの UI コンポーネントとして描画できる（Generative UI）。
- **主要トピック**
  - メッセージのロール設計（system / user / assistant / tool）、テンプレートによるプロンプト構築、Few-shot / CoT（001 Req 7.9）。
  - 推論モデルがエージェントの計画に与えた影響。推論トークンの受信と、最終回答からの分離表示。
  - UI メッセージストリームによる逐次配信と、停止操作の伝播。
  - モデル切り替え時の履歴の扱い: 切り替え先が受け付けないパーツを送信時に除外・変換し、表示は保持する（001 Req 3.3）。
  - 画像入力（マルチモーダル）、ペルソナ（バージョン管理されたシステムプロンプトのテンプレート）の切り替え、`live` モードでのレート制限（001 Req 3.9〜3.11）。
  - LangChain の AgentExecutor と `ToolLoopAgent` の対比。停止条件3種（ステップ数、累積トークン、実行時間）と停止理由。トークンと時間の上限はステップ完了時の近似判定であること（001 Req 6.1）。
  - 時刻を注入する設計（Clock）と、ツールのエラーをツール結果として返す設計（001 Req 5.7、5.8）。
- **ハンズオン**
  1. モデルとペルソナを切り替えられるストリーミングチャットを作る。画像の添付、生成の停止、エラー時の再送を確かめる（`local` / `live`）。
  2. 外部 API キーなしで動くサンプルツール（現在時刻、計算、為替換算、天気）を持つツールエージェントを作り、ツールの状態と結果をカードで描画する（`local` / `live`）。
  3. Web 検索ツールを、API キーがあるときだけ登録する。キーがないときに UI が無効の理由と必要な設定を表示することを確かめる（`local` / `live`、Web 検索の API キー）。
  4. 停止条件に達したときの停止理由（`step-limit` など）と、ステップ数・トークン・経過時間の表示を確かめる。
- **習熟度判定の観点**
  - 応答のチャンクを受信するたびに表示でき、停止しても受信済みのテキストが残る（001 Req 3.1、3.5）。
  - 会話の途中でモデルを切り替えても、履歴を保ったまま次の応答を生成できる（001 Req 3.3）。
  - ツールが不要な質問ではツールを呼ばずに回答し、呼び出したツールの一覧を結果に含められる（001 Req 5.6）。
  - すべてのエージェントが3種の停止条件を持ち、停止理由を閉じた語彙で返すことをテストで示せる（001 Req 6.1、6.2）。

## モジュール 1-3: 構造化出力と要約パイプライン

| 要件 | 元教材の対応章 |
|---|---|
| 001 Req 4 | マスター、1_llm-agent 第6〜8章 |

- **学習目標**
  - 正規表現やプロンプトの指示によるパースに頼らず、スキーマ駆動で型付きのオブジェクトを得られる。
  - スキーマ検証を通過したオブジェクトだけを UI とライブラリ利用者へ返し、検証失敗時の再生成を設計できる。
  - 長い入力を分割すべきかを、コンテキスト上限とトークン数から判断できる。
- **主要トピック**
  - `Output.object` による構造化出力と、部分オブジェクトの逐次描画。部分オブジェクトは暫定表示であり、確定値はスキーマ検証を通過したものだけであること（001 Req 4.3〜4.5）。
  - Web 記事の本文取得と、YouTube 字幕のタイムスタンプ付き取得。字幕からの目次（チャプター）生成（001 Req 4.9〜4.11）。
  - Map-Reduce が不要になった理由と、分割が必要になる境界。分割したかどうかと判断に使ったトークン数を結果に残す（001 Req 4.6、4.12）。
  - プロンプトキャッシュの原理とコスト。キャッシュ位置を明示するプロバイダと、自動でキャッシュするプロバイダの違い（001 Req 4.8）。
- **ハンズオン**
  1. Web 記事の URL、YouTube の URL、字幕テキストのいずれかを入力として、タイトル・3行の要点・重要タグ・アクション項目を持つ要約を生成し、確定したフィールドから順にカードへ描画する（`local` / `live`）。
  2. 取得に失敗する URL や字幕のない動画を入力し、LLM を呼ばずに理由付きのエラーになることを確かめる。
  3. 同じ長い入力で要約を繰り返し、キャッシュ読み出しトークン数を比べる（`live`。キャッシュに対応するプロバイダ）。
- **習熟度判定の観点**
  - スキーマに適合しない出力を再生成し（最大2回）、それでも失敗した場合に検証エラーの内容を返せる（001 Req 4.4）。
  - 入力がコンテキスト上限に収まる場合は全文を1回で、超える場合は分割して要約できる（001 Req 4.6）。
  - 対応するプロバイダでプロンプトキャッシュを有効にし、キャッシュ読み出しトークン数を示せる（001 Req 4.8）。
