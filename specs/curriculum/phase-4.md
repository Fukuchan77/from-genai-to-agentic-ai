## モジュール 4-1: コンテキストエンジニアリング

| 要件 | 元教材の対応章 |
|---|---|
| 004 Req 1 | マスター、Guide モジュール4、3_genai-agent 第2章 |

- **学習目標**
  - トークンの枯渇と Context Rot（長いコンテキストによる注意の散漫、指示追従性の低下）を防ぐ手法を実装できる（[concepts.md §4](concepts.md#4-コンテキストエンジニアリング)）。
- **主要トピック**
  - システムプロンプトの適正な高度（Goldilocks Zone）と、ゴール・行動の境界・優先順位の判断基準の3区分を持つテンプレート（004 Req 1.8）。
  - Compaction: 閾値（既定: コンテキスト上限の 70%）を超えたら、未解決事項・決定事項・重要な値を残して履歴を置き換える。システムプロンプトは要約しない。ツール呼び出しと結果の組を分断しない（004 Req 1.1、1.2、1.9）。
  - Structured Note-Taking: 外部ストレージのノートへの記憶のオフロード（004 Req 1.4）。
  - 段階的開示: 大きなツール出力（既定 2,000 トークン超）をそのまま入れず、集約・フィルタした結果を返す（004 Req 1.5）。
  - メモリの3種（短期、長期セマンティック、外部状態ストア）の使い分け（004 Req 1.7）。
- **ハンズオン**: 長い会話のログに対して閾値で Compaction を実行し、実行前後のトークン数と削減率を記録しながら、注意バジェットを保つ会話管理エンジンを作る（`local` / `live`）。
- **習熟度判定の観点**
  - Compaction の後も、未解決事項と重要な値が保持されることをテストで示せる（004 Req 1.2）。
  - Compaction の要約生成が失敗しても、元の履歴を壊さない（004 Req 1.6）。
  - ツール呼び出しと結果の組の一方だけが残る状態を作らない（004 Req 1.9）。

## モジュール 4-2: 長時間実行ハーネス

| 要件 | 元教材の対応章 |
|---|---|
| 004 Req 2 | マスター、Guide モジュール4 |

- **学習目標**
  - セッションをまたぐ長時間のタスクで、中途半端な状態での完了宣言を防ぐ2層のハーネス（Initializer → Worker）を構築できる（[concepts.md §5](concepts.md#5-長時間実行ハーネス)）。
- **主要トピック**
  - Initializer: 要件の分解、機能リスト（全項目 `passes: false`）、検証テストスクリプト、進捗ログの生成（004 Req 2.1）。
  - Worker: セッション開始時の退行検証、未完了の機能を1つだけ選んで実装、完了時のコミットと進捗ログへの追記（004 Req 2.2、2.5）。
  - `passes` の更新は、ハーネス側で検証テストを実行する専用ツールに限る。Worker の自己申告を根拠にしない。Worker は機能リストを書き換えられない（004 Req 2.3、2.4、2.6）。
  - 隔離: 作業ディレクトリをコンテナ内の独立した git リポジトリにし、コードとテストの実行もその中で行う。ホストへの書き込みはエクスポート先に限る（004 Req 2.9〜2.12）。
- **ハンズオン**: 複数の機能要件を持つ Web コンポーネント群を、検証テストが全件合格するまでコミットを重ねて自律的に構築する2層ハーネスを作る（`local` / `live`、コンテナ実行環境）。
- **習熟度判定の観点**
  - Initializer と Worker を分けた2層ハーネスを実装できる。
  - 検証テストに失敗した機能の `passes` が更新されないことをテストで示せる（004 Req 2.4。`mock` では疑似実行環境を使う、004 Req 2.14）。
  - コンテナ実行環境がない場合に、ハーネスを起動しない（004 Req 2.13）。

## モジュール 4-3: Agent Evals

| 要件 | 元教材の対応章 |
|---|---|
| 004 Req 3 | マスター、Guide モジュール5、3_genai-agent 第8章 |

- **学習目標**
  - 推論の過程（Path）ではなく、環境の最終結果（Outcome）を客観的に評価するパイプラインを構築できる（[concepts.md §6](concepts.md#6-agent-evals)）。
- **主要トピック**
  - 評価の4要素（Task、Trial、Transcript、Outcome）（004 Req 3.1）。
  - グレーダー: Code-based（決定論的なアサーション）と LLM-as-a-Judge（ルーブリック採点）。Judge は注入可能なインターフェースにし、決定論的なフェイク Judge で単体テストする。Human SME はレビュー用の出力で支援する（004 Req 3.3〜3.6）。
  - Capability と Regression の2区分。Regression は `mock` で品質ゲートに含め、Capability と LLM-as-a-Judge は別のコマンドで `local` / `live` で実行する（004 Req 3.2、3.8、3.9）。
  - 飽和の警告、卒業（Capability から Regression への昇格）、過剰トリガーのケース（004 Req 3.11、3.12、3.14）。
  - 評価は実際の失敗 20〜50 問から始める（001 Req 7.9）。評価タスクの合成生成と、人間のレビューを経た追加（004 Req 3.15）。
- **ハンズオン**: Vitest で、エージェント実行後の DB の状態や生成ファイルを検証する評価スイートを作り、回帰評価を CI の品質ゲートに組み込む（Regression は `mock`、Capability は `local` / `live`）。例: ヘルプデスクのチケットがパスワードのリセット依頼で `resolved` になり、最終回答に認証情報の形状が含まれないことを Outcome で検証する。
- **習熟度判定の観点**
  - エージェントの最終アウトカムを検証する回帰評価を、CI で運用できる（004 Req 3.4、3.8）。
  - 品質ゲートに含める回帰評価が、制御ロジックを壊した変更で失敗することを確認できる（004 Req 3.8、001 Req 1.16）。
  - タスクごとの合否、スコア、所要時間、トークン使用量のレポートを出せる（004 Req 3.10）。

## モジュール 4-4: 安全設計・オブザーバビリティ

| 要件 | 元教材の対応章 |
|---|---|
| 004 Req 4、5、001 Req 6 | マスター、Guide モジュール5、3_genai-agent 第9章、2_ai-agent 第7・9章 |

- **学習目標**
  - 本番運用での暴走とセキュリティのリスク（プロンプトインジェクション、データの破壊）を遮断できる（[concepts.md §7](concepts.md#7-安全設計ブラスト半径の制御)）。
  - エージェントの LLM 呼び出しとツール実行をトレースで可視化し、原因を追跡できる。
- **主要トピック**
  - ブラスト半径の最小化: 使い捨てのコンテナ、読み取り専用モード、強制停止条件（001 Req 6。M1 から適用している仕組みをここで解説する）。
  - Human-in-the-Loop の承認ゲート: 破壊的アクションの前に、ツール名と引数を示す承認ダイアログを出す。承認要求はサーバーが発行して署名し、1回だけ消費できる。拒否はツール結果としてエージェントへ返す。承認待ちはセッションをまたいで保持しない（004 Req 4.2〜4.5、4.12、4.13）。
  - 外部コンテンツの扱い: 区切りで包む、取り込んだ run では書き込み・破壊的なツールを必ず承認ゲートに通す、パターン検知は補助的な防御にとどまる（004 Req 4.7、4.8、4.10）。
  - 出力のサニタイズ、MCP のツール注釈からのリスク区分の決定、監査ログ（004 Req 4.9、4.11、4.14）。
  - OpenTelemetry のスパン（LLM 呼び出し、ツール実行、ワークフローのステップ）と OTLP のエクスポート。既定の収集先は Langfuse。認証情報をスパンに残さない。本文の記録は設定で切り替える（004 Req 5）。
- **ハンズオン**: ツールの実行前にクライアントで承認か拒否の入力を待ち、承認されたときだけサーバー側で処理を再開する承認 UI を作る。ファイル削除、GitHub への issue 作成、疑似メールボックスへの回答送信を承認の対象にする（`local` / `live`。GitHub はトークンがある場合）。トレースを Langfuse で1回の実行全体として閲覧する（Docker の Langfuse）。
- **習熟度判定の観点**
  - 不可逆な操作（削除、外部送信等）の前に、承認ゲートを確実に設けられる（004 Req 4.2、4.15）。
  - 引数を改ざんした承認応答や消費済みの承認応答で、ツールが実行されないことをテストで示せる（004 Req 4.12）。
  - トレースの収集先に接続できなくても、エージェントの実行を続けられる（004 Req 5.5）。

## モジュール 4-5: 総合演習 — アーキテクチャ選定

| 要件 | 元教材の対応章 |
|---|---|
| 004 Req 6 | Guide 総合演習（復元） |

- **学習目標**
  - 新しいアプリケーションの要件に対して、単一プロンプト・ワークフロー・自律型エージェントのどれを採用すべきかを、根拠を示して判断できる（[concepts.md §8](concepts.md#8-アーキテクチャ選定フロー)）。
- **主要トピック**
  - 判断フロー: 単一プロンプト + Augmented LLM で足りるか → 固定のワークフローに分解できるか → サブタスクが入力依存で動的か → 反復回数が予測できず、環境からのフィードバックによる試行錯誤が必須か（004 Req 6.1）。
  - 自律型エージェントを採用する場合に併設する安全策（ACI のポカヨケ、隔離サンドボックス、ハーネス、Evals、強制停止条件）（004 Req 6.4）。
  - マルチエージェント構成のコスト: 3-4 の実測値に基づく、単一エージェント構成とのトークン使用量の比較（004 Req 6.5）。
- **演習**: 10 件以上のシナリオに判断フローを適用し、模範解答（採用するアーキテクチャ、判断の根拠、対応するリファレンス実装のモジュール）と照らし合わせる（004 Req 6.2〜6.4）。
- **習熟度判定の観点**
  - 単一プロンプトで足りるケース、5つのワークフローパターンのそれぞれが適するケース、自律型エージェントが適するケースを見分けられる（004 Req 6.3）。
  - 自律型エージェントを選んだ場合に、併設すべき安全策を挙げられる。
