# hub-alignment — Requirements

## Overview

2026-10-03 に、Agentic AI 系リポジトリの役割を次のように定めた。本リポジトリは**入門から本番品質までを順に学ぶ学習パス**であり、
アーカイブせずに継続する（統合ハブ `vaz-agentic-ai-next` の spec `008` の「ユーザ判断」）。

| リポジトリ | 役割 |
|---|---|
| 本リポジトリ | 学習パス。19 モジュールを順に進める。リファレンス実装は教材用に最小限 |
| `vaz-agentic-ai-next` | 本番の統合ハブ。`docs/guide/` は 8 手法（PE / CE / LE / HE / AE / AO / MCP / EV）別の本番エンジニアリング・リファレンス |
| `next-agentic-stack` / `pydantic-ai-sandbox` | TypeScript / Python のベータ検証レーン |

役割分担と運用ルール（相互リンクで済ませ本文を複製しない、教材コードを第 3 の本番実装にしない、UI 部品の標準は shadcn/ui + Tailwind CSS）は、
`001-agentic-ai-platform` ブランチの `README.md`「関連リポジトリとの役割分担」と
[`specs/curriculum/README.md`](../curriculum/README.md)「本番実装との対応」に記録済みである（同ブランチの PR #10。`main` へは M1 の波の締めで入る）。

本 spec は、この運用ルールを**後続 spec（002〜004）と品質ゲートに落とし込む**。002〜004 は要件承認前で、
「先行マイルストーンの結果に合わせて改訂してよい」状態にある（各 spec の「承認ゲート」節）。承認の前に、
本番の機能との境界を要件として書き込んでおく。

## 前提（001 から継承）

- 次の事項は `001-agentic-ai-platform` を正本とし、本 spec では再定義しない: Clarifications、Technical Constraints、Runtime Environment、LLM Provider & Test Strategy、Glossary、Non-Functional Requirements、Out of Scope / Future Work。
- 品質ゲート（`mise run gate`）は `mock` モードで、API キー・Docker・ネットワークなしで完走する（001 Req 1.5、1.11）。本 spec が加える検査も同じ制約に従う。
- 本文中の `00N Req X.Y` は spec `00N` の要件 X.Y を指す。spec 番号のない `Req X.Y` は本 spec の要件を指す。
- ハブのファイルは別リポジトリにあるため、本 spec ではコードスパンで示す（相対リンクにしない）。

## 承認ゲート

本 spec の要件は、002 の要件承認より前に承認する。Req 1 の改訂を 002〜004 の要件承認に含めるためである。
Req 2〜3 の実装は、各要件が対象とするマイルストーンの実装と同じ波で行う。

## Requirements

### Requirement 1: 後続 spec に本番の機能との境界を書き込む

学習者として、教材の実装が本番のどこを簡略化しているのかを知り、本番ではどう作るかをハブで確かめたい。

**Acceptance Criteria**

1.1 THE プラットフォーム SHALL 002〜004 の各 spec に「本番実装との境界」節を設け、本番の機能を要する要件ごとに、教材で簡略化する点、簡略化の理由、対応するハブの実装または文書を表で示す。
1.2 THE プラットフォーム SHALL 1.1 の表に、少なくとも次の要件を含める。

| 要件 | 教材での扱い | ハブの対応先 |
|---|---|---|
| 002 Req 3（ワークフローパターン） | プロセス内の関数として実装。耐久実行は扱わない | `docs/adr/0005-durable-workflow-engine.md`、`packages/agents/src/supervisor.ts` |
| 003 Req 4（階層型リサーチ） | 単一プロセスのスーパーバイザー | `packages/agents/src/supervisor.ts`、`docs/owasp-agentic-threats-mitigations-mapping.md`（エージェント間の脅威） |
| 004 Req 2（長時間実行ハーネス） | 学習者のコンテナ内で完結 | `docs/guide/harness-engineering.md` |
| 004 Req 4（安全設計と HITL） | 承認待ちをセッションやプロセスをまたいで保持しない（004 Req 4.5） | `apps/web/src/lib/approvals.ts`、`packages/tools/src/allowlist.ts`、`docs/guide/agentops.md` |
| 004 Req 5（オブザーバビリティ） | 学習用途の既定値でスパンに本文を記録する（004 Req 5.4） | `docs/guide/agentops.md`（本番では本文を記録しない） |

1.3 THE プラットフォーム SHALL 認証・RBAC、承認待ちの永続化と再開、ジョブの耐久実行、本番の監査ログ保管を、本リポジトリのリファレンス実装に要件として追加しない。これらを要する学習目標は、解説ドキュメントでハブの実装を参照して扱う。
1.4 WHEN 002〜004 のいずれかの要件が 1.3 に該当する機能を求めると判断された時、THE プラットフォーム SHALL その要件を簡略版に書き換えるか、解説ドキュメントでの参照に置き換え、変更を 1.1 の表に記録する。
1.5 THE プラットフォーム SHALL 1.1〜1.4 の改訂で、002〜004 の要件の採番（受け入れ基準の枝番を含む）を変えない。削る受け入れ基準は欠番とし、理由を書く。

### Requirement 2: 解説ドキュメントからハブの手法ページへのリンクを検査する

学習者として、各モジュールを終えたときに、同じ手法を本番でどう作るかを示すページへ迷わず進みたい。

**Acceptance Criteria**

2.1 THE プラットフォーム SHALL `specs/curriculum/README.md`「本番実装との対応」の表（モジュール → ハブの手法ページ）を、モジュールとハブのページの対応の唯一の定義とする。
2.2 THE プラットフォーム SHALL 各モジュールの解説ドキュメント（001 Req 7）に「本番ではどう作るか」の節を設け、2.1 の表がそのモジュールに割り当てたハブの手法ページすべてへのリンクを置く。1-1（開発環境）はハブの `CLAUDE.md` / `AGENTS.md` へのリンクとする。
2.3 THE プラットフォーム SHALL 2.2 を品質ゲートのリポジトリ規則として検査する。検査はネットワークに接続せず、解説ドキュメント内のリンク先の文字列が 2.1 の表と一致することだけを確かめる。走査した解説ドキュメントが 0 件の場合は失敗させる（001 Req 1.15）。
2.4 IF 2.1 の表にあるモジュールの解説ドキュメントがまだ存在しない場合、THEN THE プラットフォーム SHALL 検査対象から外し、外したモジュールの一覧を検査の出力に含める（未作成のモジュールを合格に数えない）。
2.5 THE プラットフォーム SHALL 解説ドキュメントにハブの文書の本文を転載しない。引用は 1 段落以内とし、出典（リポジトリ、パス、確認日）を添える。
2.6 WHEN ハブの `docs/guide/` のページが改名・削除されたことを学習者または開発者が報告した時、THE プラットフォーム SHALL 2.1 の表を直し、表の更新日を記録する。ハブ側の対応表（`docs/guide/README.md`）と食い違わないことを、表の更新時に人が確認する。

### Requirement 3: HITL の UI 部品とテーマトークンをハブと共有する

学習者として、M4 の承認ダイアログを本番と同じ部品の形で学び、本番の UI へそのまま読み替えられるようにしたい。

**Acceptance Criteria**

3.1 THE プラットフォーム SHALL 004 Req 4.2 の承認ダイアログを、ハブのエージェント UI 部品（ハブ spec `009` Requirement 2、`apps/web/src/components/agent-ui/`）のソースをコピーして作る。ハブ側の部品が存在しない時点では、同じ props の形（ツール名、予定の引数、承認／却下の操作）で作り、ハブの部品ができた時点で置き換える。
3.2 THE プラットフォーム SHALL コピーした部品を表示に専念させ、承認要求の照合・消費・監査（004 Req 4.3、4.9、4.12）を部品の外に置く。
3.3 THE プラットフォーム SHALL `apps/web` の Tailwind v4 テーマトークン（色とコントラスト検査）を、ハブが参照する元として文書化する（ハブ ADR-0008 の Decision）。文書には、トークン名、ライト／ダークの値、コントラスト比の検査方法と基準を含める。
3.4 WHEN 3.3 のトークンを変更した時、THE プラットフォーム SHALL 変更内容を文書に記録し、ハブへ伝える必要があるかを判断して記録する。
3.5 THE プラットフォーム SHALL コピーした部品のソースに、コピー元（ハブのパスとコミット）をコメントで残す。

## Out of Scope

- ハブのリポジトリへの直接の変更（ハブ側の作業はハブの spec `009` が扱う）
- 本リポジトリのリファレンス実装を、本番の機能（認証・RBAC、耐久ワークフロー、承認の永続化）まで拡張すること（Req 1.3）
- ハブと本リポジトリのモデル ID・停止理由の語彙の統一。教材は学習目的に合わせた独自のカタログを持つ（001 Req 2）
- ハブへのリンクの到達性をネットワーク経由で検査すること（Req 2.3）
